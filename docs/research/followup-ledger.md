## L5 readback audit result 2026-11-27 (docs/research/readback-sync-audit.md; library 345f14e; read-only, nothing run)
- INFERRED spec hole: no barrier makes the image->staging copy visible to the HOST (arm64_resources.c: one global ALL_COMMANDS barrier only, no HOST stage / HOST_READ; fence wait gives ordering, not host visibility per the Vulkan "Fences" section; the guide's CPU read-back example uses dstStage HOST / HOST_READ). Likely latent on real drivers (end-of-command-buffer flush) but not guaranteed. Staging memory is HOST_VISIBLE|HOST_COHERENT only (first match), no invalidate path.
- wbverify compares guest pages with stage_map (what ms_finish_down just wrote) - it can NOT detect stale staging data or layout/format mistakes (same xfer layout on both sides).
- Cases where stale data reaches the guest while wbverify says equal: A missing HOST barrier; B down_pending left true after a failed submit; C host_valid false after failed pull (no copy, no write); D ms_finish_down returns 0 on an unreadable descriptor (frame lost in immediate mode); E swap mode: stamp complete while guest pages still old, and a later flag-1 exec's ms_pull clears `owed` and uploads old guest pixels over the GPU frame; F swap fence timeout: display command forwarded first; H layout/format errors; I DONT_CARE with a partial render area reads back undefined pixels. Immediate mode order (GPU done -> guest pages written -> stamp) is correct.
- Minimal fixes (not applied): (1) HOST barrier after every image->buffer copy; (2) clear down_pending on submit failure and require this exec recorded the copy; (3) wbverify against an independent GPU-side hash; (4) swap mode: do not treat a deferred swap as success / pay owed surfaces before flag-1 pulls; (5) set owed=true when ms_finish_down cannot read the descriptor; (6) prefer HOST_CACHED coherent staging with invalidate fallback. Fixes 1, 2, 5 are being implemented on research/g7-hostbarrier; 3, 4, 6 stay proposals (behaviour changes).

### 2. 일반 부팅 / NVRAM — [소스 분석, 미검증]

### 3. ARM64 JIT — [소스 분석, 미측정]
- 캐시는 전체 flush 방식이다: 부분 퇴출(LRU 등) 없음. flush 요청 원인은 코드 영역 가득 참 / 블록 표 가득 참 / emit 실패 / 대기 중 발견 / 기타로 분류되어 이미 세어진다(stats.flush_*). 중복 번역은 dup_* 카운터. 따라서 "캐시 크기 실험"(64/128/256 MiB)과 "엔진 개선"은 별개이며, 엔진 변경은 g7-jit 줄의 req_*, dup_mb 수치가 나온 뒤에만 한다. 근거 없는 알고리즘 변경은 하지 않았다.
- 소스에서 보이는 비효율 후보(미측정): flush 시 전체 재번역(first_s/retrans_s로 측정 가능), core/sysreg.c 의 IC(명령 캐시) 무효화는 HV_IC_FLUSH 환경변수가 있을 때만 전체 flush 를 요청한다(기본 꺼짐, 정정: 앞서 TLBI 로 적은 것은 틀림). 나머지 원인별 빈도는 실기기 측정 필요.

### 4. RAM / Swap — [소스 분석]

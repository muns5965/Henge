# 가짜 프록시 장치와 T12·T13 기준선 (S3) — 기록 (2026-11-11)

범위: `docs/fake-device-impl-scope.md` §4.3·§4.4·S3. 가짜 역방향 프록시 장치를 시험 코드에 추가하고, **변경 전** 코드에서 T12(열린 프록시 연결이 있는 종료)와 T13(연달아 오는 연결 요청)을 기록한다.
제품 코드, 벤더링 소스, 확정 설계는 변경하지 않았다. 후크 없음. 통과/실패 판정 없음. Linux x86_64 한 환경.
표기: [관측], [소스], [추론], [미검증].

## 1. 가짜 프록시 장치 [소스에서 구성]

`third_party/libimobiledevice/src/reverse_proxy.c`를 읽고 만들었다(제어 프로토콜 2).
- 제어 채널(포트 1082): 호스트가 `"BeginCtrl\0"`(10바이트)와 plist(4바이트 리틀엔디언 길이 + 이진 plist)를 보내면, 장치는 `{ConnPort: 1083}`을 같은 형식으로 답하고 100 ms 뒤 연결 요청 명령(uint32 LE 1)을 보낸다. 한 번의 쓰기로 N개를 보내 간격을 없앤다(T13).
- 연결 채널(포트 1083): 호스트가 `"HelloConn\0"`을 보내면 `{Command: HelloConn, Identifier: ...}`로 답한다. T12에서는 이어서 프록시 명령(0x105, `0 3 호스트길이 호스트 포트(BE)`)을 보내 호스트가 `127.0.0.1:<시험 서버 포트>`로 연결하게 하고, 호스트의 ack(2바이트)와 에코를 받는다. 이후 장치는 연결을 열어 둔 채 침묵한다.
- "외부 호스트": 시험이 띄운 루프백 리스너(수락 후 침묵). 호스트의 프록시 연결은 글루 소켓 연결이며 목적이 DEFAULT라서(`fdr.c`만 FDR을 지정) 시험이 `hv_net_guard_allow_local`로 그 주소를 허용 목록에 넣었다. 제품 정책 코드는 바꾸지 않았다. [관측: net_guard 거부 0, 허용 7건(가짜 mux 연결 6 + 이 연결 1)]
- 가짜 restored는 StartRestore 1.5초 뒤 StatusMsg 0(완료)을 보낸다(프록시 연결이 자리 잡을 시간).

## 2. 관측 [관측]

| 사례 | 일반 빌드 (2회) | ASan (2회) | TSan (2회) |
|---|---|---|---|
| t12: 연결 1개 열림 + 침묵, restored 완료 | **45초 안에 `restore_device` 반환 없음**(감시 만료). 만료 시점 통계: 프록시 제어 1, 연결 1, 프록시 명령 ack 1, net_guard 거부 0 | (미실행) | (미실행) |
| t12_close: 같은 구성이나 장치가 프록시 명령 ack 1초 뒤 연결 채널을 닫음 | 0, 2.4 s (정상 반환) | — | — |
| t13: 연결 요청 2개 연달아, 프록시 명령 없음, restored 완료 | 0, 2.5 s. 연결 채널 2개가 접속함. 반환 후 4초 대기 동안 이상 없음(fd 수 변화 없음; 가짜 소켓 포함 측정) | 지적 없음 | **data race 3건 + thread leak 1건**(아래; 보존된 2회차 로그 기준) |

t12 정지 위치 [관측]: 정지 중인 프로세스에 gdb를 붙여 스레드 스택을 얻었다(한 번).
- 주 스레드: `restore_device` → `reverse_proxy_client_free` → `thread_join`
- 제어 스레드: `_reverse_proxy_control_thread` → `thread_join`
- 연결 스레드: `_reverse_proxy_connection_thread`가 호스트 소켓에 대한 `socket_receive_timeout`(프록시 전달 루프)에 머묾

t13 TSan 보고 [관측] (2회차 로그 `case_t13.log` 기준. 1회차 전체 로그는 덮어써져 보존되지 않았고, 1회차에서 확인한 것은 아래 (1)~(3)의 race 3건뿐이다):
- (1) `libusbmuxd.c:1546` `use_tag` — 두 연결 스레드가 전역 태그를 보호 없이 읽고 쓴다.
- (2) `reverse_proxy.c:649`(`reverse_proxy_client_free`가 `client->parent`를 NULL로 쓰는 것)와 제어 스레드의 읽기(`:481`, 루프 조건).
- (3) `reverse_proxy.c:519`(제어 스레드가 `th_ctrl`을 NULL로 쓰는 것)와 연결 스레드의 읽기(`:433`, 루프 조건).
- (4) **thread leak**: 제어 스레드가 `reverse_proxy.c:497`의 `thread_new`로 만든 연결 스레드 T42가 종료됐지만 join되지 않았다. 두 번째 요청이 `th_conn`을 덮어 첫 스레드의 핸들이 사라진다는 소스 독해(P13)와 대응한다.
(2)(3)은 종료 신호를 보호 없이 공유 필드로 전달하는 구조에서 오는 경쟁이다. (1)은 이 설계 항목과 무관한 부수 관측이다. 같은 TSan 빌드의 대조 사례(0)와 t5a_nofree에는 thread leak 보고가 없었다.

## 3. 추론
- T12: 종료 시 `reverse_proxy_client_free`가 제어 스레드를 join하고, 제어 스레드가 마지막 연결 스레드를 join하는데, 연결 스레드의 프록시 전달 루프는 종료 신호(`th_ctrl`)를 보지 않는다. 그래서 **장치가 연결을 닫지 않는 동안 반환하지 못한다**(P15). 장치가 닫으면 반환한다(t12_close). 한도가 없다는 소스 독해와 관측이 일치한다. 영구 정지인지는 45초까지만 확인했다.
- T13: 제어 스레드의 `th_conn`이 단일 변수라서 두 번째 연결 요청이 첫 스레드의 핸들을 덮는 것은 소스상 사실이다(P13). TSan의 thread leak 보고(4)가 "join되지 않은 종료 스레드"라는 결과를 보인다(원인을 핸들 덮어쓰기로 단정하지는 않음). 이번 실행에서는 첫 연결 스레드가 해제된 `client`를 읽는 증상이 ASan에 잡히지 않았다. 4초 대기 안에 스레드가 `th_ctrl` 확인 주기(1초)로 종료하기 때문일 수 있다. "관측되지 않음"이며 "없음"이 아니다.

## 4. 미검증
- t12의 ASan·TSan, 정지 시간의 상한, 정지 중 fd 수.
- thread leak 보고는 보존된 1회분 로그에서만 확인했다(재현성 미확정).
- t13에서 첫 연결 스레드가 프록시 명령 중인 경우(첫 스레드가 오래 사는 경우)의 해제 후 접근.
- 실제 장치의 프록시 사용 형태(제어 프로토콜 1, 여러 연결의 동시성), Android 및 실기기.
- gdb 스택은 한 번만 얻었다.

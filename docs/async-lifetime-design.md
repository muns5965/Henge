# 공통 비동기 작업 수명 관리 상세 설계 (검토용 초안)

> **갱신 안내**: 결정은 `docs/restore-lifetime-integrated-design.md`(통합 설계 권고안)가 대체한다. 이 문서의 사실 항목(P1~P11, P10 판정표)은 근거로 유효하며, "후보"·"결정이 필요한 항목(D1~D7)" 표기는 통합 설계의 권고안으로 대체된다.

상태: 설계 초안. 구현·벤더링 소스 변경은 별도 승인 대상이다.
근거 조사: `docs/tss-integration-design.md` 2.6~2.8절. 시험 명세: `docs/fake-device-test-spec.md`.

표기: **[확인]** 코드로 확인한 사실, **[위험]** 코드상 도달 가능하나 미관측, **[후보]** 설계 후보(미결정), **[미확정]** 장치 응답 또는 시험이 필요.

## 1. 목적과 범위

복원 엔진의 `AsyncDataRequestMsg` 처리 스레드(5종: BasebandData, RecoveryOSASRImage, StreamedImageDecryptionKey, SystemImageData, URLAsset)가 다음과 어긋나지 않게 한다.

- 정책 훅(`hv_net_guard`)의 적용 수명
- `client`와 그 하위 객체의 수명
- 공유 연결(`client->restore->client`)의 사용 순서
- 오류·종료 상태의 전달

범위 밖: FDR 스레드·리버스 프록시 클라이언트(P11 참조, 내부 스레드 수명 미조사), 다른 비동기 경로, TSS 기록 모듈(이 설계가 확정된 뒤 소유권을 따른다).

### P10 상세: 오류 덮어쓰기와 최종 성공 보고

루프는 `err < 0`을 다음 반복 맨 앞에서 보고 `FLAG_QUIT`를 세우지만, 그 반복에서 메시지를 한 건 더 받아 처리하고 `err = handler(...)`로 값을 덮어쓴다(`restore.c:5730~5740`, `5777~5888`). `async_err`는 최초 오류를 보존하는 장치가 아니다: 비동기 작업이 오류를 내지 않으면 0이어서, 동기 경로의 최초 오류가 덮어쓰기로 사라지는 문제를 해결하지 못한다(`async_err`가 0이 아닐 때만 `err`를 대체, 5907~5908행).

| 항목 | 판정 | 근거 |
| --- | --- | --- |
| `err`가 후속 메시지 처리로 덮어써질 수 있음 | 코드 구조상 확인 | 5730~5740, 5777~5888 |
| 최초 오류 정보의 소실 | 코드상 가능 | 위와 같음 |
| `async_err != 0`이면 최종 `err` 대체 | 소스 경로상 확인 | 5907~5908 |
| `restore_device()`가 0을 반환할 가능성 | 코드상 가능, 실행 미관측 | 루프 뒤 `return err`(5924행)에 `FLAG_QUIT`·`restore_finished`로 값을 바꾸는 코드 없음 |
| 호출자가 0을 성공으로 해석해 최종 성공을 보고 | **코드로 확인** (실행 미관측) | `idevicerestore.c:1603~1608`은 `result < 0`일 때만 실패로 반환하고, 0이면 `result == 0` 분기에서 "DONE"과 진행 완료(1.0)를 보고한다. `host/install.c:88~96`은 `idevicerestore_start` 반환 0이면 `HV_INSTALL_DONE`, 아니면 `HV_INSTALL_FAILED` |
| TSS 실패가 성공으로 처리될 가능성 | **코드상 도달 가능, 실행 미관측** | 펌웨어·베이스밴드 처리기의 `-1` → `restore_handle_data_request_msg` → 루프의 `err` 대입 → (다음 반복에서 `FLAG_QUIT`) → 추가 메시지의 처리기가 0을 돌려주면 위 경로로 성공 보고. 장치가 실패 직후 추가 메시지를 보내는지는 [미확정] |

- 엔진 반환 경로(`restore_device`가 0을 반환할 수 있는가)와 상위 호출자의 성공 판정 경로(0을 성공으로 보고하는가)는 별개 질문이며 위 표에서 별도 행으로 둔다.
- 추가 메시지가 없거나(`RESTORE_E_RECEIVE_TIMEOUT`·수신 실패의 `continue`), `MsgType`이 없거나 문자열이 아닌 경우(5757~5763행 `continue`), 또는 어느 분기에도 맞지 않는 문자열 타입(5898~5901행, `err` 미변경)이면 `err`는 보존된다. 수신 오류로 `break`하는 경우는 `err = -11`로 바뀌어 원래 오류가 달라진다.
- 정지점 A(`idevicerestore.c`의 `-1` 직접 반환)는 이 루프를 거치지 않아 영향이 없다.
- 이 경로에서 확인한 메시지 해제: `MsgType` 없음/비문자열은 `plist_free(message)` 후 `continue`, 미분류 문자열 타입은 로그 후 루프 끝의 `free(type)`·`plist_free(message)`로 해제된다. 해제 누락은 발견하지 못했다(오류 보존과 별개의 사항으로 기록).

## 3. 요구조건 (안전성)

| 번호 | 요구 | 시험으로 확인 | 소스 구조로 보장 |
| --- | --- | --- | --- |
| R1 | 신규 작업 등록은 ACTIVE에서만 허용한다. **등록 승인과 활성 작업 수 증가는 하나의 원자적 전환**이고(그렇지 않으면 종료 스레드가 활성 수 0으로 보고 객체를 해제할 수 있다), 등록과 스레드 생성은 한 번의 전환이며 생성 실패 시 등록을 취소한다. 승인된 작업은 이후 `CLOSING`에서도 완료할 수 있어야 한다 | 일부 | 필요 (원자성은 시험으로 입증 불가) |
| R2 | CLOSING에서 신규 요청은 거부하고, 거부 사실이 엔진에 전달된다 | 가능 | 전달 경로 필요 |
| R3 | 이미 등록된 작업의 완료 통지와 활성 수 감소는 CLOSING에서도 허용한다 | 가능 | 필요 |
| R4 | 정상 종료는 작업 완료 확인 뒤에만 객체·정책을 정리한다 | 가능 | 필요 (해제 순서) |
| R5 | 취소 실패(대기 한도 도달) 시 참조 자원 전체와 정책 훅을 유지하고 신규 세션을 차단한다 | 가능 | 필요 (훅 수명) |
| R6 | 활성 작업이 객체를 마지막으로 참조하기 전에는 해당 객체가 무효화되지 않는다(소유자가 세션이든 처리기든 무관). 대상: `client`, `client->restore`, 장치 핸들, restored 연결, 서비스 연결, `build_identity`, `ipsw`, `filesystem`, FDR 연결. 마지막 참조를 추적하기 어려우면 작업 완료 확인을 해제의 보수적 기준으로 쓰되, 이는 **완료 통지가 모든 객체 접근 이후에 발생한다는 동기화 보장이 있을 때만** 성립한다 | 가능(관측) | 필요 |
| R7 | 공유 연결의 송신은 plist 메시지 단위로 직렬화한다 | 가능 | 필요 (하위 라이브러리 확인 포함) |
| R8 | 앱에 실패 종류(복원 실패 / 재시도 제한 / 프로세스 재시작 필요)를 구분해 보고한다 | 가능 | 필요 |
| R9 | **오류 보존**(최초 오류의 발생 사실과 원인을 식별할 수 있다: 최소한 오류가 난 경로(처리기·메시지 종류)와 오류 코드의 관계를 정의한다. `-1` 기록만으로는 원인 식별이 되지 않는다)과 **실패 전파**(최초 오류가 난 실행의 최종 결과가 성공으로 보고되지 않는다)를 각각 충족한다. 두 조건은 서로 대체할 수 없다: 진단 기록에만 남고 최종 반환값이 0이면 R9 미충족 | 가능 | 필요 |

## 4. 상태 모델 [후보]

```
ACTIVE ──(종료 시작)──▶ CLOSING ──(활성 0 확인)──▶ CLOSED
                           │
                           └──(대기 한도 도달)──▶ QUIESCENCE_FAILED
```

| 동작 | ACTIVE | CLOSING | CLOSED | QUIESCENCE_FAILED |
| --- | --- | --- | --- | --- |
| 신규 작업 등록 | 허용 | 거부 | 거부 | 거부 |
| 기존 작업 실행 | 허용 | 종료·취소 절차에 따라 처리 | 해당 없음 | 계속(생존) |
| 기존 작업 완료 통지 | 허용 | 허용 | 해당 없음 | 허용 |
| 활성 작업 수 감소 | 허용 | 허용 | 해당 없음 | 허용 |
| 신규 세션 시작 | 거부 | 거부 | 허용 | 거부 |
| 객체 해제·훅 제거 | 불가 | 불가 | 가능 | 불가 |

- `active == 0`이 안전하다는 판단은 CLOSING 진입 뒤 등록이 불가능하다는 보장(R1)을 전제로만 성립한다.
- CLOSING 진입 판정과 등록 검사는 같은 잠금 아래에서 한다 [후보].
- 대기 한도는 개별 curl 취소 주기가 아니라 작업 전체의 종료 가능성(P7)을 기준으로 정한다 [후보]. 구체 값은 결정하지 않는다.

### 종료 종류별 처리 [후보]

| 종료 종류 | 처리 |
| --- | --- |
| 정상 종료 | 진행 중 작업의 자연 완료를 기다림(한도 있음) → 완료 확인 → CLOSED |
| 오류 종료 | 취소 신호(`FLAG_QUIT`, curl 취소 플래그) 전달 → 대기 → 완료 확인 → CLOSED, 한도 도달 시 QUIESCENCE_FAILED |
| 취소 실패 | QUIESCENCE_FAILED. 참조 자원·훅 유지, 신규 세션 차단 |

### QUIESCENCE_FAILED의 운영 정책 [후보]

- 자동 복귀 없음. 뒤늦게 작업이 끝나도 서비스 연결·전역 정책·세션 기록의 일관성을 확인하기 전에는 해제하지 않는다.
- 프로세스 재시작은 **자원 정리 방법이 아니라 실패 상태에서 벗어나는 운영 정책**이다. Android 앱의 Activity 재생성·화면 재시작은 네이티브 프로세스 종료가 아니며, 프로세스가 종료되지 않으면 남은 스레드와 전역 정책 상태가 유지된다. 남은 스레드가 있는 동안 객체를 임의 해제하거나 훅을 제거하지 않는다.
- 재시작이 장치 측 복원 상태를 정상화한다는 보장은 없다.
- 앱 보고는 세 가지를 구분한다: 복원 실패 / 재시도 제한(같은 프로세스에서 재시도 불가) / 프로세스 재시작 필요 여부.

## 5. CLOSING에서의 요청 거부

| 구분 | 내용 | 표기 |
| --- | --- | --- |
| 호스트 내부 오류 반환 | 거부 시 `err = -1`을 돌려주는 것이 기본 후보. `thread_new` 실패 경로(5789행)와 같은 형식 | [후보] |
| 루프 종료까지의 전달 | `err < 0` → 다음 반복에서 `FLAG_QUIT`(5736~5739행). 단 P10 때문에 추가 메시지 처리 후 덮어쓰일 수 있고, `FLAG_IGNORE_ERRORS`가 켜지면 오류가 무시된다(우리 세션은 설정하지 않음) | 경로 [확인] / 보존 [위험] |
| 장치에 대한 실패 응답 | 별개의 문제. 장치가 응답을 기다리는지 소스로 확정할 수 없다 | [미확정] |
| 조용히 버림 | 장치가 응답을 기다릴 가능성이 있어 기본 후보에서 제외 | 제외 |

P10의 처리 후보(구현 시 별도 승인):
1. 오류를 `err` 대입과 별개의 영구 필드(예: 첫 오류 보존)에 기록하고, 루프 종료 뒤 그 값을 반환값에 합성한다.
2. `err < 0` 확인 직후 같은 반복에서 루프를 빠져나가 추가 메시지를 처리하지 않는다 (동작 변경이므로 영향 검토 필요).

## 6. 공유 연결 [후보 / 미확정]

- 확인할 것: `restored_send` 한 번이 하위 소켓 쓰기 한 번(또는 원자적 연속)인지, 소켓 송신의 스레드 안전성, 루프의 수신과 비동기의 송신이 같은 연결 객체의 상태를 공유하는지.
- 소켓에 뮤텍스 하나를 두는 것만으로 충분한지는 미확정이다. plist 메시지 단위 직렬화와 송수신 순서(요청-응답 대응)를 함께 본다.
- 동기 처리로 전환하는 후보(비동기 종류를 알리지 않음)는 이 문제를 자동으로 해결하지 못한다.

## 7. 오류·종료 상태의 전달 (`async_err`, `flags`) [후보]

수명 대기(완료 동기화)와 별개 항목이다. 원자 변수나 뮤텍스를 쓰더라도 스레드 종료 대기를 대체하지 못한다.

- 위 두 항목은 P10(최초 오류 보존·실패 전파)과 별개다. `async_err`를 동기화해도 동기 경로의 최초 오류 소실은 해결되지 않는다.
- `async_err`: 쓰기와 읽기 사이에 동기화(잠금 또는 원자) 필요. 읽는 시점이 종료 대기 뒤여야 늦은 쓰기를 놓치지 않는다.
- `flags`: 비동기 스레드와 루프의 `|= FLAG_QUIT`가 읽기-수정-쓰기다. 종료 요청 전용 원자 플래그를 분리하는 후보.

## 8. 객체 수명과 소유권 [후보]

| 객체 | 현재 소유·해제 | 설계 요구 |
| --- | --- | --- |
| `client` | 엔진(`idevicerestore_client_free`) | 활성 작업 0 확인 뒤에만 해제 |
| `client->restore` 및 하위 | `restore_client_free` | 같은 조건. 비동기 작업이 쓰는 필드 전부 포함 |
| `build_identity`, `ipsw`, `filesystem` | 엔진 | 같은 조건 |
| PLIST 서비스 연결, ASR 연결 | 처리기 자신 | 취소 시에도 처리기가 닫는지 확인 |
| 공유 restored 연결 | `restore_client_free` | 비동기 송신이 끝난 뒤에만 해제 |
| 작업 객체(`args`, `message` 복사본) | 처리기 | 생성 실패 시 `args->message`도 해제(현재 누수) |

## 9. 정책 훅과의 관계

- `end()`는 엔진 스레드 수만 보지 않고, 활성 비동기 작업이 0이며 CLOSED일 때만 훅을 제거한다 [후보].
- QUIESCENCE_FAILED에서는 훅을 유지한다. 다음 `begin()`은 거부한다(신규 세션 차단).
- 훅 영구 유지는 정책 보호만 해결하고 객체 수명은 해결하지 못한다.

## 10. 결정이 필요한 항목 (승인 전)

| 번호 | 항목 | 선택지 |
| --- | --- | --- |
| D1 | 완료 대기 방식 | 카운터+조건변수 / 작업 목록+join / 기타. 등록·완료 통지의 원자성을 먼저 명세 |
| D2 | 대기 한도와 취소 전달 | 작업 종류별 한도 / 일괄 한도. T7·T8 관측 전에는 수치를 정하지 않음 |
| D3 | 오류 보존·실패 전파의 의미 (P10) | 첫 오류 보존 / 오류 후 즉시 탈출. 보존만으로는 R9 미충족이며 최종 반환값과 호출자 판정에 연결되어야 함 |
| D4 | 공유 연결 직렬화 위치 | 호스트 래퍼 / 벤더링 소스. plist 프레이밍과 송수신 경계 확인 필요 |
| D5 | 비동기 종류를 동기로 전환할지 | 대안으로만 유지, 기본안에서 제외(프로토콜 호환성·루프 블로킹 미검증) |
| D6 | 앱 보고 형식 | 상태 코드와 UI 전달 경계 정의 |
| D7 | 객체 소유권 | 세 가지를 구분해 결정: (a) 소유권 — 누가 생성하고 최종 해제하는가, (b) 사용 권한 — 어느 스레드가 언제까지 참조할 수 있는가, (c) 종료 책임 — 취소 실패 시 누가 객체를 유지하고 정리를 보류하는가. 처리기가 PLIST·ASR 연결을 소유해도 세션 종료 절차는 해당 작업의 종료를 확인해야 하고, 세션이 소유권을 넘겨받아도 살아 있는 처리기가 쓰는 동안 해제하면 해결되지 않는다 |

**권고 결정 순서** (설계 의존성 기준, 구현 순서 확정 아님): D3 → (D7 + D1) → D4 → D2 → D6, D5는 대안으로 유지.
D3을 먼저 정해도 독립 구현이 가능하다는 뜻은 아니다. 비동기 오류를 첫 오류로 보존하려면 그 기록이 언제까지 가능한지 알아야 하며, 이는 D1의 완료 확인과 기록 객체의 수명에 연결된다.

## 10a. D3 선택지 비교 (결정 아님, 근거 정리)

D3의 목적은 R9의 두 수준을 모두 충족하는 것이다: **실패 상태 보존**(최초 오류 이후 최종 결과가 성공으로 바뀌지 않음)과 **오류 원인 보존**(처리기·메시지 종류·오류 코드를 식별할 수 있음).

**결정할 네 가지**
1. 최초 오류를 어디에서 포착하는가 (각 처리기 반환 지점 / 루프의 `err` 대입 직후 / 비동기 스레드의 기록 지점)
2. 후속 오류가 최초 오류를 덮어쓰지 못하게 하는가 (첫 오류 우선 / 마지막 오류 우선 / 둘 다 보존)
3. 발생 사실을 최종 반환값과 앱 보고에 어떻게 반영하는가 (R9 실패 전파)
4. 비동기 오류 기록의 수명을 D7·D1과 어떻게 연결하는가

**제약**: 첫 오류를 보존하는 변수가 있어도, 비동기 작업이 종료되기 전에는 최종 결과를 확정할 수 없다. 완료 확인 이전에 성공을 보고하면 늦게 발생한 비동기 오류가 누락된다.

| 선택지 | 내용 | 실패 상태 보존 | 오류 원인 보존 | 동작 변경 | 한계·미확정 |
| --- | --- | --- | --- | --- | --- |
| A. 첫 오류 보존 | 루프 지역 또는 `client` 필드에 첫 음수 오류(처리기·메시지 종류·코드)를 기록하고 반환 직전에 `err`가 0이면 그 값으로 대체 | 충족 (반환값 합성) | 충족 (기록 구조에 따라) | 없음(추가 메시지는 계속 처리됨) | 추가 메시지 처리 중 부작용(장치로 전송 등)은 그대로 남음. 비동기 기록은 완료 확인 뒤에만 확정 가능 → D1 의존 |
| B. 오류 직후 탈출 | `err < 0`을 보면 같은 반복에서 추가 메시지를 받지 않고 루프를 빠져나감 | 충족 (덮어쓸 처리기가 없음) | 부분 (원인 기록은 별도 필요) | **있음**: 현재는 한 건을 더 처리함. 장치가 실패 후 보내는 마무리 메시지(예: 상태 메시지)에 의존하는지 미확정 | 장치 프로토콜 영향 미검증. `FLAG_IGNORE_ERRORS`의 의미와 충돌 가능 |
| C. A+B | 위 둘 모두 | 충족 | 충족 | B와 같음 | 변경 범위가 가장 큼 |

- A는 추가 메시지 처리를 유지하므로 프로토콜 영향이 작지만 부작용 문제가 남는다. B는 부작용을 막지만 프로토콜 호환성이 미검증이다. 둘 다 `async_err`·`flags` 동기화(별개 항목)와 독립이다.
- 비동기 오류는 두 방식 모두 완료 확인 뒤에 합쳐야 한다. 합치는 시점과 기록 객체의 수명은 D7·D1과 함께 정한다.
- 가짜 장치 시험 T2로 현재 코드의 기준선(덮어쓰기와 성공 보고 여부)을 먼저 기록한 뒤 선택한다.

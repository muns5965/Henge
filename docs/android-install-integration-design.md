# Android 설치 실행기 통합 설계 (초안)

이 문서는 실제 IPSW 복원·설치 기능을 Android 앱에서 활성화하기 전에 필요한 세 가지 설계(앱–네이티브 실행기 계약, 네트워크 승인·격리 계약, 저장장치·설치 상태 계약)를 정리한 초안이다. `docs/android-port-notes.md` §9.5에서 확인된 선결 과제를 바탕으로 작성했다.

**범위:** 설계와 기존 소스 조사만 다룬다. 이 문서 작성을 위해 어떤 코드도 변경하지 않았고, 실제 네트워크 요청·저장장치 생성·초기화·새로운 VM 실행도 수행하지 않았다. `host/ui_runner_vm.c`의 읽기 전용(HV_* 환경변수 제거) 안전장치는 전제로 유지한다.

**표기:** 각 항목을 **확인된 사실**(소스로 확인됨), **설계 선택**(이 문서의 제안, 아직 구현되지 않음), **미해결**(추가 조사나 결정이 필요함)으로 구분한다.

---

## 1. 앱–네이티브 실행기 계약 (프로세스 생명주기)

### 1.1 현재 구조 — 확인된 사실

Android 앱(`MainActivity.java`)은 각 기능을 별도 네이티브 실행파일로 `ProcessBuilder`를 통해 구동한다(`vmrun`, `libipswdl.so`, `libromextract.so` 등). `host/restore_session.c`의 소유권·정리·quiescence 추적은 복원을 실제로 실행하는 **그 네이티브 프로세스 내부**에 한정되며, 프로세스 경계를 넘어 앱에 상태를 전달하는 기존 규약은 없다.

`host/restore_registry.h`에는 이미 성숙한 결과 분류 체계가 정의돼 있다(재사용 대상):
```
HvRegReport: HV_REG_R_SUCCESS, HV_REG_R_RESTORE_FAILED, HV_REG_R_ABORTED_BY_USER,
             HV_REG_R_CLEANUP_DELAYED, HV_REG_R_CLEANUP_FAILED, HV_REG_R_SESSION_NOT_QUIESCENT
HvRegQfReason: HV_REG_QF_TASKS_NOT_QUIESCENT, HV_REG_QF_ENGINE_NOT_EXITED,
               HV_REG_QF_CONN_REF_NOT_RETURNED, HV_REG_QF_CONN_TABLE
```
이 값들은 이미 네이티브 프로세스 내부의 결과를 정확히 분류한다. 설계 과제는 새 분류 체계를 만드는 것이 아니라, **이 값을 프로세스 경계 밖(앱)으로 어떻게 전달하는가**이다.

### 1.2 상태 전달 수단 — 설계 선택

프로세스 종료 코드만으로는 `HvRegReport`의 세부 구분(예: 성공이지만 정리 지연)을 전달할 수 없다. 설치 실행기가 종료 전에 **상태 파일**(예: `install_state.json`, 작업 디렉토리 안)에 다음을 기록하는 방식을 제안한다:
- 마지막으로 도달한 `HvRegReport` 값(또는 아직 결정되지 않았다면 `HV_REG_R_NONE`)
- `install_step`/`install_progress`(`host/install.c`의 `on_install_progress` 콜백이 이미 추적하는 값과 동일한 스키마)
- 기록 시각, ECID, 대상 디스크 경로

앱은 프로세스 종료 코드와 검증된 상태 파일을 함께 읽되, 둘 중 하나만으로 설치 성공을 확정하지 않는다. 상태 파일이 없는 경우 설치 이력에 따라 '미설치'와 '상태 불명'을 구별하며, 진행 상태로 멈춘 파일은 해당 시도의 실행기 생존 여부를 확인한 뒤 '불완전 설치' 후보로 분류한다. 구체적인 판정 규칙은 §5를 따른다.

### 1.3 정상 취소 vs 강제 종료 — 설계 선택 (리뷰어 지적 반영)

- **정상 취소**: 사용자가 앱에서 취소를 누르면, 앱이 네이티브 프로세스에 신호(예: 작업 디렉토리의 취소 플래그 파일 생성, 또는 플랫폼이 허용하면 프로세스 신호)를 보낸다. 네이티브 측은 이를 감지해 `hv_install_cancel()`(이미 구현됨 — `host/install.c`, 내부적으로 `hv_restore_session_cancel()`과 `global_quit_flag`를 사용)을 호출한다. 이 호출은 **취소 요청**일 뿐이다. 실제 최종 결과는 복원 작업과 취소 요청의 경합, 엔진 종료 및 정리 결과에 따라 달라질 수 있으므로, `restore_session`이 확정한 결과만 최종 `HvRegReport`로 기록한다.
- **강제 종료**(앱 스와이프 종료, OOM kill, 기기 재부팅 등): 네이티브 프로세스의 정리 콜백 실행이 보장되지 않는다. 상태 파일은 "진행 중"에서 멈춘 채로 남는다. 이 구분을 앱이 직접 감지할 수는 없으므로(죽은 이유를 알 수 없음), **재시작 시 상태 파일의 마지막 상태로부터 추론**하는 §1.4의 복구 절차에 위임한다.

### 1.4 앱 재시작 후 상태 복구 — 설계 선택

앱 시작 시 상태 파일을 읽는다.
- 상태 파일이 없고 해당 VM에 설치 시도 이력이 없으면 **미설치**, 설치 이력이 있는데 상태 파일이 없으면 **상태 불명**으로 취급한다.
- 상태 파일의 `HV_REG_R_SUCCESS`는 단독으로 성공을 확정하지 않는다. 동일한 설치 시도의 종료·정리·저장장치 일관성을 확인한 경우에만 **설치 완료 후보**로 분류한다.
- '진행 중'에서 상태 갱신이 멈춘 경우 시도 식별자·프로세스/잠금 상태를 검증한다. 실행기 종료가 확인되면 **불완전 설치**, 생존 여부가 불확실하면 **상태 불명**으로 분류한다. PID만으로 생존을 확정하지 않는다.
- 복구 과정에서 디스크를 자동 삭제·초기화하지 않는다. 사용자의 명시적인 선택 및 기존 `disk_policy` 검증을 거친다.

### 1.5 미해결

- 작업 디렉토리/상태 파일의 정확한 스키마, 파일 잠금 방식(동시 실행 방지는 `host/install.c`의 Android 분기에 이미 `started`/`g_mux_alive` 정적 변수로 일부 구현돼 있으나, 이는 같은 프로세스 내부 중복 실행 방지이지 앱 재시작 간 상태 복구는 아님).
- 신호 전달 수단(파일 기반 폴링 vs 플랫폼 네이티브 방식)은 Android 프로세스 생명주기 제약(백그라운드 프로세스 강제 종료 정책)을 추가 조사해야 확정할 수 있다.

## 2. 네트워크 승인·격리 계약

### 2.1 현재 구조 — 확인된 사실

`host/net_guard.h`/`.c`: 기본 거부, 세 개의 후킹 지점(libimobiledevice-glue, curl 대체, URLAsset). `hv_net_guard_allow_host(name, port)`는 **`void`**이고 등록 목록은 `#define MAXL 8`로 고정, 가득 차면 `if (g_nhost < MAXL)` 체크로 **조용히 무시**된다(`net_guard.c:205-208`). `hv_restore_session_begin()`이 매 세션 시작 시 `hv_net_guard_reset()`을 호출해 목록을 비운다(`restore_session.c:83`) — "세션 종료 시 초기화"가 아니라 "다음 세션 시작 시 초기화"이지만 결과적으로 이전 세션의 등록이 새 세션에 남지 않는다는 목적은 이미 충족된다.

### 2.2 등록 시점과 대상 — 설계 선택 / 미해결

제안: `hv_restore_session_begin()` 성공 직후, `hv_restore_session_allow_usbmuxd()`와 **같은 자리에서** 복원에 필요한 모든 공개 호스트를 한 번에 등록한다(등록은 세션당 1회, 복원 도중 동적으로 추가하지 않음 — 공격 표면을 줄인다).

**미해결**: 실제로 어떤 호스트(TSS 서명 서버, URLAsset/캐시 서버 등)가 필요한지는 `third_party/idevicerestore`/`third_party/libtatsu` 소스를 별도로 조사해야 확정된다. 이번 설계 작업에서는 이 조사를 수행하지 않았다 — 고정 호스트 이름만으로 해결된다고 가정해서는 안 된다는 지적(검토 의견)을 그대로 반영한다. 목록이 `MAXL=8`로 고정돼 있으므로, 조사 결과 필요한 호스트 수가 이를 넘는지도 함께 확인해야 한다.

### 2.3 등록 실패 감지 — 설계 선택

`hv_net_guard_allow_host()`가 성공 여부를 반환하지 않으므로, 호출자가 등록 실패(목록 가득 참)를 알 방법이 없다. 코드 변경 없이 설계만 제시한다:
- 등록 전후로 `hv_net_guard_stats()`(이미 존재, `HvNetStats`) 또는 별도의 "현재 등록된 host 수를 읽는" 조회 함수가 필요하다 — 현재는 그런 조회 함수도 없다.
- 설치 실행기는 **필요한 모든 호스트 등록이 성공했는지 확인한 뒤에만** 복원 엔진을 시작해야 한다. 하나라도 등록되지 않았다면 복원을 시작하지 않고 실패로 보고한다(기본 거부 원칙 유지).
- 이 "등록 확인" 자체가 `net_guard.c`의 함수 시그니처 변경(반환형 추가 또는 조회 함수 신설)을 필요로 하므로, 실제 구현은 이번 설계 승인과는 별도의 코드 변경 승인 대상이다.

### 2.4 중복 호스트, HTTPS 검증 — 설계 선택

- 동일 `(name, port)`를 중복 등록하면 `MAXL=8`의 슬롯을 낭비한다. 등록 전 중복 검사가 필요하다(현재 `hv_net_guard_allow_host()`에는 없음).
- HTTPS 전용 검증은 `hv_net_guard_check_url()`(URLAsset 경로)에 이미 존재한다고 헤더에 명시돼 있다("https only, no user info, host name on the allow list for that port") — 이 부분은 재사용 가능하며 추가 설계가 필요 없어 보인다.

### 2.5 세션 종료 시 권한 회수 — 확인된 사실 (대부분 기존 메커니즘으로 충족)

`hv_restore_session_end()`/`finalize()`의 정상 정리 경로는 `hv_net_guard_uninstall()`을 통해 후킹을 해제하고, 다음 세션의 `begin()`에서는 `hv_net_guard_reset()`으로 허용 목록을 비운다. **종료 시 후킹 해제**와 **다음 시작 시 목록 초기화**는 서로 다른 동작이다. 종료 직후 목록 메모리 자체가 모두 비워진다고 단정하지 않는다. 정리 실패로 후킹 제거에 실패하면 정책이 유지되며 새 세션 시작도 제한되는 기존 안전 동작을 보존해야 한다.

## 3. 저장장치·설치 상태 계약

### 3.1 생성과 초기화 구분 — 확인된 사실

`host/disk_policy.h`/`.c`에 이미 명확히 구분돼 있다:
- `hv_install_disk_create()`: 파일이 **존재하지 않을 때만**(`O_EXCL`) 생성, 기존 파일은 절대 건드리지 않음.
- `hv_install_disk_reset()`: 정확한 확인 문자열(`HV_INSTALL_DISK_RESET_CONFIRM = "ERASE macos_disk.img"`)이 일치할 때만 삭제, 생성은 하지 않음.
- 디렉터리 소유권·권한 검사(`dir_trusted()`), `openat`/`fstatat` 기반 TOCTOU 방어가 이미 구현돼 있다.

이 모듈은 재사용 대상이며 추가 설계가 거의 필요 없다. 현재 **아무 코드도 이 두 함수를 호출하지 않는다**는 점만 남은 공백이다(`disk_policy.h` 자체 주석, `check-no-test-flags.sh`가 CI에서 검증).

### 3.2 디스크 크기 정책 — 확인된 사실 + 권고안 (설계 선택)

iOS는 신규 설치 시 64GiB(`ios/Henge/Installer.swift`: `64 << 30`), Android `host/disk_policy.h`는 `HV_INSTALL_DISK_BYTES = 128ULL << 30`(128GiB) — 확인된 불일치다.

양쪽 모두 **스파스 파일**이므로 선언 크기 자체가 즉시 소모되는 저장공간은 아니다(게스트가 실제로 쓴 블록만 할당됨). 다만 다음 이유로 무조건 둘 중 하나에 맞추기보다 추가 조사가 필요하다는 리뷰어 지적을 받아들인다:
- 실제 macOS 설치가 필요로 하는 최소 공간(파일시스템 오버헤드 포함)을 조사하지 않았다 — **미해결**.
- 모바일 기기(Galaxy S26 Ultra 등)의 가용 저장공간은 데스크톱보다 제약이 클 수 있어, 선언 크기가 클수록 `statvfs()` 여유공간 검사(`hv_install_disk_check()`의 `dir_free`)에서 부정확한 "공간 부족" 오판을 유발할 여지가 있는지도 확인이 필요하다 — **미해결**.

**권고안(설계 선택, 결정 아님)**: 현재로서는 iOS와 동일한 64GiB로 통일하는 쪽이 더 보수적인 기본값으로 보이지만, 이는 실제 macOS 버전별 설치 용량 요구치를 조사한 뒤 확정해야 한다. 이번 설계에서는 "어느 쪽이 맞다"고 결정하지 않고, **두 정책이 다르다는 사실과 결정에 필요한 조사 항목만** 기록한다.

### 3.3 설치 상태 전이 — 설계 선택

기존 `HvRegReport`(§1.1)를 그대로 재사용해 아래와 같이 매핑한다(새 열거형을 만들지 않음):

| 앱이 보는 상태 | 조건 | 대응하는 기존 값 |
|---|---|---|
| 미설치 | `hv_install_disk_check()` → `HV_DISK_MISSING` | — |
| 설치 준비 | 디스크 생성 완료(`hv_install_disk_create()` 성공), ECID 발급됨, 엔진 미시작 | — |
| 설치 진행 | 상태 파일에 `install_step`/`install_progress` 갱신 중, 프로세스 생존 확인됨 | `HV_REG_R_NONE` |
| 설치 완료 후보 | 동일 설치 시도의 복원 성공, 세션 정리 완료, 상태 파일·디스크 일관성 확인 | `HV_REG_R_SUCCESS`(최종 결과) |
| 설치 실패 | `HV_REG_R_RESTORE_FAILED` / `HV_REG_R_CLEANUP_FAILED` / `HV_REG_R_SESSION_NOT_QUIESCENT` | 해당 값 |
| 사용자 취소 | `HV_REG_R_ABORTED_BY_USER` | 해당 값 |
| **불완전 설치**(신규 구분 필요) | "설치 진행"에서 멈춘 채 프로세스가 죽어 있음(§1.4) | 기존 값으로 표현 불가 — 앱이 재시작 시점에 추론 |

리뷰어 지적대로, **설치 완료 마커는 macOS의 실제 정상 부팅 가능성을 보증하지 않는다.** 따라서 "설치 완료"(복원 엔진 성공)와 "설치 후 첫 부팅 확인"(§9.4의 실제 정상 부팅 시험)은 별도 상태로 관리해야 하며, 후자를 이 설계에 포함하지 않는다 — 이는 실제 VM 실행을 전제하므로 별도 승인 대상이다.

### 3.4 불완전 설치 처리 — 설계 선택

자동 삭제는 하지 않는다. 사용자에게 "이전 설치가 완료되지 않았습니다 — 다시 시도 / 디스크 초기화" 중 선택을 제시한다. "디스크 초기화"를 선택하면 `hv_install_disk_reset()`의 정확한 확인 문자열을 거쳐야 한다(기존 보호 메커니즘 그대로 재사용).

### 3.5 설치 후 일반 부팅 전환 — 확인된 사실

**VM 엔진의 부팅 모드 분기 자체에는 별도의 '설치 완료 → 일반 부팅' 전환 로직이 필요하지 않다.** `--installer`를 생략하면 `installer=0` 일반 부팅 경로가 선택된다(`devices/vmapple.c`/`host/vm.c`). 다만 설치 당시 ROOT/AUX와 ECID·seed·RAM·CPU 등 VM 설정의 연결 및 보존은 앱/실행기 통합 계약의 책임이다. 이 조건을 충족하더라도 실제 macOS의 첫 부팅 성공은 별도 검증 대상이다.

## 4. 요약 — 확인된 사실 / 설계 선택 / 미해결

**확인된 사실 (재사용 가능, 신규 구현 불필요):**
- `HvRegReport`/`HvRegQfReason` 결과 분류 체계 (restore_registry.h)
- `hv_install_cancel()`에 의한 정상 취소 경로 (install.c)
- `hv_net_guard_reset()`이 매 세션 시작 시 호출되어 사실상 "세션 간 격리"를 충족 (restore_session.c)
- `disk_policy.c`의 생성/초기화 분리, TOCTOU 방어, 확인 문자열 보호
- VM 엔진 레벨에서 `--installer` 생략 시 일반 부팅 모드가 선택됨(설치 파일·식별정보 일치나 정상 부팅 성공을 보증하지 않음)

**설계 선택 (이 문서가 제안, 아직 구현 안 됨 — 별도 코드 변경 승인 필요):**
- 상태 파일(`install_state.json`)을 통한 프로세스 경계 간 상태 전달
- 앱 재시작 시 상태 파일 기반 "불완전 설치" 추론
- 네트워크 호스트 등록을 세션 시작 시 일괄 수행, 등록 확인 후에만 엔진 시작
- `HvRegReport`를 그대로 재사용한 설치 상태 전이표 + "불완전 설치" 신규 구분

**미해결 (추가 조사·결정 필요):**
- 복원에 실제로 필요한 호스트 목록(idevicerestore/libtatsu 소스 조사)과 `MAXL=8`로 충분한지
- `hv_net_guard_allow_host()`에 성공 여부를 알리는 수단 — 함수 시그니처 변경이 필요한지, 별도 조회 함수가 필요한지
- 64GiB(iOS) vs 128GiB(Android) 중 어느 쪽을 기준으로 할지(macOS 버전별 실제 요구 용량 조사 필요)
- Android 프로세스 생명주기 제약을 고려한 정상 취소 신호 전달 수단의 구체적 구현 방식
- 설치 완료와 설치 후 첫 정상 부팅 확인을 분리된 상태로 관리하는 구체적 UI/저장 방식

이 문서에 기록된 모든 항목은 설계 제안이며, 실행 코드 변경·네트워크 접근·저장장치 생성/초기화·VM 실행은 수행하지 않았다.

## 5. 구현 전 계약 보완 — 설계 선택 / 미해결

### 5.1 엔진 결과와 앱의 영속 상태를 분리 — 확인된 사실 / 설계 선택

- **확인된 사실:** `host/restore_registry.h`의 `HvRegReport`는 한 복원 세션의 결과 분류이다. `host/install.c`는 엔진 반환값 `r`, `hv_restore_session_finalize()`의 결과 `rep`, 실행기 내부의 `g_result`를 구별한다. 현재 `g_result`에는 `r == 0`에 기반한 완료값을 기록하므로 앱이 `g_result`만 보고 정리 완료까지 확정해서는 안 된다.
- **설계 선택:** 앱 설치 단계는 `미설치 / 준비 / 진행 / 취소 요청 / 설치 완료 후보 / 실패 / 불완전 설치 / 상태 불명`으로 표현하되, 네이티브 보고 값에는 기존 `HvRegReport`와 `HvRegQfReason`을 재사용한다. 앱 상태는 기존 네이티브 열거형을 대체하지 않는다. `HV_REG_R_CLEANUP_DELAYED`는 최종 성공으로 간주하지 않는다.
- **판정 규칙:** `HV_REG_R_SUCCESS`는 동일한 실행 세대에서 확인된 복원 성공·정리 완료 결과일 때에만 설치 완료의 필요조건이 된다. 상태 파일의 성공 표식, 엔진 단독 반환값, 프로세스 종료코드 중 어느 하나만으로 완료를 확정하지 않는다. 설치 후 첫 부팅 성공은 별도의 관측 항목이다.

### 5.2 상태 파일 계약 — 설계 선택

- 파일은 앱 전용의 신뢰 가능한 VM별 디렉터리에서 관리한다. 제안 필드: `schema_version`, `vm_id`, `attempt_id`, `sequence`, `phase`, `restore_report`, `qf_reason`, `cleanup_status`, `progress_step`, `progress_fraction`, `updated_at`, `disk_identity`, `exit_status`(알 수 없다면 null). 실제 필드 이름과 형식은 구현 전 확정한다.
- 상태 기록은 같은 디렉터리의 임시 파일에 완전 작성 → `fsync` → 원자적 `rename` → 가능한 경우 부모 디렉터리 `fsync` 순서로 설계한다. 읽는 쪽은 스키마·작업 ID·순번·범위를 검증한다. 쓰기 실패는 성공으로 처리하지 않는다.
- 디스크 경로 문자열만으로 설치 대상을 판정하지 않는다. VM/설치 시도 식별자, 설치 대상의 파일 식별 및 유효한 앱 메타데이터를 결합한다. ECID를 상태 파일에 원문으로 중복 기록할 필요가 있는지는 미해결로 두고, 기록 시에는 권한 제한 및 로그 비노출을 전제로 한다.
- 동시 실행 배제는 네이티브 프로세스 내부의 `started` 변수가 아니라 앱–실행기 공통의 VM별 잠금/시도 계약으로 관리한다. PID는 보조 정보로만 사용하고 PID 재사용에 대비한 실행 시도 식별자를 사용한다.

### 5.3 취소·프로세스 사망·재시작 판정 — 설계 선택

- 앱의 사용자 취소는 `취소 요청`을 기록하고, 실행기가 이를 수신하면 기존 `hv_install_cancel()`을 호출한다. 요청 전달 성공과 엔진 최종 `HV_REG_R_ABORTED_BY_USER` 판정은 서로 다르다. 취소보다 복원 완료가 먼저 확정될 수 있다.
- 앱 종료·OS에 의한 실행기 종료·기기 재부팅은 네이티브 정리 콜백의 실행을 보장하지 않는다. 살아 있는 실행기와 단지 상태 파일 갱신이 지연된 실행기를 혼동해서는 안 된다.
- 앱 시작 시 **설치 이력 없음+상태 파일 없음 → 미설치**, **이력 있음+파일 없음/손상 → 상태 불명**, **진행 중+실행기 종료 확인 → 불완전 설치**, **최종 실패/취소 결과 확인 → 해당 결과**로 분류한다. 불확실할 때 자동 삭제·재복원을 금지한다.
- **미해결:** Android의 프로세스 수명에 맞는 취소 신호 수단, 락 소유권 회수, 강제 종료 후 식별·복구 방식, 영속 파일 접근 권한을 실제 테스트로 검증해야 한다.

### 5.4 네트워크 허용 목록과 세션 종료 — 설계 선택 / 확인된 사실

- `host/net_guard.c`의 `hv_net_guard_allow_host()`는 `void`, 공개 호스트 목록 상한은 8개이며 중복도 소비할 수 있다. **제안:** 등록 결과를 명시적으로 알려주는 API와 중복 제거, 용량 초과 시 fail-closed 동작을 추가한다. 현재 `hv_net_guard_stats()`는 허용 호스트 수를 확인하는 API로 확정되지 않았으므로 그것만으로 등록 성공을 증명한다고 가정하지 않는다.
- 호스트별 목적(TSS/URLAsset 등), 포트, 승인 주체, 등록 시점을 실제 `idevicerestore`/`libtatsu`의 호출 경로를 확인한 뒤 결정한다. 사전 일괄 등록안은 제안이며 모든 요청 대상을 미리 알 수 있는지는 미확인이다. HTTPS 확인만으로 모든 라이브러리 경로의 접근 정책이 증명되지는 않는다.
- **확인된 사실:** `hv_restore_session_begin()`에서 `hv_net_guard_reset()`이 호출되고, 정상 종료 경로에서 `hv_net_guard_uninstall()`을 호출한다. 다음 세션 시작 시 목록 초기화와 종료 직후 목록 제거는 다르다. 정리 실패 시 보호 정책을 무리하게 해제하지 않는다.

### 5.5 디스크·VM 정체성과 첫 부팅 — 설계 선택 / 미해결

- `hv_install_disk_create()`와 `hv_install_disk_reset()`의 별도 승인·기존 파일 보호 규칙을 유지한다. `--make-blank --recreate-blank`를 설치 완료 디스크의 초기화 수단으로 재사용하지 않는다.
- 64GiB(iOS)와 128GiB(Android)는 정책상 차이로 기록한다. 실제 대상 macOS의 요구 공간, 기기 여유 공간 및 스파스 파일의 물리 할당량을 조사하기 전에는 어느 값도 확정하지 않는다.
- 정상 부팅을 위한 **모드 선택**은 `installer=0`으로 충분하다는 코드상 사실을 유지한다. 다만 ROOT/AUX 및 설치 당시 VM 식별·설정값을 일치시켜야 하며, 엔진 성공과 첫 부팅 성공을 분리 기록한다.

### 5.6 다음 검증 관문 — 미해결

1. 프로세스 경계 상태 계약에 대한 오프라인 모의 실행: 상태 파일 손상·누락, 시도 ID 불일치, 취소/성공 경합, PID 재사용, 강제 종료를 주입해 실패 시 보수적으로 분류하는지 확인한다.
2. 허용 목록 단위 시험: 중복 호스트, 8개 초과, 등록 실패, 취소·정리 실패 중 권한 유지, 다음 세션 초기화, HTTPS 외 경로를 검증한다. 실제 외부 네트워크 연결은 제외한다.
3. VM별 디스크·식별정보의 일관성 시험: 다른 VM의 상태 파일·ROOT/AUX를 혼합했을 때 실행을 거부하도록 설계한다. 기존 읽기 전용 `ui_runner_vm`의 제약은 변경하지 않는다.
4. 위 시험 기준이 확정되고 별도 코드 변경 승인을 받은 후에만 Android 설치 진입점 구현을 검토한다. 실제 IPSW 복원·서버 접근·저장장치 변경·실기기 VM 실행은 별도 단계로 유지한다.

**이번 문서 보완의 범위:** 설계 및 기존 소스와의 대조에 한정하며 실행 코드를 변경하거나 실제 복원·네트워크 요청·디스크 생성·VM 실행을 수행하지 않는다.

# 시험 전용 후크 설계안 (S4) — 설계만, 구현 없음 (2026-11-11)

범위: `docs/fake-device-impl-scope.md` §5·§6의 S4. 가짜 장치만으로 재현하기 어려운 항목(T1a·T3, 그리고 T5·T1b의 점검)에 필요한 **시험 전용 후크의 설계안**이다.
후크는 구현하지 않았다. 제품 코드, 벤더링 소스, 확정 설계(D1~D8, C1~C19), 검사 스크립트(`tools/check-no-test-flags.sh`)는 변경하지 않았다. 설계 확정·구현 승인·실기 검증이 아니다.
표기: [관측]=이번에 실행/소스로 확인, [추론], [설계]=제안, [미검증].

## 1. 먼저 확인한 사실 (범위 문서의 표를 수정하는 근거)

| 항목 | 범위 문서(§5)의 분류 | 이번 확인 | 분류 |
|---|---|---|---|
| T5 비동기 부분 | (A)/(B)/(C) 미정 | [관측] S2에서 (A) 성립: 빈 build_identity와 가짜 장치만으로 URLAsset 비동기 스레드가 DataPort 접속에서 대기하고, `restore_device` 종료·`client` 해제 뒤 `client->async_err`를 쓴다(ASan·TSan heap-use-after-free, `restore.c:5161`). 후크 불필요 | 가짜 장치만으로 가능 |

따라서 후크가 실제로 필요한 것은 T1a(그리고 같은 종류인 T14·T15의 순서 제어)로 줄어든다. 이 판단은 설계 제안이며 확정이 아니다.

## 2. 후크 종류와 기본 원칙 [설계]

원칙: 벤더링 소스를 고치지 않고 얻을 수 있는 수단을 먼저 쓰고, 그래도 안 되는 것만 호스트 소유 코드의 후크로 한다.

| 수단 | 설명 | 벤더링 변경 | 제품 빌드 영향 |
|---|---|---|---|
| W 링크 대체 | 시험 실행 파일 링크 때 `-Wl,--wrap=<함수>`로 `thread_new` 등 외부 함수 호출을 시험용 함수로 돌린다. 시험 파일에서만 정의 | 없음 | 없음(시험 실행 파일에만 적용) |
| H 호스트 후크 | I1 레지스트리(호스트 소유 새 코드)의 상태 전환 지점에 `HV_TEST_HOOK(id)`를 둔다. `HV_TEST_HOOKS` 정의 빌드에서만 컴파일되고, 그 밖에서는 빈 매크로 | 없음(호스트 코드) | 정의되지 않으면 코드가 남지 않음. 검사 스크립트 확장 필요(별도 승인) |
| V 벤더링 후크 | 벤더링 소스(`restore.c`) 안에 후크 | 있음 | 있음 |

설계상 V는 사용하지 않는다. V가 필요해지면 그 부분만 보류하고 별도 승인을 요청한다.

### 2.1 W의 가능성 [관측]
스크래치패드 실험(저장소에 넣지 않음): 시험 실행 파일을 `-Wl,--wrap=thread_new`로 링크하고 대체 함수를 둔 결과, 정적 라이브러리 안의 `restore.c`가 호출한 `thread_new`가 대체 함수에 도달했다.
- 통과 모드: 호출 1회 관측, 원래 함수로 전달, `restore_device`는 이전과 같은 값(-1)과 시간(1.6초).
- 실패 주입 모드: 대체 함수가 -1을 돌려주자 `restore.c`의 `Failed to start async data request handler thread!` 분기가 실행됨.
한계: Linux x86_64, gcc/ld 한 환경. 같은 번역 단위 안의 호출(정적 함수끼리)은 대체되지 않는다. Android/iOS 링크 환경은 [미검증].

## 3. T1a 등록 검사와 CLOSING 전환의 경합 [설계]

전제: 등록(원자적으로 "허용 판정 + 활성 수 증가")은 I1 레지스트리에만 존재한다. 현재 코드에는 없으므로 I1 구현 전에는 시험할 수 없다.

필요한 순서 제어는 두 곳이다.
- P1 (등록 승인 직후, 스레드 생성 전): 활성 수가 이미 증가한 상태에서 다른 스레드가 CLOSING으로 전환하는 순서. W로 `thread_new` 호출 직전에 멈추면 만들 수 있다(벤더링 변경 없음).
- P2 (허용 판정과 활성 수 증가 사이): 이 사이에 틈이 없어야 한다는 것이 시험 대상이다. 이 틈은 레지스트리 내부에 있으므로 `thread_new`를 멈추는 W로는 만들 수 없다(시험 명세 T1a가 "스레드 생성 직전 지연은 불충분"이라고 한 부분). 호스트 후크 H로 레지스트리의 `try_register()` 안(판정 직후)에서 멈춘다.

제안 후크 목록(H, I1 구현 때 호스트 코드에 존재해야 함):

| id | 위치 | 용도 |
|---|---|---|
| HV_HOOK_REG_AFTER_CHECK | `try_register()`에서 상태 확인 직후, 활성 수 증가 직전(락 보유 여부는 구현 설계에 따름) | T1a: 틈이 있으면 종료 스레드가 활성 수 0으로 판단하는 순서 |
| HV_HOOK_REG_AFTER_INC | 활성 수 증가 직후 | T1a: 승인된 작업이 CLOSING 이후에도 끝낼 수 있는지 |
| HV_HOOK_CLOSE_BEFORE_ZERO_CHECK | CLOSED 판정 직전 | T14·T15와 공용 |

후크의 동작(시험이 설정): 지정 id에서 래치를 기다림(일시 정지)하거나 반환값을 바꿈. 이 id들은 I1 설계에 이름이 고정되는 것이 아니라, 구현 설계 때 확정한다. 위 위치가 락 안에 있으면 래치 대기는 락을 쥔 채 멈추는 것이므로 시험이 교착으로 오인되지 않도록 래치 대기에 시간 제한을 둔다.

판정 방식(시험 명세 T1a 그대로): CLOSING 이후 승인 / 거부 사실 미전달 / 승인과 증가 사이의 틈 / 활성 수 어긋남 중 하나라도 있으면 실패. 시험은 원자성을 입증하지 못한다(시험한 순서에서만).

## 4. T3 생성 실패 시 등록 취소 [설계]

- 현재 코드 [관측: 소스]: `restore.c`의 AsyncDataRequestMsg 분기는 `thread_new` 실패 때 `free(args)`만 하고 `args->message`(`plist_copy`한 사본)를 해제하지 않는다. 등록 취소는 존재하지 않는다(등록 자체가 없음). 누수 여부의 실행 확인은 [미검증].
- 주입: W로 `thread_new`가 -1을 돌려주게 한다(§2.1에서 도달 확인). 벤더링 변경 없음.
- 관측(I3 이후): 활성 수가 0으로 복귀하는가, 오류가 엔진에 전달되는가, `args->message`가 해제되는가(ASan LeakSanitizer; 시험 프로세스를 `_exit` 대신 정상 종료해야 누수 검사가 동작함).
- 그 전(변경 전 기준선): 위 주입으로 `restore_device` 반환값과 누수를 기록할 수 있다. 별도 승인 후 시험 코드로 추가 가능(이번에는 구현하지 않음).

## 5. T5 비동기 (재확인) [설계]

가짜 장치만으로 재현되므로 후크는 불필요하다. 다만 "대기 한도 도달 뒤 객체 해제 금지"(I1~I7 이후 판정)는 레지스트리와 호스트 세션 종료 경로가 있어야 판정 가능하며, 지금의 기준선은 "해제 후 접근이 실제로 일어난다"는 사실만 기록한다(S2 문서).

## 6. 검사 스크립트와 승인이 필요한 항목

| 항목 | 이유 | 승인 필요 |
|---|---|---|
| `tools/check-no-test-flags.sh`에 `HV_TEST_HOOKS` 금지 추가 | H 후크가 제품 빌드에 들어가지 않음을 보장 | 예(검사 규칙 변경) |
| 호스트 코드(I1)에 H 후크 포함 | 구현 | 예(I1~I10 구현 승인 범위) |
| W 대체 함수를 쓰는 시험 파일 추가 | 시험 코드 | 시험 코드 추가는 S 단계 승인 범위로 가능하나, 위 항목이 선행 |
| 벤더링 후크(V) | 설계상 사용하지 않음 | 필요해지면 별도 승인 |

## 7. 한계
- 이 문서는 설계안이다. 후크는 어디에도 구현되지 않았고, I1 레지스트리 API가 확정되기 전에는 후크 위치가 최종이 아니다.
- W 실험은 한 환경의 한 함수(`thread_new`)에 대한 것이다. `thread_join`·`socket_connect` 등 다른 함수의 대체와 플랫폼별 링크 동작은 [미검증].
- T1a·T3의 실제 판정은 I1·I3 구현 이후에만 가능하다. 지금 가능한 것은 변경 전 기준선(T3 주입)이다.

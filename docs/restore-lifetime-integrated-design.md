# 복원 세션 수명·오류 전달 통합 설계 (권고안, 일괄 승인 대상)

상태: **구현 전 통합 설계 권고안.** 이 문서의 권고안(D1~D8)은 한 번의 일괄 승인으로 확정한다. 구현(벤더링 소스 수정, 호스트 모듈, 시험 구현)은 이 승인과 별개로 승인한다.
사실 근거: `docs/async-lifetime-design.md`(P1~P11 전제, P10 판정표, 상태 모델 초안), `docs/tss-integration-design.md` 2.6~2.8절. 시험: `docs/fake-device-test-spec.md`.
이 문서가 결정 문서이며, 앞선 두 문서의 "후보"·"미결정" 표기는 이 문서의 결정으로 대체된다(사실 항목은 그대로 유효).

표기: **[확인]** 코드로 확인 / **[위험]** 코드상 도달 가능, 미관측 / **[제약]** 반드시 충족할 설계 제약 / **[권고]** 대안 비교 뒤 선정한 안 / **[검증]** 시험·실기 확인이 필요한 사항(검증 조건과 실패 시 대안 포함).

## 0. 설계 완료 기준과 점검 결과

아래 여섯 가지를 모두 충족해야 이 설계를 완성으로 본다. 점검 결과는 11절에 둔다.

| 번호 | 기준 |
| --- | --- |
| K1 | 정상 종료, 오류 종료, 취소 실패의 모든 경로에서 객체 해제 책임이 정의되어 있다 |
| K2 | 스레드 등록부터 완료까지 상태 전환과 동기화 조건이 모순되지 않는다 |
| K3 | 최초 오류가 보존되고 최종 성공으로 잘못 보고되지 않는다 |
| K4 | 공유 연결과 정책 훅의 수명이 활성 작업보다 짧아지지 않는다 |
| K5 | 모든 안전성 요구에 소스상 보장 방법과 검증 방법이 연결되어 있다 |
| K6 | 미확정 사항마다 검증 조건과 검증 실패 시 적용할 대안이 있다 |

"완성"은 모든 위험이 해소됐다는 뜻이 아니라 모든 위험의 처리 방식이 정의됐다는 뜻이다. 소스 구조로 보장해야 하는 사항(객체 수명, 등록 원자성, 오류 전파)은 "시험 예정"으로 남기지 않고 보장 방법을 둔다.

## 1. 범위

관리 대상 실행 단위:

| 단위 | 생성 | 현재 종료 보장 | 이 설계의 처리 |
| --- | --- | --- | --- |
| 복원 엔진 스레드 | `host/restore_session.c` | `end()`가 등록 수만 확인 | 유지, 종료 순서에 포함 |
| 비동기 데이터 요청 스레드(5종) | `restore.c` 루프, detach | **없음** | 등록부(레지스트리)로 관리 (D1) |
| 리버스 프록시 제어·연결 스레드 | `reverse_proxy_client_start_proxy` | `reverse_proxy_client_free`가 join(제어·마지막 연결만) | 결함 보완 + 종료 순서에 포함 (D8) |
| FDR 스레드 | `#ifndef HAVE_REVERSE_PROXY` 분기 | 빌드 설정상 컴파일되지 않음(P11) | 해당 없음(설정이 바뀌면 재평가) |
| 다운로드·TSS 스레드 | 호스트 모듈 | 별도 | 이 설계의 취소 신호만 연결 |

관리 대상 객체: `client`, `client->restore`(장치 핸들, restored 연결, `bbtss`), `build_identity`, `ipsw`, `filesystem`, 서비스 연결, ASR 연결, FDR 관련 연결, 정책 훅, 세션 기록(TSS 기록 포함).

## 2. 추가로 확인한 사실 (이번 소스 조사)

| 번호 | 내용 | 표기 | 근거 |
| --- | --- | --- | --- |
| P12 | 리버스 프록시: `start_proxy`(엔진 스레드)가 **제어 스레드** 하나를 만든다. 제어 스레드는 연결 요청마다 **연결 스레드**를 만들며 핸들을 지역 변수 `th_conn` 하나에 대입한다 | [확인] | `reverse_proxy.c:478,497,601` |
| P13 | 연결 요청이 연달아 오면 **이전 연결 스레드의 핸들이 덮어써져** join·free되지 않는다. 그 스레드는 제어 클라이언트 `client`를 참조한다(`client->th_ctrl` 등). `reverse_proxy_client_free`가 `client`를 해제한 뒤에도 남아 있으면 해제된 메모리 참조 | [위험] | `reverse_proxy.c:433,497,519~523,644~660` |
| P14 | 연결 스레드는 장치가 지정한 호스트로 `socket_connect`하며 글루 훅(`limd_glue_connect_guard`)의 적용을 받는다. 프록시 루프(`while (1)`)는 종료 플래그를 보지 않고 **장치 연결이 닫히거나 오류가 날 때까지** 돈다 | [확인] | `reverse_proxy.c:191`, 프록시 루프 `207~262` |
| P15 | `reverse_proxy_client_free(rproxy)`는 `restore_client_free` **앞**(`restore.c:5912` vs `5923`)에서 엔진 스레드가 호출한다 → 리버스 프록시 스레드는 `client` 해제·`end()` 전에 join됨. 단 마지막 연결 스레드가 끝나지 않으면 join이 **무기한 블로킹**될 수 있고 취소 경로가 없다 | [확인] 순서 / [위험] 블로킹 | `restore.c:5912,5923`, `reverse_proxy.c:519~523` |
| P16 | 리버스 프록시 스레드는 `hv_net_guard_engine_enter`로 등록되지 않는다 → 훅 해제 판정(`engine 수`)에 보이지 않음. P15의 순서 덕에 정상 경로에서는 훅 제거 전에 join되지만 P13의 유실 스레드는 보호되지 않음 | [확인] / [위험] | `host/net_guard.c`, 앞선 조사 |
| P17 | 복원 연결(`restored_send`)은 `property_list_service_send_xml_plist` 하나로 가며, 한 메시지가 **두 번의 `service_send`**(4바이트 길이, 본문)로 나간다. 두 스레드가 같은 연결로 동시에 보내면 길이와 본문이 뒤섞여 프레이밍이 깨질 수 있다. 연결 객체에 잠금이 없다. `restored_send`가 모든 복원 연결 송신의 단일 진입점이다 | [확인] 구조 / [위험] 손상 | `property_list_service.c:109~`, `libimobiledevice/src/restore.c:160` |
| P18 | `DataPort` 없는 비동기 처리기 호출(`_restore_get_service_client_for_data_request`)이 `SERVICE_TYPE_RESTORED`로 `restored_send`를 부르는 곳은 최소 7곳(1139, 1199, 1305, 1363, 1475, 1544, 1872행의 처리기)이다 | [확인] | `restore.c` |
| P19 | `usbmuxd_disconnect`는 `close(fd)`만 한다. `shutdown(SHUT_RDWR)`는 fd 번호를 유지한 채 다른 스레드의 블로킹 수신을 깨울 수 있는 수단이다(POSIX TCP; **이 환경에서의 효과는 [검증]**) | [확인] / [검증] | `libusbmuxd.c:1584`, `socket.c:1379` |
| P20 | 루프 뒤 반환 경로: `async_err != 0`이면 `err` 대체 → `reverse_proxy_client_free` → `restore_client_free` → `return err`(5907~5924). 정리 구간은 하나의 함수 `restore_device` 안이다 | [확인] | `restore.c:5907~5924` |

P1~P11(비동기 스레드 detach·카운터 부재, 훅 제거 후 허용·본문 상한 상실, `client` 참조 필드, `FLAG_QUIT` 미확인, `async_err`·`flags` 비동기화 접근, 호출당 수신 한도와 작업 전체 한도의 차이, `close`의 한계, 루프의 오류 덮어쓰기 P10, 빌드 설정 P11)는 `async-lifetime-design.md`를 따른다.

## 3. 확정할 설계 제약 [제약]

선택 사항이 아니라 구현이 반드시 충족할 조건이다.

| 번호 | 제약 |
| --- | --- |
| C1 | 신규 비동기 작업의 **등록 승인과 활성 작업 수 증가는 하나의 원자적 전환**이다(같은 잠금) |
| C2 | 등록된 작업은 스레드 생성 지연·실패와 무관하게 활성 수로 보호된다. 생성 실패 시 등록을 취소하고 종료 대기자를 깨운다 |
| C3 | `CLOSING` 진입과 등록 검사는 같은 잠금 아래에서 한다. `CLOSING` 이후 등록은 거부된다. 이미 승인된 작업의 실행·완료 통지·활성 수 감소는 `CLOSING`에서도 허용된다 |
| C4 | 완료 통지는 작업이 `client` 및 하위 객체에 접근하는 **마지막 동작 뒤**에 한 번 일어난다. 통지 이후 작업은 세션 객체를 건드리지 않는다 |
| C5 | 레지스트리는 세션 객체보다 오래 산다(프로세스 정적 저장소). 늦은 완료 통지가 해제된 메모리에 쓰지 않는다 |
| C6 | `client`, `client->restore`, 장치 핸들, restored 연결, 서비스·ASR 연결, `build_identity`, `ipsw`, `filesystem`, 세션 기록은 **활성 작업이 0이고 상태가 `CLOSED`일 때만** 해제된다. 대기 한도 도달만으로 해제하지 않는다 |
| C7 | 정책 훅은 `CLOSED`일 때만 제거된다. 정책 훅은 활성 작업(리버스 프록시 스레드 포함)보다 먼저 사라지지 않는다 |
| C8 | 최초 오류가 발생한 실행의 최종 결과는 성공으로 보고되지 않는다(실패 전파). 최초 오류의 경로(처리기·메시지 종류)와 오류 코드를 식별할 수 있다(오류 보존) |
| C9 | 최종 결과는 활성 작업이 0임을 확인한 **뒤에** 확정한다. 완료 확인 전에 성공을 보고하지 않는다. 활성 수가 0이 되지 않은 채(`QUIESCENCE_FAILED`) 끝나는 실행의 결과는 항상 실패다 |
| C10 | 복원 연결로의 송신은 **메시지 단위로 직렬화**한다(길이+본문이 한 임계구역) |
| C11 | `QUIESCENCE_FAILED`에서는 아무것도 해제하지 않고 훅을 유지하며 같은 프로세스의 신규 세션을 거부한다. 자동 복귀는 없다 |
| C12 | 레지스트리 잠금을 잡은 채 처리기·콜백·네트워크 호출을 하지 않는다. 종료 대기는 비동기 처리기 스레드에서 호출하지 않는다(자기 대기 교착 방지) |

## 4. 통합 구조 (권고안)

### 4.1 구성 요소

| 구성 요소 | 위치 | 역할 |
| --- | --- | --- |
| 세션 레지스트리 | 호스트 신규 모듈(예: `host/restore_registry.{h,c}`), 프로세스 정적 저장소 | 상태(`IDLE/ACTIVE/CLOSING/CLOSED/QUIESCENCE_FAILED`), 활성 수, 뮤텍스+조건변수, 취소 신호, **첫 오류 기록** |
| 훅 인터페이스 | `hv_*` 함수 포인터(NULL이면 기존 동작), 벤더링 소스에는 호출 지점만 추가 | 벤더링 코드가 레지스트리를 직접 알지 않게 함. 기존 `hv_urlasset_guard`와 같은 방식 |

| 호스트 사용 | `host/restore_session.c`(`begin/end`), `host/install.c`(결과·정리 순서) | 상태 점검, 결과 합성, 실패 종류 보고 |

### 4.2 상태와 전환

```
IDLE ─begin()─▶ ACTIVE ─(종료 시작)─▶ CLOSING ─(활성 0 확인)─▶ CLOSED ─end()─▶ IDLE
                                         │
                                         └─(대기 한도)─▶ QUIESCENCE_FAILED (종단, 프로세스 재시작 전까지)
```

| 동작 | ACTIVE | CLOSING | CLOSED | QUIESCENCE_FAILED |
| --- | --- | --- | --- | --- |
| 신규 작업 등록 | 허용 (승인+수 증가 원자) | 거부 | 거부 | 거부 |
| 기존 작업 실행 | 허용 | 취소 신호에 따라 | 해당 없음 | 계속(생존) |
| 완료 통지·활성 수 감소 | 허용 | 허용 | 해당 없음 | 허용(기록만, 상태 불변) |
| 객체 해제·훅 제거 | 불가 | 불가 | 가능 | **불가** |
| `begin()` | 거부 | 거부 | 거부(`end()` 전) | **거부** (`IDLE`에서만 허용) |
| 오류 기록 | 허용 | 허용 | 해당 없음 | 허용(기록만) |

- `begin()`은 기존 규칙(엔진 스레드 수 0)에 더해 상태가 `IDLE`일 때만 허용한다(정리되지 않은 `CLOSED`에서 훅을 다시 설치·목록을 비우는 일을 막는다).
- `end()`는 `CLOSED`에서만 훅을 제거하고 `IDLE`로 전환한다. 다른 상태면 훅을 유지하고 실패를 돌려준다.
- 늦은 완료 통지는 활성 수만 줄인다. `QUIESCENCE_FAILED`에서 활성 수가 0이 되어도 상태는 바뀌지 않는다(자동 복귀 없음). 진단 값(`late_quiesced`)만 기록한다.

### 4.3 정상·오류·취소 실패의 종료 순서 (K1)

`restore_device` 안에서 루프 종료 직후부터 반환까지의 순서를 하나로 정한다. 벤더링 변경 지점은 `restore.c:5907~5924` 구간이다.

| 순서 | 동작 | 정상 종료 | 오류 종료 |
| --- | --- | --- | --- |
| 1 | 루프 탈출 | `FLAG_QUIT`(완료 상태) | `FLAG_QUIT`(오류) |
| 2 | 첫 오류 확정 보류 | 해당 없음 | 첫 오류는 루프가 기록해 둠(D3) |
| 3 | `CLOSING` 전환(신규 등록 차단) | 동일 | 동일 |
| 4 | 취소 신호 | **보내지 않음**(자연 완료 대기) | **보냄**(D2) |
| 5 | 리버스 프록시 정리(`reverse_proxy_client_free`) | 동일(D8: 종료 보장 추가 뒤) | 동일 |
| 6 | 활성 수 0 대기(한도 있음) | 자연 완료 대기 | 취소 후 대기 |

| 7b | 한도 도달 → `QUIESCENCE_FAILED` | (정상 종료여도 동일) **`restore_client_free`를 호출하지 않고** 실패 종류 `QUIESCENCE`와 첫 오류를 돌려줌 | 동일 |
| 8 | 호출자(`install.c`) | 7a: `idevicerestore_client_free` → `end()` | 7a 동일. 7b: **해제·`end()` 생략**, 실패 보고 |

| `build_identity`, `ipsw`, `filesystem` | 엔진 | 엔진 | 7a 뒤 | 유지 |
| 서비스 연결(PLIST), ASR 연결 | 비동기 처리기 | **처리기 자신** | 처리기 안(정상·오류·취소 모두) | 처리기가 살아 있는 동안 유효 |
| `args`, `message` 복사본 | 루프 | 처리기 | 처리기 끝(생성 실패 시 루프가 해제 — 현재 `message` 누수 수정) | 해당 없음 |
| 리버스 프록시 클라이언트와 스레드 | 엔진 | `reverse_proxy_client_free` | 5단계 | 5단계가 끝나지 않으면 7b |
| 세션 기록(TSS 포함) | 레지스트리 | 레지스트리 | `CLOSED` 확정 뒤 | 유지 |
| 정책 훅 | `begin()` | `end()` | `CLOSED`에서만 | 유지 |

### 4.4 레지스트리 동작 개요 (구현 인터페이스는 구현 승인에서 확정)

| 동작 | 설명 |
| --- | --- |
| `try_register()` | 잠금 → 상태가 `ACTIVE`이면 활성 수++ 하고 성공, 아니면 거부 |
| `unregister()` | 생성 실패 시: 활성 수--, 대기자 깨움 |
| `complete()` | 처리기의 마지막 동작: 활성 수--, 0이면 대기자 깨움 (C4, C5) |
| `close_begin()` | 잠금 → `CLOSING`. 이후 `try_register`는 거부 |
| `wait_quiescent(deadline)` | 조건변수 대기. 활성 수 0이면 `CLOSED`, 한도 도달이면 `QUIESCENCE_FAILED` |
| `request_cancel()` | 원자 취소 플래그 설정 + 등록된 연결에 `shutdown` (D2) |
| `record_error(source, code)` | 잠금 → 첫 오류가 비어 있으면 `{source, code, seq}` 저장, 아니면 총 오류 수만 증가 |
| `first_error()` | 최종 합성용 읽기 |

교착·순서 점검(C12): 잠금은 짧은 임계구역뿐이다. `wait_quiescent`는 엔진 스레드(루프 종료 뒤)에서만 호출한다. 비동기 처리기는 `complete()`만 부르며 대기하지 않는다. 루프는 종료 뒤 대기하므로 대기 중에 처리할 메시지가 없다. 단, 비동기 처리기가 루프의 수신 처리나 장치 측 후속 메시지에 의존하면 대기가 풀리지 않는다 — 이 경우는 `QUIESCENCE_FAILED`로 수렴한다(안전 측 실패, [검증] V1).

## 5. 결정 (D1~D8)

각 항목은 **제약 / 대안 비교 / 권고안 / 검증 조건과 실패 시 대안**으로 쓴다.

### D1 완료 대기 방식

- 제약: C1~C5, C12.
- 대안: (a) 카운터+조건변수, (b) 작업 목록+`thread_join`.
- 비교: 비동기 스레드는 `thread_detach`되어 핸들이 없고 생성 지점도 `restore.c` 한 곳이다. (b)는 detach 취소와 목록 관리가 필요하고 join 대기는 한도 있는 대기(`timedjoin`)를 이식성 있게 제공하지 않는다. (a)는 `pthread_cond_timedwait`로 한도를 주기 쉽고 detach를 유지해 변경이 작다.
- **권고: (a) 카운터+조건변수.** 레지스트리는 4.4절.
- 검증 조건: T1a(등록·전환 경합 후크), T3, T9. 실패 시 대안: 레지스트리 잠금 순서에 결함이 나오면 (b)로 전환하지 않고 잠금 범위를 줄인다(핵심 구조는 유지).

### D2 대기 한도와 취소 전달

- 제약: C6, C11. 소스가 작업 단위 종료를 보장하지 않는다(P7). 개별 curl 취소 주기(200 ms)는 작업 전체 종료 시간이 아니다.
- 대안: (a) 일괄 한도, (b) 작업 종류별 한도, (c) 단계별(자연 완료 유예 → 취소 → 재대기).
- **권고: (c) 단계별.** 정상 종료는 취소 없이 유예 한도까지 대기하고, 오류 종료는 즉시 취소 신호 후 취소 한도까지 대기한다. 한도 값은 **T7 관측 전에는 정하지 않는다**(구현 파라미터, 기본값은 시험 뒤 결정). 취소 신호는 두 가지다.
  1. **원자 취소 플래그**를 처리기·ASR 송신 루프·ASR 연결 재시도 루프·URLAsset/BasebandData 경로가 확인한다(기존 curl 플래그 재사용 + 처리기 진입·청크 사이·재시도 사이).
  2. **`shutdown(SHUT_RDWR)`**: 레지스트리에 등록된 연결 fd에 호출해 블로킹 수신·송신을 깨운다. **`close`는 쓰지 않는다**(P19: 대기를 깨운다는 보장이 없고 fd 번호 재사용 위험). 연결은 소유 처리기가 자신의 종료 경로에서 닫는다.
- 검증 조건: T7(종류별 취소 반응·종료 시간), T8(`shutdown`/`close`의 대기 해제, 플랫폼별 기록). 실패 시 대안: `shutdown`이 대기를 깨우지 않는 플랫폼이면 취소 한도를 길게 두고 `QUIESCENCE_FAILED` 수렴에 의존한다(안전 측). 취소 플래그 확인 지점이 부족하면 해당 블로킹 구간(`getaddrinfo`, libtatsu `sleep(2)`)은 한도 내 자연 종료만 기다린다.
- Android 보장: Android 검증 전까지 `shutdown` 동작을 보장하지 않는다.

### D3 오류 보존과 실패 전파 (P10)

- 제약: C8, C9.
- 대안: A 첫 오류 보존 / B 오류 직후 탈출 / C A+B.
- 비교 기준: 추가 메시지 처리 유지 여부와 프로토콜 영향(B는 장치가 실패 후 보내는 마무리 메시지에 의존하는지 미검증).
- **권고: A.** 구성:
  1. 루프의 `err` 대입 지점 직후(처리기 반환 지점)에서 `err < 0`이면 `record_error(source=MsgType/처리기, code)`를 부른다(첫 오류만 저장). 비동기 처리기는 `async_err` 대입을 같은 `record_error`로 대체한다.
  2. 종료 순서 7a에서 최종 `err`를 합성한다: `첫 오류 있음 → 반환값은 그 코드(음수)`, 없고 `async_err`도 없으면 기존 `err`. 이 합성은 **활성 수 0 확인 뒤**에 한다(C9).
  3. `host/install.c`에서 방어적 이중 확인: `idevicerestore_start`가 0을 돌려줘도 레지스트리에 첫 오류가 있으면 `HV_INSTALL_FAILED`로 보고한다(호스트만의 변경).
  4. 메시지 처리 순서는 바꾸지 않는다(추가 메시지는 현재처럼 처리됨). 외부에서 관찰되는 변화는 최종 반환값과 앱 보고뿐이다. **추가 메시지 처리의 부작용(장치로의 추가 전송 등)은 그대로 남는다 — 허용하는 한계로 명시한다.**
- 오류 식별 정보: `{source(처리기 이름/메시지 종류 열거), code, seq(기록 순서), thread(루프/비동기)}`. TSS 실패 분류기 결과는 별도 TSS 기록(`tss-integration-design.md` 3.4)에 있고, 첫 오류 기록은 그 항목을 `source`로 참조한다.
- 검증 조건: T2-보존, T2-전파((a)~(d) 및 대조군), 변경 전 기준선과 변경 후 회귀. 실패 시 대안: T2에서 추가 메시지의 부작용이 문제로 나오면 B(오류 직후 탈출)를 추가로 검토하되, 그 전에 장치 프로토콜 영향을 시험으로 확인한다.
- B는 현 단계에서 선택하지 않는다(프로토콜 영향 미검증).

### D4 공유 연결 직렬화

- 제약: C10. P17: 한 메시지가 두 번의 송신이므로 메시지 단위 잠금이 필요하다.
- 대안: (a) `restored_send` 안에 연결별 뮤텍스(벤더링 `libimobiledevice/src/restore.c`), (b) `restore.c`의 호출 지점 전부를 래퍼로 교체, (c) 호스트가 연결 계층을 가로챔.
- 비교: `restored_send`가 모든 복원 연결 송신의 단일 진입점(P17)이므로 (a)는 한 곳 변경으로 모든 호출자를 덮는다. (b)는 수십 곳 변경. (c)는 링크 가로채기 Android 미검증.
- **권고: (a).** 잠금은 `restored_client` 객체에 두고 `restored_send` 전체를 감싼다. 수신(`restored_receive`)은 확인한 범위에서 루프 스레드만 호출한다(`_restore_service_recv_timeout`의 호출처는 찾지 못했다)고 보고 잠그지 않는다. 이는 구현 승인 전에 호출처를 다시 확인한다. 요청-응답 대응 순서는 비동기 응답이 어느 순서로 가도 장치가 받아들이는지 [검증] V2.
- 검증 조건: T4(동시 송신, 큰 메시지). 실패 시 대안: 송신 잠금으로 해결되지 않는 프로토콜 순서 문제가 나오면 `DataPort` 없는 비동기 요청을 루프 스레드에서 직렬 처리(동기 전환)하는 안(D5)을 해당 종류에 한해 재평가한다.

### D5 비동기 종류를 동기로 전환

- **권고: 채택하지 않는다(대안으로만 유지).** 이유: 프로토콜 호환성, 루프 블로킹(장시간 `SystemImageData` 전송 중 루프가 다른 메시지를 못 받음) 미검증. D4의 대안으로만 재평가한다.

### D6 앱 보고

- 제약: C11, C8.
- **권고:** `host/install.c`에 실패 종류를 구분하는 조회를 추가한다. 종류: `RESTORE_FAILED`(복원 실패, 재시도 가능), `SESSION_NOT_QUIESCENT`(재시도 제한: 같은 프로세스에서 새 복원 불가, 프로세스 재시작 필요), `ABORTED_BY_USER`. `hv_install_result()`의 0/-1은 유지하고 종류 조회 함수를 추가한다(기존 호출자 호환). 앱은 `SESSION_NOT_QUIESCENT`일 때 "프로세스 재시작이 필요함"을 표시한다.
- Android Activity 재생성은 네이티브 프로세스 종료가 아니다. 프로세스가 종료되지 않으면 남은 스레드와 전역 정책 상태가 유지되므로 앱은 프로세스 종료를 요청해야 한다. 재시작이 장치 측 복원 상태를 정상화한다는 보장은 없다.
- 검증 조건: T5, T6, T11. 실패 시 대안 없음(앱 표시 문제로 국한).

### D7 객체 소유권

- 제약: C4, C6.
- 세 가지를 나눠 결정한다.

| 구분 | 결정 |
| --- | --- |
| 소유권 | 서비스·ASR 연결은 처리기 소유(현행 유지). `client`, `client->restore`, 공유 restored 연결은 엔진 소유(현행). 레지스트리와 세션 기록은 레지스트리 소유 |
| 사용 권한 | 처리기는 등록~`complete()`까지만 `client`·하위 객체를 참조한다. `complete()` 이후에는 세션 객체를 건드리지 않는다(C4) |
| 종료 책임 | 취소 실패 시 엔진(`restore_device`)이 모든 객체를 유지하고, 호출자(`install.c`)도 해제를 생략한다. 유지된 객체는 프로세스 종료 때 운영체제가 회수한다 |

- 처리기가 연결을 소유해도 세션 종료는 작업 종료를 확인한다(6단계). 세션이 연결 소유권을 넘겨받는 안은 채택하지 않는다(살아 있는 처리기가 쓰는 동안 해제하면 해결되지 않음).
- 검증 조건: T5, T9, T3, 해제 감시(AddressSanitizer). 실패 시 대안: 처리기 안의 늦은 참조가 발견되면 해당 필드를 처리기 시작 시점에 지역 복사(스냅샷)하도록 바꾸되 `client` 자체는 C6로 유지한다.

### D8 리버스 프록시 종료 보장

- 제약: C7, C6. P13~P16.
- 판단: 리버스 프록시는 `client` 해제 전에 join되는 순서(P15)로 공통 수명 관리에 **부분적으로** 이미 묶여 있다. 보완이 필요한 것은 (1) 연결 스레드 핸들 유실(P13), (2) 무기한 join(P15).
- 대안: (a) 현행 유지 + 종료 순서 5단계에서 `request_cancel`로 프록시 장치 연결에 `shutdown`, (b) `reverse_proxy.c`에서 연결 스레드를 목록/카운터로 관리하고 종료 플래그를 프록시 루프가 확인.
- **권고: (b) 최소 변경 + (a) 취소 연계.** 연결 스레드 수를 세어 `reverse_proxy_client_free`가 전부 기다리고(핸들 덮어쓰기 제거), 프록시 루프(`while (1)`)가 종료 플래그를 보게 한다. 리버스 프록시 스레드가 5단계에서 끝나지 않으면 `QUIESCENCE_FAILED`로 수렴한다(join 무기한 대신 한도 있는 대기가 필요하므로 구현 시 `thread_join` 대신 완료 카운터 사용).
- 범위 판단: 리버스 프록시는 공통 수명 관리 **대상에 포함**한다(독립 보장이 불충분하므로 "범위 밖"이 아님).
- 검증 조건: T12(열린 프록시 연결이 있는 상태에서 종료), T13(연달아 연결 요청 시 이전 스레드 유실). 실패 시 대안: 벤더링 `reverse_proxy.c` 수정이 승인되지 않으면 5단계를 건너뛰는 선택지는 없고(C7), 대신 프록시 정리를 별도 감시 스레드에서 한도 있게 수행해 실패 시 `QUIESCENCE_FAILED`로 처리한다.

추가 발견(모두 이 문서에서 해결 또는 시험 항목화):
1. 정리 구간(`restore_client_free`)이 `restore_device` 안에 있으므로 대기와 7b 분기는 호스트가 아니라 **벤더링 `restore.c`** 안에 있어야 한다. 호스트(`install.c`)가 해제를 생략하려면 `restore_device`가 취소 실패를 호출자에게 알려야 하므로 반환 규약에 실패 종류 전달(전역 레지스트리 조회)을 쓴다.
2. 거부된 요청의 `err = -1`은 D3 A에서 첫 오류로 기록되어 덮어쓰기와 무관하게 전파된다(R2의 "오류가 루프 종료까지 전달" 전제가 P10 때문에 깨졌던 문제가 해소됨).
3. `async_err`/`flags`의 동기화는 D3의 `record_error`와 `__atomic` 종료 요청으로 처리하되, 완료 동기화(D1)와 별개 변경으로 둔다.
4. 시험 T12/T13을 추가했다(`fake-device-test-spec.md`).

남은 위험(처리 방식은 정의됨, 실행 관측 없음): P10 성공 오보고, 비동기 수명 결함, 공유 연결 프레이밍 손상, 리버스 프록시 스레드 유실/무기한 join. 모두 구현·시험 전까지 코드상 위험이며, 실제 장치 동작은 이 설계로 검증되지 않는다.

# Android 복원 흐름 통합 설계 (TSS ~ 가상 디스크)

기준일: 2026-11-10 · 브랜치 `research/android-port` · 기준 커밋 `fbbabea`, 통합 구현 반영(아래 "구현 상태")
이 문서는 읽기 전용 소스 분석의 결과이며, 구현이 바뀌면 같은 커밋에서 함께 고친다.
문서에 적힌 정책이 "설계 결정"이라고 해서 구현되었다는 뜻이 아니다. 구현 상태는 각 항목의 "구현" 열을 따른다.

## 0. 상태 표기

근거 수준과 실행·승인 상태는 서로 다른 축이므로 항목마다 둘을 따로 적는다.

| 표기 | 의미 |
| --- | --- |
| 검증 완료 | 실기기 또는 명시한 시험 환경에서 실제 동작을 확인함 |
| 코드 확인 | 소스에서 경로를 확인함. 실제 동작은 확인하지 못함 |
| 설계 결정 | 구현에 적용하기로 한 정책·구조. 구현 완료를 뜻하지 않음 |
| 미검증 | 해당 동작을 실제로 확인하지 못함 |
| 별도 승인 필요 | 네트워크 요청, 펌웨어 전송, 디스크 변경 등 실행에 별도 승인이 필요함 |

## 3. TSS

| 요청 | 시점 | 결과물 | 실패 시 |
| --- | --- | --- | --- |
| 첫 TSS (`get_tss_response`) | 정지점 A 직후, DFU 전송 전. `tss_enabled`일 때 | AP 티켓 (메모리) | 복원 중단 |
| LocalPolicy | macOS variant일 때, 첫 TSS 직후 | `tss_localpolicy` (`lpolrestore`용) | 복원 중단 |
| RecoveryOS root ticket | macOS variant일 때, LocalPolicy 직후 | RecoveryOS 티켓 | 복원 중단 |
| 재요청 | iBSS 후 DFU에서 AP nonce가 달라졌을 때 | 새 AP 티켓 | 복원 중단 |
| 추가 요청 (`restore.c`의 `tss_request_send` 약 10곳) | 복원 모드에서 장치가 펌웨어 데이터를 요청할 때 | 부품별 티켓 | 해당 요청 실패 처리 (미평가) |

- 코드 확인: 앞의 세 요청은 DFU 전송보다 먼저 나가고 장치 USB는 nonce 읽기에만 쓴다. `FLAG_SHSHONLY`가 그 지점에서 멈춘다.
- 정책 충돌: `FLAG_SHSHONLY`는 shsh 파일을 캐시 폴더에 쓴다. 티켓을 저장하지 않는 원칙과 충돌하므로 이 경로를 쓰지 않거나 쓰기를 막아야 한다 (벤더링 변경, 별도 승인).
- 추가 요청 약 10곳 중 가상 Mac에서 실제로 나가는 것이 몇 개인지는 실행 전에는 알 수 없다 (미검증). 허용 개수를 정하지 않고, 차단 모드에서 시도된 종류만 기록해 보고한다.
- 모든 TSS 요청은 curl 대체 계층(`curl_mbedtls.c`)을 지나므로 현재의 차단 모드·시도 카운터가 적용된다.

## 4. DFU 재접속

iBSS 전송이 끝났다는 사실만으로 다음 단계로 가지 않는다.

### 호출 순서 (코드 확인: `idevicerestore.c`, `dfu.c`, `recovery.c`)

1. 개인화된 iBSS 전송, DFU 핸들 닫기
2. 장치 끊김을 최대 10 s 대기 (모드가 UNKNOWN이어야 함)
3. 재접속을 최대 10 s 대기 (모드가 DFU 또는 RECOVERY여야 함)
4. 새 DFU 클라이언트를 열어 AP nonce 재읽기, 달라졌으면 TSS 재요청
5. `SET_CONFIGURATION(1)`, macOS면 `Ap,LocalPolicy`를 `lpolrestore` 명령으로 전송
6. `boot-stage` 환경변수 읽기, stage1 구성요소 전송
7. `setenv auto-boot false`, `saveenv`, `setenvnp boot-args rd=md0 nand-enable-reformat=1 -progress -restore`, `RestoreLogo`, `setpicture 4`, `bgcolor 0 0 0`
8. iBEC 전송, RECOVERY 모드면 1 s 뒤 `go`. 이후 `recovery_send_ibec`가 끊김·재접속을 각 60 s까지 대기

### 완료 판정

각 이미지는 ① 전송 성공 반환, ② 끊김 관측(세션 번호 변경), ③ 재접속 관측(새 열거와 ARRIVED), ④ 새 모드가 기대값, ⑤ 새 핸들로 nonce 또는 환경변수 읽기 성공이 모두 맞아야 완료다. ②~④ 중 하나라도 없으면 "실패, 장치 상태 불명"으로 보고하고 자동 재시도하지 않는다.

### 가상 USB의 재접속 방식 (코드 확인: `devices/bdif.c`, `devices/virtio_usb.c`, `host/libusb_shim.c`)

- 끊김은 게스트가 만든다. 부트 단계가 바뀔 때 ROM 쪽 `REG_UNK2` 쓰기 또는 커널 드라이버의 `DRIVER_OK`가 `hv_vusb_set_online`을 부르며, 이 함수는 세션 번호를 올리고 대기 중인 요청·응답을 모두 버리고 대기 스레드를 깨운다. 온라인이 되는 것도 새 세션이다.
- 진행 중인 전송은 실패한다. `hv_vusb_recv`는 기다리던 세션이 바뀌면 -1을 돌려준다. 정상 끊김과 오류를 구분하는 규칙은 아직 없다.
- libusb 대체 계층의 `refresh()`는 세션이 다르거나 오프라인이면 이전 장치를 `gone`으로 표시하고 미완료 전송·남은 버퍼를 비우고 LEFT를 발생시킨다. 온라인이면 버스 리셋(최대 2 s) 후 디스크립터를 다시 읽어(각 2 s) 새 주소로 ARRIVED를 발생시킨다. 끊김과 재접속이 폴링 사이에 한꺼번에 일어나도 세션 비교로 LEFT→ARRIVED가 나온다.
- 이전 libirecovery 클라이언트는 죽은 장치를 가리킨다. 닫고(`dfu_client_free`) 새로 열어야 하며, "libirecovery를 다시 부르면 된다"는 가정은 성립하지 않는다. 새 장치의 모드는 다시 읽은 디스크립터(PID, 시리얼 문자열)로 정해진다.

### 위험 (미검증)

1. 정상 끊김이 전송 함수의 실패로 보일 수 있다.
2. iBSS가 돈 뒤 가상 장치가 내보내는 PID·시리얼 문자열을 모른다. 모드 판정이 맞는지는 실제 관측 전에는 알 수 없다. 첫 관측은 읽기 전용 로그(PID, 시리얼 길이, 모드)만 남기고 ECID는 남기지 않는다.
3. 타임아웃이 계층마다 다르다 (도구 10 s / 60 s / 30 s / 300 s, 열거 중 제어 읽기 2 s, 사전점검 총 상한 150 s). 바깥 상한을 안쪽보다 크게 맞춘다.
4. 벤더링 코드의 오류 반환 경로는 열린 DFU 핸들을 남길 수 있다 (정지점 A 성공 경로만 고침).

### PC 스탠드인 시나리오

`hv_vusb_set_online`을 시험에서 직접 불러 (a) 전송 후 끊겼다 다른 PID로 재접속(정상), (b) 안 끊김, (c) 끊기고 안 돌아옴, (d) 끊김과 재접속이 폴링 사이에 일어남, (e) 재접속 때 열거 실패를 재현한다. 각 시나리오에서 도구가 제한 시간 안에 끝나고, USB 핸들 0, 스레드 증가 없음을 자원 보고서로 확인한다. 기존 `restore_preflight.c`의 stage를 확장해 재사용한다.

## 5. 네트워크 정책

### 사실 (코드 확인)

- 현재의 curl 차단 모드(`hv_curl_deny_network`)와 카운터는 **curl 대체 계층만** 통제한다. 소켓을 직접 여는 경로는 통제하지 못한다.
- 가상 Mac이 호스트에 연결을 요청하는 경로가 둘 있다. TSS와 달리 목적지를 **장치가 정한다**.

### AEA / URLAsset (`restore.c`)

| 항목 | 내용 |
| --- | --- |
| 호출 위치 | 1265행 `restore_send_url_asset`, 4253행 AEA 경로(첫 조각이 "AEA1"이면 메시지를 3000 ms 대기, `Arguments`가 있을 때만 호출), 5066행 데이터 요청 종류 `URLAsset` |
| 대상 | 장치 메시지의 `Arguments.RequestURL`. 실제 호스트(Apple인지)는 실행 전에는 모른다 |
| 요청 | `RequestMethod`는 `GET`만 허용 |
| 응답 | plist `ResponseBody` · `ResponseBodyDone` · `ResponseHeaders` · `ResponseStatus`, 바이너리 plist로 복원 서비스에 전송 |
| 클라이언트 | libcurl API (우리 쪽은 `curl_mbedtls.c`). 리다이렉트를 따라감 |
| 인증서 | 소스는 `SSL_VERIFYPEER`=0이지만 대체 계층이 이 옵션을 무시하고 체인·호스트명을 항상 검증함 |
| 실패 영향 | `curl_easy_perform` 결과를 확인하지 않고 상태 0과 빈 본문을 장치에 돌려줌 |
| 제한 없음 | 본문 크기, 주소 허용 목록, 리다이렉트 횟수 |

호스트는 AEA 파일을 복호화하지 않고 그대로 전달한다. 장치가 URL을 요청할 때만 대신 열어 준다.

### FDR (`fdr.c`, 코드 확인: 프록시 본문 485~629행)

- 제어 채널(`FDR_CTRL`)은 복원 모드 연결 뒤 데이터 요청보다 먼저 연결하며, usbmuxd로 최대 10회, 회당 2 s 간격 재시도한다.
- 프록시 명령: 장치가 `0 3 <길이> <호스트> <포트>` 형식 패킷을 보내면 호스트가 `socket_connect(host, port)`(libimobiledevice-glue)로 **일반 TCP 소켓**을 열어 양방향을 중계한다. 호스트·포트는 검증 없이 장치 값을 그대로 쓴다. 연결 시간·전송량 제한이 없다.
- 이 연결은 curl 대체 계층을 지나지 않는다. 현재 차단 모드와 카운터로는 막지도 세지도 못한다.
- 같은 `socket_connect`를 libusbmuxd도 쓴다 (`libusbmuxd.c`가 비공개 usbmuxd 루프백으로 연결, `idevice.c`는 `socket_connect_addr`). 따라서 정책 지점은 호스트 전체의 연결 생성 경계여야 하고, usbmuxd 연결과 FDR 프록시를 구분해야 한다.
- 실패 처리: 제어 채널 시작 실패는 오류 로그 후 진행, `FDRTrustData` 전송 실패는 복원 중단. 종료 시 `fdr_disconnect` 후 `thread_join`.

### 설계 결정 (구현 상태는 위 "구현 상태" 표)

| 연결 경로 | 정책 |
| --- | --- |
| 앱 내부 usbmuxd | 실제로 생성한 리스너의 **주소·포트**와 정확히 일치하는 연결만, 기본 목적의 연결에 한해 허용 (판정기는 호출한 주체를 알지 못한다). 포트 범위(27100+) 전체 허용은 금지. FDR 연결과 curl 연결에는 이 예외를 적용하지 않는다 |
| FDR이 지정한 외부 호스트·포트 | 기본 거부 |
| AEA URLAsset의 HTTP 요청 | 기본 거부 |
| TSS 등 별도 승인된 Apple 요청 | 승인된 목적과 범위에 한해 허용 |
| 그 밖의 연결 | 기본 거부 |

허용 조건은 목적별로 다르다.

| 목적 | 조건 |
| --- | --- |
| 공통 (모든 연결) | 명시한 목적지·포트만, 해석된 실제 주소를 연결 직전에 검증(이름을 검증한 뒤 다른 주소로 연결하는 틈이 없음), 로컬·루프백·사설망·링크로컬·멀티캐스트 차단(usbmuxd 등록 항목 제외), 시도와 거부 사유 기록(주소·포트·이유만, URL 쿼리·경로·ECID 제외) |
| TSS · URLAsset (HTTP) | https만, 사용자 정보가 든 URL 거부, 호스트 이름·포트가 허용 목록에 있을 것. 리다이렉트는 매번 같은 `connect()` 검사를 다시 지나고 횟수는 3회, 본문은 32 MiB로 제한 |
| FDR (일반 TCP) | https 조건을 적용하지 않는다. 이름 없이 주소만 보이는 연결이므로 공개 주소는 기본 거부이며, 허용하려면 주소·포트를 개별 항목으로 승인한다. TLS 요구 여부는 FDR 실제 프로토콜을 본 뒤 따로 정한다 (미결정) |

연결 목적: 기본(라이브러리 내부, 비공개 usbmuxd 연결) / FDR(장치가 정한 목적지) / HTTP(curl). 목적은 판정기에 인자로 전달된다. FDR은 `connect()` 호출 하나를 감싸는 스레드별 표시(`limd_glue_connect_purpose`)로 알리며, 표시와 해제 사이에 빠져나가는 경로가 없다. 정책이 해제되면 거부가 허용으로 바뀌므로, 도구 스레드가 등록되어 있는 동안에는 해제를 거부한다.

구현 위치: glue의 세 `connect()` 직전에 호스트 쪽 판정 함수(`limd_glue_connect_guard`)를 부르고, curl 대체 계층과 URLAsset은 같은 판정기를 별도 훅으로 부른다. 훅이 비어 있으면(기본) 라이브러리의 동작은 이전과 같다.

## 6. 자원 관리

| 항목 | 현재 | 장기 실행 전 조치 |
| --- | --- | --- |
| IPSW 파일 디스크립터 | 수정됨: `ipsw_open`이 확인용으로 연 archive를 바로 닫는다 (이전에는 실행마다 1개 남음, 빌드 70에서 실측) | PC 시험으로 0 확인. 실기기 확인은 다음 APK에서 |
| usbmuxd 스레드 | 수정됨: 중지 요청 → 200 ms 이내 루프 복귀 → 리스너 닫기 → join | PC 시험으로 스레드 증감 0, 리스너 닫힘 확인 |
| DFU/RECOVERY 핸들 | 수정됨: `idevicerestore_client_free`가 두 클라이언트를 닫는다 (오류 반환 경로 포함) | PC 시험으로 핸들 0 확인 (정지점 A 경로). 오류 경로 시험은 잘못된 IPSW 시나리오로 간접 확인 |
| 복원 스레드 | 한 번에 하나, 취소 플래그 `global_quit_flag`, 타임아웃 시 실행 중인 클라이언트를 해제하지 않음 | 유지. 취소 후 유한 시간 join, 실패하면 "종료 못 함"으로 보고 |
| FDR 스레드 | 종료 시 disconnect + join | 중단 경로에서도 같은 호출인지 확인 |

종료 순서: 취소 플래그 → 복원 스레드 join(유한) → FDR → usbmuxd → libusb 핸들 → 자원 보고서에서 fd·스레드·핸들 비교.

## 7. 가상 디스크

**설계 기준값 (설계 결정, 디스크 생성은 아직 승인되지 않음)**

| 항목 | 값 |
| --- | --- |
| 파일명 | `macos_disk.img` |
| 논리 크기 | 128 GiB (137,438,953,472 바이트) |
| 생성 방식 | 희소 파일 |
| 재실행 | 기존 파일 유지 |
| 자동 삭제·재생성 | 금지 |
| 초기화 | 사용자의 명시적 요청과 별도 확인 후에만 |
| 크기 불일치 | 설계값과 다르면 자동 확장·축소하지 않고 불일치를 보고한 뒤 명시적 조치를 요구 |

- 현재 시험용 `blank_disk.img`는 8 GB sparse이고 루트 이미지(9.26 GB)보다 작아 설치 대상으로 쓸 수 없다. `--recreate-blank`는 이름이 `blank_`로 시작하는 파일만 지운다. 설치 디스크는 이 접두어를 쓰지 않으므로 영향받지 않아야 하며, 이를 시험으로 확인한다.
- DMG 크기만으로 설치 필요 용량을 계산할 수 없다. 희소 파일이라도 게스트가 쓰면 물리 사용량이 늘어나므로 복원 중 여유 공간을 계속 확인한다. 약 140 GB는 파일시스템 여유일 뿐이다.
- 생성 시점은 복원 모드(단계 5) 진입 전이다. 복원 중에는 디스크 구성을 바꾸지 않는다.

## 7.1 설치 디스크 구현 기준

`host/disk_policy.c`: 이름 `macos_disk.img`, 128 GiB(137,438,953,472 B) 희소 파일, 기존 파일 유지, 자동 재생성 금지, 크기가 다르면 확장·축소하지 않고 불일치로 보고, 초기화는 정확한 확인 문구(`ERASE macos_disk.img`)가 있을 때만. 이 파일 이름은 `blank_`로 시작하지 않아 `--recreate-blank`가 건드리지 않는다. 생성·초기화를 부르는 앱 코드는 아직 없으며(CI가 검사), 실제 생성은 별도 승인 항목이다.

## 8. 성공·실패 판정

| 단계 | 성공 | 실패 | "확인 못 함"으로 둘 경우 |
| --- | --- | --- | --- |
| TSS | 요청한 응답 모두 수신, 재시도 0, ECID·nonce·ticket 미출력 | 어느 하나라도 오류 응답 | 응답 형식만 맞고 내용을 검증하지 못함 |
| iBSS | 4절 ①~⑤ 모두 | 제한 시간 초과, 끊김 없음, 안 돌아옴 | 끊김은 봤으나 모드 판정 불가 |
| LocalPolicy · iBEC | 명령 성공, RECOVERY 재접속 | 명령 실패, 60 s 초과 | 환경변수 읽기만 실패 |
| RecoveryOS | 읽기 전용 확인 통과 | 모드 불일치 | 화면이 없어 눈으로 확인 불가 |
| 복원 모드 → ASR → FDR | MODE_RESTORE 300 s 이내, ASR 시작, 네트워크 호출이 허용 목록 안 | 타임아웃, URLAsset·FDR 오류 | FDR 소켓이 계측 밖인 동안은 네트워크 0건을 신뢰할 수 없음 |

"복원 완료"는 마지막 단계가 끝난 뒤 호스트가 정상 종료를 보고하고 장치가 다시 부팅했을 때만 쓴다. 그 전까지는 "준비 단계 성공"이다.

## 10. 알려진 한계

- 다른 IPSW 구성요소의 추출 규칙은 확인하지 않았다. 정지점 B가 필요 없다는 결론은 이 IPSW의 stored DMG에 한한다.
- `restore_device`의 펌웨어 TSS 세부와 AEA 이후 장치 쪽 동작은 읽지 않았다.
- 이번 구현의 시험 범위: URLAsset은 정책 판정만, FDR은 연결 거부와 패킷 길이 검증 코드만 있고 장치 메시지를 흉내 낸 시험은 없다. 재접속 판정은 복원 실행기에 연결되지 않았다(전송 단계가 없다). 실기기에서는 아무것도 확인하지 않았다.
- 문구 수정 3건은 사전점검 출력에 반영하지 않았다: "추출된 것 없음" → "작업 폴더에서 새 쓰기가 관측되지 않음", "디스크 쓰기 없음" → "복원 대상 디스크에 쓰기 없음".

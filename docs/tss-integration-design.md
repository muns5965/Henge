# TSS 통합 설계: 호출 경계, 결과 기록, 비동기 스레드와 정책 수명

상태 표기는 `docs/restore-architecture.md` 0절과 같다: 검증 완료 / 코드 확인 / 설계 결정 / 미검증 / 별도 승인 필요.
이 문서는 `docs/stop-b-design.md`(독립 분류기와 가짜 서버 시험)의 다음 단계, 곧 분류기를 실제 복원 흐름에 연결할 때의 문제만 다룬다. **구현안은 확정하지 않는다.** 확정하는 것은 안전성 요구조건이다.

조사는 소스 열람만 했다. 어떤 항목도 실행으로 관측하지 않았다(아래 표의 "실행 관측"은 전부 미실행).

## 1. 판정 틀

코드상 판정과 실행 관측은 별개의 축이다. 한 칸에 섞어 쓰지 않는다.

| 코드상 판정 | 실행 관측 |
| --- | --- |
| 결함 확인 | 미실행·미관측 / 실제 발생 관측 |
| 조사한 경로에서 불성립 | 해당 경로에서 발생 불가능 |
| 미확정 | 미관측 |

결함 확인은 세 조건이 같은 세션의 같은 실행 경로에서 시간적으로 이어질 수 있을 때만 쓴다. 각각 가능하다는 것만으로는 경쟁 조건이 입증되지 않는다. 불성립은 "조사한 경로"를 명시하고, 보지 못한 경로는 미확정으로 둔다.

## 2. 공통 정책 수명 문제 (TSS 통합과 분리해서 다룬다)

### 2.1 사실 (코드 확인)

| 항목 | 내용 |
| --- | --- |
| 비동기 요청 처리 | `restore.c:5780` 근처에서 `AsyncDataRequestMsg`마다 `thread_new`로 스레드를 만들고 `thread_detach`한다 (5786·5794행). 복원 도구가 비동기로 받겠다고 알리는 종류: `BasebandData`, `RecoveryOSASRImage`, `StreamedImageDecryptionKey`, `SystemImageData`, `URLAsset` (5682~5688행) |
| 종료 대기 | 비동기 스레드를 기다리는 `thread_join`이나 카운터·조건변수는 `restore.c`에서 찾지 못했다. FDR 스레드만 `thread_join`한다 (5914~5917행). `AsyncWait` 처리기(5187행)는 로그만 남기고 0을 반환한다 |
| 오류 전달 | `client->async_err`는 일반 `int`이다(`common.h:130`). 뮤텍스나 원자 연산이 없다. 스레드 종료를 알리는 수단이 아니다 |
| 루프 종료 | `FLAG_QUIT`가 서면 루프를 나가 `restore_client_free(client)`를 부르고 반환한다 (5923행). 진행 중인 비동기 작업을 기다리지 않는다 |
| 세션 종료 | `hv_restore_session_end()`는 `hv_net_guard_uninstall()`이다. 이 함수는 **등록된 엔진 스레드**가 있을 때만 거부한다. 엔진 스레드는 `hv_restore_session_run`이 등록하고, 복원 도구가 내부에서 만든 비동기 스레드는 등록되지 않는다 |
| 호출 순서 | `install.c`는 `idevicerestore_client_free(c)`(91행) 뒤에 `hv_restore_session_end()`(93행)를 부른다. 클라이언트 구조체는 세션 종료 전에 해제된다 |

### 2.2 훅 해제 후의 경로별 상태 (코드 확인)

| 경로 | 해제 후 | 근거 | 성격 |
| --- | --- | --- | --- |
| curl 연결 (TSS, 다운로드) | 검사 없이 연결 | `curl_mbedtls.c`: 훅이 NULL이면 건너뜀. libtatsu의 https 전용과 TLS 검증은 남음 | 외부 네트워크 |
| 글루 소켓 (FDR, usbmuxd) | 검사 없이 연결 | `socket.c` 441·1122·1256행: `limd_glue_connect_guard`가 NULL이면 건너뜀 | 장치가 지정한 주소 / 로컬 |
| URLAsset 전체 URL 검사 | 검사 없이 통과 | `restore.c:1297`: `hv_urlasset_guard`가 NULL이면 건너뜀 | 외부 네트워크 |
| URLAsset 본문 상한 | **상한이 사라진다** | `restore.c:1346`: `g_body_cap = hv_urlasset_guard ? hv_urlasset_max_body : 0` | 크기 제한 |

해제하면 보호가 줄어드는 정도가 경로마다 다르다. usbmuxd의 허용된 로컬 연결과 외부 연결은 같은 위험으로 묶지 않는다.

### 2.3 판정

| 조건 | 판정 근거 |
| --- | --- |
| ① `end()` 시점에 비동기 작업이 진행 중일 수 있음 | 코드상 가능: 대기 수단이 없다 |
| ② 그 상태에서 `hv_net_guard_uninstall()`이 성공함 | 코드상 가능: 비동기 스레드가 엔진 스레드로 등록되지 않는다 |
| ③ 남은 작업이 훅 경로에 도달함 | 코드상 가능: `BasebandData` 처리기가 TSS를 부르고(`restore.c:2351`), `URLAsset` 처리기가 curl과 URL 검사를 쓴다 |
| 시간적 연결 | 가능한 순서: 다른 메시지의 오류(`err < 0`)로 루프가 끝나는 동안 `URLAsset` 다운로드나 `BasebandData` TSS가 진행 중 |

- **코드상 판정: 결함 확인 (정책 수명). 실행 관측: 미실행·미관측.**
- **현재 노출 범위:** 지금의 시험 모드(정지점 A)는 복원 모드 메시지에 도달하지 않으므로 이 경로가 실행되지 않는다. 실제 복원 단계로 가는 시점에 위험이 켜진다.
- **client 구조체 (확인된 사실과 미확정을 분리):**
  - 확인된 사실: `restore_device`는 반환 직전에 `restore_client_free(client)`를 부르고(5923행), `install.c`는 `idevicerestore_client_free(c)` 뒤에 `end()`를 부른다. 이 해제 앞에 비동기 스레드를 기다리는 코드는 없다.
  - 확인된 참조(2.6절): 비동기 처리기는 `client`, `client->restore`, `client->restore->device`, `client->restore->client`를 쓴다.
  - 미확정: 각 필드의 마지막 참조 시점(처리기 하위 호출 전체를 읽지 않았다). 해제 뒤 참조는 코드상 도달 가능하나 미관측이다.

### 2.4 필수 확인 조건 (구현 전)

1. 비동기 작업이 모두 끝났거나 안전하게 분리됐다는 보장 없이 기록 객체와 클라이언트 구조체를 해제하지 않는다.
2. 진행 중인 네트워크 작업이 남은 상태에서 정책 보호를 약화시키지 않는다. 즉 `end()`는 비동기 작업을 기다리거나, 기다릴 수 없으면 훅을 남긴다.
3. 비동기 스레드도 정책 수명 안에 들어오게 한다(등록 또는 완료 대기).
4. 마지막 네트워크 접근 시점과 마지막 객체 참조 시점을 별개로 취급한다. 네트워크가 끝나도 참조가 남아 있으면 해제하지 않는다.

### 2.5 수정 후보 (선택하지 않음)

| 후보 | 변경 위치 | 정책 보호 | 객체 수명 | 비고 |
| --- | --- | --- | --- | --- |
| 비동기 스레드를 `restore_session`에 등록 | 벤더링 `restore.c`의 스레드 생성부 | 해결 가능 | 등록·해제 사이 경쟁이 남으면 불충분 | 벤더링 소스 변경 필요 |
| 완료 카운터 + 조건변수로 `end()`가 대기 | 같은 위치 + 호스트 | 해결 가능 | 해결 가능 | 교착 확인 필요(2.7) |
| 훅을 영구 유지 | 호스트만 | 부분 해결(해제 안 함) | **미해결** | 다음 세션의 `begin()`과의 관계 확인 필요 |
| 비동기 종류를 알리지 않음(동기만) | `restore.c` 5682~5688행 | 해당 비동기 경로의 수명 경쟁 제거 가능 | 해당 비동기 경로의 해제 경쟁 제거 가능 | 5종 비동기 데이터 요청에 한정(다른 비동기 경로·FDR 스레드는 해결 범위 밖). 프로토콜 호환성 및 복원 루프 블로킹 영향 미검증. 공유 연결(`DataPort` 없음)의 사용 순서 문제는 동기 전환으로 자동 해결되지 않으므로 별도 판단 |

공통 정책 수명의 수정은 TSS 통합과 분리해 별도로 승인받는다.

### 2.6 비동기 작업 수명 조사 결과 (소스 열람, 실행 관측 없음)

**비동기 처리기가 하는 일**

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| 처리 내용 | `restore_handle_data_request_msg`를 별도 스레드에서 호출한다. 비동기로 알린 종류는 `BasebandData`, `RecoveryOSASRImage`, `StreamedImageDecryptionKey`, `SystemImageData`(루트 파일시스템을 ASR로 전송, 장시간), `URLAsset` | `restore.c:5159`, `5682~5688` |
| 연결 | 메시지에 `DataPort`가 있으면 요청마다 **새 서비스 연결**을 연다(`client->restore->device`). 없으면 **복원 루프와 같은** `client->restore->client`(restored 연결)로 보낸다 | `restore.c:652~683` |
| 메시지 루프 의존 | `DataPort`가 있는 경우 별도 서비스 연결을 사용한다. 다만 장치 측 메시지 처리나 상태 전환에 대한 의존성은 확인되지 않았으므로, 복원 루프 종료 후 독립적으로 완료 가능한지는 미확정이다. 없는 경우 루프와 같은 연결에 쓰므로 루프와 동시에 송신한다(동시 접근의 안전성은 미확인) | 위와 같음 |
| 취소 확인 | 비동기 처리기 안에서 `FLAG_QUIT`를 읽는 곳이 없다. `FLAG_QUIT`를 확인하는 곳은 루프(5731행)와 일부 DFU·복구 대기 루프뿐이다 | `FLAG_QUIT` 전수 검색 |
| 블로킹 구간 | ASR 연결은 최대 30회 재시도(`asr.c:52`). URLAsset은 curl 120 s 제한. BasebandData는 libtatsu 재시도(최대 150 s, `sleep(2)` 포함) | 코드 확인 |

**`async_err`와 `flags`**

| 항목 | 내용 |
| --- | --- |
| `async_err` 접근 경로 | 전체 3곳: 비동기 스레드의 쓰기(`restore.c:5161`), 엔진 스레드의 읽기(5907~5908), 선언(`common.h:130`, 일반 `int`) |
| 판정 | 쓰기와 읽기가 서로 다른 스레드에서 동기화 없이 일어날 수 있다 → 데이터 경쟁 **가능성**(코드상). 더 큰 문제: 읽기는 루프 종료 뒤 한 번뿐이고 스레드 종료를 기다리지 않으므로, 쓰기가 읽기보다 늦으면 **오류가 전달되지 않는다** |
| `flags` | 비동기 스레드의 `client->flags \|= FLAG_QUIT`(5162행)와 루프의 같은 연산(5740행)이 읽기-수정-쓰기라 동시에 일어나면 한쪽이 사라질 수 있다 (코드상 가능성, 미관측) |
| 수정 후보의 한계 | 원자 변수나 뮤텍스는 오류 상태 전달의 동기화이지 스레드 종료 대기를 대체하지 않는다 |

**`begin()` / `end()`**

| 항목 | 내용 |
| --- | --- |
| `begin()` | 엔진 스레드 수가 0보다 크면 거부하고, 아니면 목록을 비우고 훅을 설치한다. 비동기 작업의 존재를 모른다 |
| `end()` | `hv_net_guard_uninstall()`. 엔진 스레드 수만 본다 |
| 결과 | 이전 세션의 비동기 작업이 남은 채 다음 `begin()`이 정책 목록을 지우고 새로 설치하는 것이 코드상 가능하다 (미관측) |

**생성 경로** (`restore.c:5783~5794`): `thread_new` 실패 시 오류를 기록하고 `args`를 해제하며 `err = -1`로 한다. 활성 작업 등록은 없으므로 "등록 취소"에 해당하는 코드는 없다. 생성 성공 뒤 `thread_detach`한다.

### 2.7 수명 모델 (검토용, 확정 아님)

세션의 종료 상태를 하나의 상태 전환으로 관리하는 모델이다.

| 상태 | 의미 | 동작 |
| --- | --- | --- |
| `ACTIVE` | 정상 | 비동기 작업 등록 허용 |
| `CLOSING` | 종료 시작 | **신규 등록 차단**, 취소 신호, 활성 작업이 0이 되기를 제한 시간까지 기다림 |
| `CLOSED` | 종료 확인 | 관련 작업이 끝나고 자원 정리가 확인된 뒤에만 도달. 정책 훅 해제, `client` 해제 |
| `QUIESCENCE_FAILED` | 대기 제한 도달, 작업 생존 또는 상태 미확인 | **참조 자원 전체와 정책 훅을 유지**하고 신규 세션을 차단 |

- 작업 등록과 스레드 생성은 한 번의 전환으로 다룬다: 등록 성공 → 생성 성공 / 생성 실패 시 등록 취소 / 생성 직후 부모가 종료 절차에 들어가도 작업 객체가 유효해야 한다. `active == 0`이 안전하다는 판단에는 "종료 상태 전환 뒤 신규 등록이 불가능하다"는 보장이 전제다.
- 종료 종류별 질문: 정상 종료(작업의 자연 완료를 기다릴 수 있는가) / 오류 종료(취소 신호와 연결 종료가 필요한가) / 취소 실패(제한 도달 시 객체와 정책을 어떻게 유지하는가).
- 타임아웃이 났다는 이유만으로 살아 있는 작업이 참조하는 `client`를 해제하지 않는다.
- `QUIESCENCE_FAILED`에서 작업이 뒤늦게 끝나도 즉시 차단을 풀지 않는다. 서비스 연결, 전역 정책, 세션 기록이 일관된지 확인한 뒤 재평가한다.
- 취소 실패와 자원 해제 실패는 다르다: 취소 후 종료 확인 → 정상 정리 / 제한 도달·작업 생존 확인 → 유지·차단 / 제한 도달·상태 미확인 → 유지·차단 / 뒤늦은 종료 확인 → 재평가.
- **유지 대상은 `client` 하나가 아니다.** 비동기 작업이 참조하는 `client->restore`, 장치 핸들, restored 연결, 서비스 연결, FDR 스레드가 쓰는 연결까지 포함해야 한다. 서비스 연결이 먼저 닫히면 비동기 스레드가 무효한 연결을 쓸 수 있다.
- 다른 세션이 전역 정책을 바꾸면 남은 작업의 보호 조건이 달라지므로, 안전성이 입증되기 전에는 신규 세션 차단이 기본 후보다.

**완료 대기를 넣기 전에 확인할 관계**

| 관계 | 현재 확인 상태 |
| --- | --- |
| 비동기 작업 → 메시지 루프 | `DataPort` 있는 경우 별도 서비스 연결을 쓰나 장치 측 의존성은 미확인이므로 루프 종료 후 독립 완료 가능 여부는 미확정. 없는 경우 루프와 연결 공유(미확인) |
| 메시지 루프 → 비동기 작업 | 루프가 종료된 뒤 대기하므로 대기 중 루프가 처리할 메시지는 없음. 단 루프 종료 전에 대기를 넣으면 교착 가능(미검증) |
| 비동기 작업 → 서비스 연결 | 연결을 닫으면 블로킹 읽기가 깨어나는지 미확인 |
| 취소 요청 → 작업 종료 | 처리기에 취소 확인이 없다. curl 읽기·연결 대기는 200 ms 단위로 취소 플래그를 확인하지만, `getaddrinfo`, libtatsu 재시도 대기, ASR 연결 재시도, 장치 응답 대기는 취소되지 않는다 |

완료 대기 제한 시간은 개별 curl 취소 확인 주기가 아니라 작업 전체의 종료 가능성(위 블로킹 구간)을 기준으로 정해야 한다. 이 모델이 가능한지는 서비스 연결 닫기와 취소 전달 경로 확인 뒤에 판단한다.

### 2.8 서비스 연결·취소 경로 조사 결과 (소스 열람, 실행 관측 없음)

결과는 코드로 확인 / 코드상 위험 / 미확정으로 나눈다.

**코드로 확인**

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| 연결 생성 | `DataPort` 있음: 요청마다 `property_list_service_client_new`로 새 연결(`SERVICE_TYPE_PLIST`). 없음: `client->restore->client`를 그대로 가리키는 래퍼(`SERVICE_TYPE_RESTORED`) | `restore.c:652~683` |
| 연결 해제 | 래퍼 해제는 PLIST 형만 연결을 닫고, RESTORED 형은 아무것도 닫지 않는다(공유 연결 소유권은 `restore_client_free`) | `restore.c:719~735` |
| ASR 연결 | `restore_send_filesystem`은 `client->restore->device`로 ASR 연결을 직접 열고 처리기 안에서 닫는다(`client->restore->client`는 쓰지 않음) | `restore.c:1056`, `asr.c:20~` |
| 수신 대기 한도 | `usbmuxd_recv`는 호출당 5 s, 소켓 수신 기본 20 s이며 시간 초과 시 오류를 돌려준다 → **호출 단위 블로킹은 한정적** | `libusbmuxd.c:1626`, `socket.c:73` |
| 전체 작업 한도 | 호출 단위 한도가 있어도 작업 전체의 종료 한도는 아니다: ASR 연결 재시도 30회 × `sleep(2)`, 송신 무진전 허용 600 s(`asr_send_buffer`), URLAsset curl 120 s, libtatsu 재시도 | `asr.c:25~`, `asr.c:~190`, 앞선 조사 |
| `restore_client_free` | `restored_client_free`, `idevice_free`, `bbtss` 해제, `client->restore` 해제를 한 번에 수행하고 대기 장치가 없다 | `restore.c:142~160` |
| 재연결 해제 | `restore_wait_for_reconnect`가 `client->restore->client/device`를 해제하지만 호출은 리버스 프록시 설정 단계(5530행, 메시지 루프 이전)이므로 비동기 작업과 겹치지 않는 것으로 읽힌다(빌드에서 `HAVE_REVERSE_PROXY` 사용 여부는 미확인) | `restore.c:5380~5403`, `5530` |
| 스레드 생성 실패 | `thread_new` 실패 시 `args`만 해제하고 `args->message`(복사본)는 해제하지 않는다 → 누수(작은 결함, 수명 문제와 별개) | `restore.c:5780~5788` |

**코드상 위험** (도달 가능하나 미관측)

| 항목 | 내용 |
| --- | --- |
| 연결 닫기 방식 | `usbmuxd_disconnect`는 `close(fd)`만 호출한다(`shutdown` 없음). 다른 스레드가 같은 fd에서 대기 중일 때 `close`가 대기를 깨우는 것은 보장되지 않고, 닫힌 fd 번호가 재사용되면 다른 연결에 잘못 쓰일 위험도 있다. 따라서 "연결을 닫으면 작업이 끝난다"는 가정은 쓰지 않는다 |
| 공유 연결 동시 사용 | `DataPort` 없는 비동기 요청은 `restored_send`를 루프와 동시에 호출할 수 있고, 연결 객체에 대한 잠금은 찾지 못했다 |
| `client` 해제 후 참조 | 비동기 처리기는 `client->restore->device`, `client->restore->build_identity`, `client->ipsw`, `client->filesystem`을 읽는다. `restore_client_free`와 `idevicerestore_client_free` 뒤에 실행 중이면 해제된 메모리를 읽는다 |
| 취소 | 처리기 안에 `FLAG_QUIT` 확인이 없으므로 취소 요청은 작업에 전달되지 않는다(curl 읽기 대기만 별도 플래그로 200 ms 단위 확인) |

**마지막 참조 객체와 해제 순서** (확인된 것만)

| 객체 | 비동기 처리기의 사용 | 해제 지점 | 해제 전 대기 |
| --- | --- | --- | --- |
| `client` (엔진 소유) | 전 구간 | `idevicerestore_client_free` (`install.c:91`) | 없음 |
| `client->restore` | 장치 핸들, 빌드 정보, 공유 연결 | `restore_client_free` (`restore.c:5923`) | 없음 |
| `client->restore->client` | `DataPort` 없는 요청의 송신 | 같은 곳 | 없음 |
| 서비스 연결(PLIST) | 처리기 자신이 열고 닫음 | 처리기 안 | 해당 없음 |
| ASR 연결 | 처리기 자신이 열고 닫음 | 처리기 안 | 해당 없음 |
| `message` 복사본 | 처리기가 해제 | 처리기 끝 | 해당 없음 |

**미확정** (장치 응답 또는 실행 시험이 필요)
- 장치 측이 비동기 요청의 응답을 기다리는 동안 다른 메시지나 상태 전환을 요구하는지.
- 루프 종료 후 `DataPort` 없는 요청이 공유 연결에서 반환하는지.
- `close`가 다른 스레드의 대기를 깨우는지(플랫폼 의존).
- 가짜 장치 시험이 필요한 항목: 비동기 요청 중 루프 종료, 공유 연결 동시 송신, 연결 종료 후 대기 반환.

**설계에 미치는 영향**: 소스는 작업 단위의 종료나 취소를 보장하지 않는다. 따라서 완료 대기는 "대기 한도 + 한도 도달 시 참조 자원 유지(`QUIESCENCE_FAILED`)"를 전제로만 설계할 수 있고, "연결을 닫아 종료시킨다"를 전제로 삼을 수 없다.

## 3. TSS 통합

### 3.1 호출 경계 (코드 확인)

`tss_request_send(request, client->tss_url)` 호출식은 15곳이다: `idevicerestore.c` 5곳(816, 2574, 2668, 2757, 2842행), `restore.c` 10곳(2351, 2731, 2827, 2937, 3043, 3189, 3301, 3363, 3509, 3693행). 모두 두 번역 단위에 있다. 전체 15곳이 NULL을 반환하면 호출부가 `-1` 또는 `NULL`로 처리한다. 상위 전파는 다음과 같다.

- `idevicerestore.c` 5곳: `-1`로 `idevicerestore_start`까지 올라가 중단한다.
- `restore.c` 10곳: 펌웨어·베이스밴드 처리기 → `restore_handle_data_request_msg`의 `-1` → 루프의 `err < 0` → `FLAG_QUIT`. 비동기 경로는 `async_err`와 `FLAG_QUIT`.
- 예외: `FLAG_IGNORE_ERRORS`(명령행 옵션으로만 켜짐, 현재 세션 플래그에는 없음), 오류 뒤 메시지 하나가 더 처리됨.

| 조건 | 판정 |
| --- | --- |
| 전송 통제 | PC 시험 범위에서 충족 (허용 목록이 비어 있어 모든 TSS가 정책에서 막힘) |
| 결과 관측 | 미구현 |
| 최종 흐름 중단 | 현재 플래그 구성에서 코드상 충족 |
| 실패 직후 추가 작업 차단 | 미검증 (오류 뒤 메시지 하나가 더 처리됨) |

정지점 A는 `idevicerestore.c:1163`에서 모든 `get_*_tss_response` 호출 앞에 반환한다. 예외 하나: 816행은 `MODE_PORTDFU`(PID `0xf014`) 블록 안이라 정지점 A보다 앞에 있다. 가상 장치의 실제 PID는 소스에서 찾지 못했다(미확정). 실기기 실행(APK 72·73)은 TSS 0건이었다(관측, 코드 보증 아님).

### 3.2 호출을 분류기에 연결하는 후보

`hv_tss_send(request, url, HvTssResult *)`는 인자가 세 개이고 기존 호출은 두 개다. **이름만 바꾸는 매크로는 성립하지 않는다.** 두 인자 어댑터가 필요하다.

| 후보 | 호출 연결 | 확인할 것 |
| --- | --- | --- |
| 공통 헤더 매크로 | `common.h`의 함수형 매크로 | idevicerestore의 `common.h`는 약 20개 번역 단위가 포함한다. libtatsu에는 이름이 같은 별개의 `common.h`가 있어 `tss.c`에는 전파되지 않는다. `tss.h` 포함 뒤에 정의해야 한다 |
| 호출부 전용 헤더 | 두 번역 단위의 맨 끝에서 함수형 매크로 | 정확히 두 파일에만 적용되는지, 선언 가시성, 원래 함수 재귀 방지 |
| 명시적 래퍼 | 15개 호출식 수정 | 누락 없음, 오류 전달 |
| 링크 가로채기 (`--wrap`) | 링커 심볼 치환 | Android 링크에서 적용되는지(미검증), 빌드 스크립트별 옵션 |

우열은 정하지 않는다. 선택은 2.4의 조건과 3.3의 문맥 전달 방식이 정해진 뒤에 한다.

### 3.3 세션 문맥 전달 (선택하지 않음)

어댑터는 인자에 세션이 없으므로 어떻게든 기록 객체를 찾아야 한다.

| 방식 | 장점 | 위험 |
| --- | --- | --- |
| 스레드별 세션 문맥 | 다른 세션과 분리 | 비동기 스레드 생성 지점(벤더링)에서 문맥을 넘겨야 함 |
| 전역 활성 세션 | 두 인자 호출 유지 | 세션이 하나여도 종료와 비동기 작업이 겹치면 해제된 객체를 가리킬 수 있음 |
| 호출부 인자 | 소유 관계 명확 | 15개 호출식 변경 |

결정 순서: ① 비동기 작업의 종료 보장 → ② 세션 객체의 소유권과 참조 수명 → ③ 문맥 전달 방식.

### 3.4 결과 기록 구조 (설계 결정)

논리적 TSS 요청 1건과 libtatsu 내부 시도 여러 건을 구분한다. 기록은 논리적 요청 단위다.

| 필드 | 의미 |
| --- | --- |
| `seq` | 논리적 요청 시작 시 부여하는 단조 증가 번호 |
| `completion_seq` | 요청 결과가 기록기에 확정된 순서. 네트워크 완료 시각이 아니다 |
| `first_failure` | 실패 중 가장 작은 `completion_seq` |
| `last_failure` | 실패 중 가장 큰 `completion_seq` |
| `total` | 기록기에 접수된 논리적 요청 수 |
| `stored` | 배열에 보존된 결과 수 |
| `overflow` | 보존 한도 초과 여부. `total - stored`로 누락 규모를 안다 |

- 보존 개수는 고정 크기로 한다. 넘친 뒤에도 최초·최종 실패 요약은 갱신한다.
- 각 항목은 `HvTssResult`의 필드(코드, 시도 수, HTTP, TSS 상태, curl 코드, 거부·시도 주소 수 등)만 담는다. 요청 본문, 응답 본문, ECID, nonce, 티켓은 담지 않는다.
- 필드 관측 범위는 `stop-b-design.md` 5.6절과 같다(`attempts`·`tss_status`는 libtatsu 진단, 나머지는 마지막 시도).
- 저장 위치, 한도 값, 초기화 시점, 읽는 위치는 2.4의 수명 요구조건을 만족하는 방식이 정해진 뒤에 정한다. 뮤텍스만으로는 해제 경쟁을 막지 못한다.

### 3.5 검증 계획

- PC 단위시험: 기록기(순서, `total`·`stored`·`overflow`, 최초·최종 실패, 동시 요청).
- 비동기 종료 경합 시험: 지연시킨 비동기 작업이 있는 동안 `end()`와 기록 해제가 일어나는 순서를 가짜 장치로 재현. 이 시험은 2.4의 조건이 구현된 뒤에 의미가 있다.
- 호출 연결: 선택한 방식이 15개 호출을 모두 덮는지 `rg`로 대조하고, 전용 헤더 방식이면 두 번역 단위에만 적용되는지 확인.
- Android: NDK 링크와 전처리 조건이 PC와 같은지 CI에서 빌드 확인(`--wrap`을 쓸 경우 포함).
- 기존 정지점 A 회귀: 정책, FDR/세션, 사전점검, 디스크 정책, TSS 프로브, 다운로드, 출하 검사를 전부 다시 실행하고, 변경 전후를 구분해서 보고.

## 4. 미확정 사항

- 가상 장치가 보고하는 PID(`MODE_PORTDFU` 여부).
- 펌웨어 요청이 동기로 오는지 비동기로 오는지(비동기 종류 목록에는 펌웨어 갱신 데이터가 없다. `BasebandData`만 TSS를 부른다).
- Android 네이티브 링크에서 `--wrap`이 적용되는지.
- `restored`가 오류 직후 추가 메시지로 장치 전송을 요구하는 실제 시나리오.
- 비동기 스레드가 `client`의 각 필드를 마지막으로 참조하는 시점.
- `DataPort`가 없는 비동기 요청이 복원 루프와 같은 연결에 동시에 쓸 때의 안전성.
- 서비스 연결을 닫으면 블로킹 중인 비동기 작업이 깨어나는지.
- 다음 세션 차단을 `begin()`의 어디에 넣을지.

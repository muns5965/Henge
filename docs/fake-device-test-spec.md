# 가짜 장치 시험 명세 (비동기 작업 수명)

상태: 명세 초안. 시험 구현은 별도 승인 대상이다.
관련: `docs/restore-lifetime-integrated-design.md`(통합 설계, 제약 C1~C12와 추적표 8절), `docs/async-lifetime-design.md`(요구 R1~R9, P10 판정표), `docs/tss-integration-design.md` 2.6~2.8절.

이 명세는 구현 구조를 선결정하지 않는다. 정의하는 것은 세 가지뿐이다: **어떤 실행 순서를 재현할 것인가 / 어떤 상태와 자원을 관측할 것인가 / 어떤 결과를 실패로 판정할 것인가.** 등록·완료 통지·취소·종료 대기의 인터페이스는 수명 관리 상세 설계에서 정한다.

## 1. 한계 (결론 해석 규칙)

- 가짜 장치는 제어 가능한 연결이다. 실제 Apple 장치의 메시지 순서와 프로토콜 동작은 검증하지 못한다.
- 통과는 "시험한 실행 순서에서 위반이 없었다"는 뜻이다. 모든 스레드 실행 순서에서 안전하다는 결론을 내리지 않는다.
- 시험으로 입증할 수 없는 것: 등록 차단의 원자성, 객체 해제 순서의 일반 보장, 정책 훅 수명의 일반 보장. 이는 소스의 동기화 구조와 함께 검증한다.
- 실제 Apple 서버·실제 장치·RecoveryOS·루트 파일시스템 전송은 사용하지 않는다. 연결은 루프백 또는 소켓쌍이며 시험 전용 빌드에서만 켠다(`check-no-test-flags.sh` 대상에 포함).

## 2. 시험 환경 개요

- 가짜 restored: 시험이 지정한 순서로 plist 메시지(`AsyncDataRequestMsg`, `DataRequestMsg`, `ProgressMsg` 등)를 보내고, 수신한 응답을 기록한다.
- 가짜 `DataPort` 서비스: 지정한 지연·정지·끊김을 낸다.
- 제어점: 응답 지연, 응답 정지(무한 대기), 연결 끊김, 메시지 사이 간격, 처리기 진입 시점 통지.
- 관측점: 활성 작업 수, 세션 상태, 정책 훅 설치 여부, 객체 해제 여부(해제 감시용 표식 또는 소멸 알림), 가짜 장치가 받은 메시지 목록, 반환 오류값, 스레드 생존 여부.
- 동기화 취약 지점 탐지는 스레드 새니타이저(ThreadSanitizer)와 주소 새니타이저(AddressSanitizer) 빌드를 병행한다(PC에서만; Android 네이티브는 미검증).

## 3. 시험 항목

각 항목: **재현 순서 / 관측 / 실패 판정 / 확인 대상 요구**.

### T1a 등록 검사와 `CLOSING` 전환의 경합
- 재현: 비동기 요청의 등록 진입 지점과 종료 상태 전환의 실행 순서를 제어한다. 이를 위한 **시험 전용 후크**가 필요하며(장치 메시지 송신만으로는 재현되지 않을 수 있다), 시험 전용 빌드에만 존재해야 한다(`check-no-test-flags.sh` 대상). 스레드 생성 직전에 지연만 넣는 방식은 등록 검사와 상태 전환 사이의 순서를 제어하지 못하므로 불충분하다.
- 관측: **등록 승인 시점, 활성 작업 수 증가 시점, `CLOSING` 전환 시점의 순서**, 스레드 생성 시점, 활성 작업 수, 엔진이 받은 오류값, 완료 통지와 활성 수 감소.
- 정상으로 허용: `ACTIVE`에서 등록이 승인되고 활성 수가 증가한 뒤 다른 스레드가 `CLOSING`으로 전환하고, 승인된 작업의 스레드 생성·완료 통지·활성 수 감소가 그 뒤에 일어나는 순서. 이미 승인된 작업은 `CLOSING`에서도 완료할 수 있어야 한다.
- 실패: (1) `CLOSING` 전환 **이후에** 등록이 승인됨, (2) 거부 사실이 엔진에 전달되지 않음, (3) 등록 승인과 활성 수 증가 사이에 틈이 있어 종료 스레드가 활성 수 0으로 판단하고 객체를 해제함(등록 승인과 활성 수 증가는 하나의 원자적 전환이어야 한다), (4) 활성 수가 어긋남.
- 대상: R1, R2, R3. 시험은 원자성을 입증하지 못한다(시험한 순서에서의 관측).

### T1b 종료 후 장치 메시지 도착
- 재현: 복원 루프가 종료된 뒤 가짜 장치가 `AsyncDataRequestMsg`를 보낸다.
- 관측: 메시지 수신 여부, 장치 측 대기 상태, 종료 프로토콜에 미치는 영향.
- 판정 없음(기록): 루프가 끝났으면 메시지가 수신되지 않을 수 있으므로 이를 등록 거부 기능의 실패로 판정하지 않는다. 장치가 응답을 기다리는지와 종료 프로토콜 영향은 [미확정].
- 대상: R2의 프로토콜 측면(미확정 해소용).

### T2 오류 보존과 실패 전파 (P10)
두 조건을 **독립된 판정**으로 둔다. 서로 대체하지 않는다.

- 재현: 비동기가 아닌 처리기(예: 데이터 요청 처리기)가 `-1`을 돌려주게 한 직후, 가짜 장치가 다음을 보낸다.
  - (a) 아무 메시지도 보내지 않아 수신이 **시간 초과**(`RESTORE_E_RECEIVE_TIMEOUT`)가 됨: `err`를 바꾸지 않고 `continue`하므로 최초 오류가 유지되어야 함
  - (b) `err`를 0으로 돌려주는 메시지(예: `ProgressMsg`, `RestoreAttestation`)
  - (c) **대조군**: `MsgType` 없음, 비문자열, 또는 어느 분기에도 맞지 않는 문자열 타입 (코드상 `err` 미변경)
  - (d) **시간 초과가 아닌** 수신 오류: `HAVE_RESTORE_E_RECEIVE_TIMEOUT`가 켜진 빌드에서만 존재하는 분기이며 `err = -11`로 대체하고 `break`한다. 이 매크로가 꺼진 빌드에서는 모든 수신 실패가 `continue`가 되어 최초 오류가 유지되므로 (d)는 (a)와 같은 결과가 된다. (a)와 (d)는 입력이 겹치지 않게 구분한다
  - 빌드 조건: 현재 `third_party/restore_config/config.h:13`이 `HAVE_RESTORE_E_RECEIVE_TIMEOUT 1`을 정의하고, 이 파일을 쓰는 빌드(`-DHAVE_CONFIG_H -Ithird_party/restore_config`; `Makefile:42`, `tools/restore-android-check.sh` 등)에서 (d)의 분기가 존재한다. 시험 결과에는 **적용된 빌드 설정(매크로 정의 여부와 포함된 config.h 경로)을 함께 기록**한다. 번역 단위에 실제로 전달됐는지는 시험 빌드에서 확인한다(앱 빌드 명령은 이번에 확인하지 않음)
- 관측: 최초 오류 발생 여부와 코드, 추가 메시지 처리 여부, 최초 오류가 보존되는 위치, `restore_device()` 최종 반환값, 호출자(`idevicerestore_start`)의 최종 반환값과 `DONE`/실패 보고, 최종 결과가 최초 오류를 반영하는지, 메시지 객체 해제.
- 판정 T2-보존: 최초 오류의 발생 사실과 원인(처리기·메시지 종류·오류 코드)을 식별할 수 있는가. (d)처럼 최종 결과가 실패로 남아도 최초 원인이 `-11`로 대체되면 이 판정은 실패다.
- 판정 T2-전파: 최초 오류가 난 실행에서 최종 결과가 성공으로 보고되지 않는가.
- 실패: 한 조건이라도 충족하지 못함. 최종 반환값이 음수라는 사실만으로 통과시키지 않는다(다른 오류가 우연히 남은 경우일 수 있음). (b)에서 최종 성공이 보고되면 P10의 성공 처리 경로가 관측으로 확정된다.
- 기준선: 현재 코드의 동작을 먼저 기록한다. (c)가 실제로 `err`를 유지하는지는 이 시험으로 확인한다(코드 읽기상으로는 유지).
- 대상: R9.

### T3 생성 실패 시 등록 취소
- 재현: 스레드 생성 실패를 주입(시험 전용 후크)한다.
- 관측: 활성 작업 수, 오류값, 작업 객체의 해제 여부(`args->message` 포함).
- 실패: 활성 수가 0으로 돌아오지 않음, 객체 누수.
- 대상: R1.

### T4 공유 연결 동시 송신
- 재현: `DataPort` 없는 비동기 요청 처리 중 루프도 같은 연결로 송신하도록 가짜 장치가 두 종류 메시지를 겹쳐 보낸다. 송신 크기를 크게(소켓 버퍼를 넘는 크기) 해서 부분 쓰기를 유도한다.
- 관측: 가짜 장치가 받은 바이트열이 plist 단위로 온전한지, 메시지 순서.
- 실패: plist 파싱 실패, 메시지 중간에 다른 메시지가 끼어듦.
- 대상: R7. 통과해도 일반 안전성은 주장하지 않는다.

### T5 장치 응답 정지와 대기 한도
- 재현: 비동기 작업이 가짜 서비스의 응답을 기다리는 중 서비스가 응답을 멈춘다. 종료를 시작하고 대기 한도까지 둔다.
- 관측: 한도 도달 시 상태, 훅 설치 여부, 객체 해제 여부, 스레드 생존, 신규 세션 시작 결과.
- 실패: 한도 도달 후 `client` 등 참조 객체가 해제됨 / 훅이 제거됨 / 신규 세션이 시작됨.
- 대상: R5, R6.

### T6 지연 완료 후 상태 변화
- 재현: T5 이후 정지했던 서비스가 응답하고 작업이 뒤늦게 끝난다.
- 관측: 상태 전이, 활성 수, 신규 세션 시작 가능 여부.
- 실패: 일관성 확인 없이 자동으로 정상 상태 복귀하고 신규 세션이 시작됨(기본안은 자동 복귀 없음).
- 대상: R5.

### T7 취소 신호 전달 범위
- 재현: 작업 종류별(ASR 연결 대기, URLAsset 다운로드, BasebandData 요청)로 블로킹 상태를 만들고 취소 신호를 보낸다.
- 관측: 종료까지 걸린 시간, 종료 여부.
- 기록(판정 아님): 취소에 반응하는 종류와 반응하지 않는 종류의 구분. 실패 기준이 아니라 대기 한도 설계의 입력이다.
- 대상: R4, R5, D2.

### T8 연결 닫기와 대기 해제 (P8)
- 재현: 다른 스레드가 수신 대기 중인 연결을 `close`(shutdown 없음)로 닫는다. 비교군으로 `shutdown` 후 `close`. **시험 프로세스와 연결을 격리**해, 오래된 작업이 재사용된 fd 번호로 새 연결(또는 시험 도구 자신의 fd)을 잘못 조작하지 않게 한다.
- 관측: 대기 스레드의 반환 시점과 오류값, 닫힌 fd 번호 재사용 시 오사용 여부.
- 기록: 플랫폼별 결과(PC Linux에서의 결과가 Android와 같다고 가정하지 않음).
- 대상: 미확정 해소(P8).

### T9 정상 종료 순서
- 재현: 비동기 작업이 자연 완료되는 정상 종료.
- 관측: 객체 해제와 훅 제거가 작업 완료 뒤에 일어나는지(순서 기록).
- 실패: 작업 완료 전 해제/제거.
- 대상: R4, R6.

### T10 오류·종료 상태 동기화 (P6)
- 재현: 비동기 작업의 오류 기록과 루프의 종료 판정이 겹치도록 타이밍을 조정하고 반복 실행한다. ThreadSanitizer 병행.
- 관측: 데이터 경쟁 보고, 최종 오류값.
- 실패: 경쟁 보고 또는 오류 유실.
- 대상: R9. 반복 실행에서 미검출이어도 경쟁이 없다는 결론은 내리지 않는다.

### T11 세션 간 경계
- 재현: QUIESCENCE_FAILED 이후 `begin()`을 호출한다.
- 관측: 거부 여부, 정책 목록·훅 상태 불변 여부.
- 실패: `begin()`이 성공해 목록이 비워지거나 훅이 재설치됨.
- 대상: R5, 정책 보호.

### T12 열린 프록시 연결이 있는 상태에서의 종료 (D8, P15)
- 재현: 리버스 프록시의 연결 스레드가 장치 연결을 연 채 프록시 루프에 있는 상태에서 종료를 시작한다. 가짜 장치는 연결을 닫지 않는다.
- 관측: `reverse_proxy_client_free`의 반환 여부와 걸린 시간, 레지스트리 상태(`CLOSED`/`QUIESCENCE_FAILED`), 객체·훅 유지 여부.
- 실패: 대기 한도 도달 뒤 `client` 해제 또는 훅 제거가 일어남 / 한도 없이 무기한 블로킹(현재 코드에서의 기준선 기록 대상).
- 대상: C6, C7.

### T13 연달아 오는 연결 요청 (P13)
- 재현: 제어 스레드에 연결 요청을 이전 연결 스레드가 끝나기 전에 연속으로 보낸다.
- 관측: 연결 스레드 수, join된 스레드 수, `reverse_proxy_client_free` 뒤 남은 스레드, 해제 후 접근(AddressSanitizer).
- 실패: 남은 스레드가 있거나 해제된 `client`를 참조.
- 대상: C7(D8). 현재 코드는 기준선 기록 대상.

### T14 취소 요청 수락과 `CLOSED` 전환의 경합 (C13, C17)

- 시험 전용 후크로 (i) 취소 수락 직전, (ii) `CLOSED` 판정 직전에 한쪽을 멈추는 두 순서를 만든다.
- 기록: 먼저 수락되면 진행 중 취소 카운터>0이라 `CLOSED`가 보류되는가, 먼저 `CLOSED`면 취소가 거부되고 거부 사실만 기록되며 새 취소 작업이 생기지 않는가.
- 엔진·감시의 동시 취소 요청이 하나의 종료 절차로 합쳐지는가(실행 횟수 1).
- 취소 개시가 실패하도록 주입(후크)한 경우 "취소 완료"로 간주되지 않고 실패가 기록·재시도·수렴되는가. 생성 실패 주입은 예약→생성→실패 기록 순서와 재시도 가능 구분(C2)을 확인.
- 한계: 원자성 자체는 시험으로 입증 불가. 순서 두 가지에서 위반이 관측되지 않았음만 통과.

### T15 참조 반환 한도와 fd 유지 (C14)

- 취소 측이 `shutdown` 중 참조를 오래 쥐는 상황을 후크로 만든다.
- 통과: 소유자가 한도 초과 시 fd를 닫지 않고 실패만 기록하며, 이후 늦게 반환돼도 상태가 `QUIESCENCE_FAILED`에서 복귀하지 않는다. 한도 초과 기록이 있으면 카운터 0이어도 `CLOSED`가 되지 않는다.
- 실패: 참조 보유 중 `close`가 일어남(fd 재사용 가능), 또는 소유자가 직접 상태를 전환.

### T16 `IDLE` 격리와 세션 간 전역 상태 (C15, S8)

- 엔진 등록 해제 직후 `end()` 이전에 `begin()`을 시도 → 거부되는가.
- 이전 세션의 마지막 진행 콜백이 다음 세션의 `g_progress`/`g_progress_user`를 읽지 않는가(시작 시 복사한 값 사용).
- 객체 정리 실패·재시도 금지 기록이 있으면 `IDLE`이 되지 않는가.
- 조기 반환 경로(`client_new` 실패, 스레드 생성 실패)에서 `end()`·`g_result`가 정리되어 이후 시작이 막히지 않는가(기준선 기록 후 변경 후 비교).

### T17 루프 미종료와 감시 (C11, C16, S6)

- 가짜 장치가 응답하지 않아 루프가 탈출하지 못하는 상황에서 종료 트리거 후 감시가 한도 뒤 `QUIESCENCE_FAILED(engine_not_exited)`를 확정하는가.
- 감시와 엔진의 `CLOSED` 선착순: 먼저 `CLOSED`면 감시는 상태를 바꾸지 않는가, 확정 뒤 엔진이 탈출하면 7b를 따라 객체를 해제하지 않는가.
- 호스트·감시가 `client`에 접근하지 않고 레지스트리 플래그만 쓰는가(코드 검토 + 새니타이저).
- `global_quit_flag`만 설정했을 때 루프가 반응하지 않음을 기준선으로 기록.

### T18 실패 기록과 `CLOSED` 경쟁, 완료 통지 순서 (C4)

- 작업이 실패 기록 전에 완료 통지를 하지 않는가(후크로 기록 직전에 멈춤): 멈춘 동안 카운터>0이라 `CLOSED` 불가여야 한다.
- 기록 후 감소가 한 임계구역임을 확인(감소는 되었는데 실패 기록이 없는 관측 시점이 없는가).
- `CLOSED` 이후 도착한 취소 요청은 거부 기록만 남고, 객체 정리 실패는 정리 진단으로 남아 `IDLE`을 막는가.

### T19 반환 계약 (C18, S9)

- 7b(`QUIESCENCE_FAILED`)를 만든 뒤: `restore_device`가 음수를 돌려주는가, `idevicerestore_start`가 `build_identity`를 해제하지 않고 반환하는가, `install.c`가 레지스트리 조회로 `idevicerestore_client_free`와 `end()`를 생략하는가, `g_result`와 앱 보고는 실행되는가.
- 대조군: 일반 복원 실패(`CLOSED`)에서는 해제 허용 조회가 참이고 정상 해제·`end()`·`IDLE`로 가는가.
- 반환값이 0인데 레지스트리가 `QUIESCENCE_FAILED`인 주입 경우에도 실패로 처리되고 해제가 생략되는가.
- 실패: 7b 뒤 어떤 객체라도 해제되거나 반환값만으로 분기.

### T20 취소 스레드 생성 실패와 중복 요청자 (C2, C17)

- 예약 직후 스레드 생성 실패를 주입: 실패 기록과 예약 해제가 한 임계구역인가, 대기 중인 중복 요청자가 종결 통지(생성 실패 코드)로 깨어나는가, 재시도가 한 요청자에게만 허용되는가, 생성 실패가 "취소 완료"로 취급되지 않는가.
- 예약·실행 중인 취소가 있을 때 두 번째 요청이 스레드를 만들지 않고 종결을 기다리는가. 실행 완료와 취소 성공이 따로 판정되는가.
- 마감을 넘긴 취소 스레드의 카운터를 강제로 0으로 만들지 않고 `QUIESCENCE_FAILED`로 수렴하는가.

### T21 마감 시계 (C19, V12)

- 벽시계를 앞뒤로 조정해도 유예·취소·정리 마감이 단조 시계로 유지되는가(PC 한정).
- 조건변수가 `CLOCK_MONOTONIC`으로 초기화되는지 확인. Android 지원 여부는 기록(미검증으로 남김).

### T22 유예 단계의 프록시 동작 (D8, V9)

- 정상 종료 유예 중: 신규 프록시 연결 등록이 `CLOSING` 상태 판정으로 거부되는가(별도 플래그 검사 없이), 기존 연결에는 `shutdown`이 호출되지 않는가.
- 유예 한도 이후 또는 오류 종료: 기존 연결 `shutdown`이 취소 단계에서만 호출되는가.
- `CLOSING` 전환과 신규 연결 등록의 경합을 후크로 두 순서 모두 확인(원자성 입증 아님). 장치 프로토콜 영향은 가짜 장치로 확인 불가(미검증).

### T23 정리 지연·실패와 최종 결과 단일 확정 (C9, C15, C19)

- 정리 호출을 지연시켜 `CLEANUP_DELAYED`(중간)가 나오고 이후 정리 완료 시 최종 결과가 한 번만 확정되는가.
- 정리 마감 초과 → `CLEANUP_FAILED` 확정; 이후 정리가 늦게 반환해도 같은 세대에서 `IDLE`로 가지 않고 객체·훅이 강제 해제되지 않는가. 감시가 `CLOSED` 이후에도 관찰을 계속했는가.
- 4.7 표의 조합 확인: 일반 복원 실패 + 정리 완료 → `RESTORE_FAILED`, `IDLE`, 재시도 허용 / 정리 실패 확정 → 재시도 금지. 정리 실패가 최초 오류 기록을 지우지 않는가.
- 최종 결과 중복 확정 시도가 거부·기록되는가.

### T24 세대 번호 (C15)

- 이전 세대의 감시·취소·진행 콜백·실패 기록 통지가 다음 세대의 상태·결과를 바꾸지 못하고 진단으로만 남는가.
- 한계: 세대 번호는 기록 오염을 막을 뿐 객체 수명 보호가 아니다(수명은 T5, T9, 새니타이저).

## 4. 판정 구분

| 구분 | 의미 |
| --- | --- |
| 통과 | 시험한 순서에서 위반 관측 없음 (일반 안전성 아님) |
| 실패 | 실패 판정 조건 관측 |
| 기록 | 판정 없이 값을 수집 (T7, T8) |
| 시험 불가 | 시험으로 입증할 수 없고 소스 구조로 보장해야 함 |

## 5. 현재 코드에 대한 기대 (관측 전 가설, 결과로 쓰지 않음)

- T2(b), T3, T5, T11은 현재 코드에서 실패할 수 있는 항목이다. 결과를 보기 전에는 결함 확정으로 쓰지 않는다.
- 시험은 설계 변경 전 기준선을 먼저 기록한 뒤 변경 후 회귀로 쓴다.

- T14~T18은 통합 설계 v2(C13~C17), T19~T24는 v2.1(C15, C17~C19)의 신규 항목이다. 원자성·해제 순서·훅 수명은 시험으로 입증되지 않으며 소스 구조(추적표 8절)로 보장해야 한다.
- 열린 프록시 연결 거부(V9)와 `shutdown` 효과(V5)의 장치·Android 측 결과는 가짜 장치로 확인할 수 없고 미검증으로 남는다.

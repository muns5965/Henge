# 정지점 B 설계: TSS 준비·개인화 검증, 실패 분류, 가짜 TSS 서버 시험 계약

상태 표기는 `docs/restore-architecture.md` 0절과 같다: 검증 완료 / 코드 확인 / 설계 결정 / 미검증 / 별도 승인 필요.

## 1. 목적과 범위

**목적**: 복원 엔진이 "TSS를 준비하고 개인화 요청을 만들고 응답을 처리하는" 단계를 PC에서 끝까지 시험할 수 있게 하고, 실패가 어느 층에서 났는지 구별할 수 있게 한다.

| 구분 | 이번 문서의 범위 |
| --- | --- |
| 포함 | 요청 목적지 정책, TLS 검증 범위, 요청·응답 계약, 크기·시간·재시도 제한, 실패 분류 코드, 가짜 TSS 서버 시험의 입력·출력·합격 기준 |
| 제외 (구현도 하지 않음) | 실제 Apple TSS 요청, 개인화된 이미지의 장치 전송, RecoveryOS 진입, 설치 디스크 생성·쓰기 |
| 별도 승인 필요 | 위 제외 항목 전부. 문서가 승인되어도 이 항목들의 승인이 되지는 않는다 |

## 2. 이미 있는 것 (코드 확인)

| 항목 | 위치 | 내용 |
| --- | --- | --- |
| https 전용 TSS (Android 빌드) | `third_party/libtatsu/src/tss.c`, `HV_TSS_HTTPS_ONLY` | 목록의 https 3개 호스트만 사용: `gs.apple.com`, `gs.apple.com.akadns.net`, `gs.apple.com.v.aaplimg.com` (포트 443). http 항목은 목록에 없다 |
| 재시도 제한 | 같은 파일 | 최대 6회, 총 150 s, 연결 20 s / 전체 60 s. 인증서·정책 거부는 재시도하지 않는다 (`tss_curl_error_retryable`) |
| 진단 문자열 | `tss_last_diag()` | 서버가 보낸 텍스트를 복사하지 않는 고정 어휘: 시도 수, 전송 계층 분류(`DNS`/`CONNECT`/`TIMEOUT`/`IO`/`POLICY_REFUSED`/`TLS_OR_OTHER`), HTTP 코드, `TSS_STATUS`, `MESSAGE_CLASS`, `NOT_A_TSS_REPLY`, `SUCCESS_BUT_NOT_A_PLIST` |
| libtatsu 시험 | `tools/tatsu-test.sh`, `tests/test_tatsu.py` | 가짜 TSS 서버 대상: 정상 응답, 청크 응답, STATUS 오류, 신뢰되지 않는 인증서, 호스트 이름 불일치, STATUS 없는 응답 6회, 연결 거부, 출하 빌드의 http 거부 |
| 요청 구조 시험 | `tools/tss-dryrun-test.sh` | 전송 경로 없는 빌드로 요청 plist 구조 확인, ECID·nonce 비출력 |
| 연결 정책 | `host/net_guard.c` | 기본 거부, curl 연결은 로컬 예외 없음, 공개 주소는 승인된 (이름, 포트)만 |
| 시험 전용 신뢰 저장소 | `curl_mbedtls.c`의 `HV_ALLOW_CA_ENV` | 시험 빌드에서만 `HV_CA_PATH`/`HV_EXTRA_ANCHOR` 사용. `tools/check-no-test-flags.sh`가 출하 빌드에 없음을 검사 |

## 3. 비어 있는 것 (이번 단계의 일)

1. **정책 층과 서버 층의 구별이 안 된다** (코드 확인 + 확인 필요)
   - `curl_mbedtls.c`는 연결 직전 훅이 거부한 주소를 건너뛴다 (374행). 모든 주소가 거부되면 호출자에게는 연결 실패와 같은 경로로 보인다.
   - libtatsu는 연결 실패를 재시도 대상으로 본다. 그러면 정책 거부가 6회 재시도되고 진단에는 `CONNECT`로 찍혀 "서버에 닿지 못함"과 구별되지 않는다.
   - 확인 필요: 거부 시 shim이 정확히 어떤 `CURLcode`를 돌려주는지.
2. **복원 도구를 통한 TSS 경로는 정책 아래서 시험된 적이 없다.** libtatsu 단독 시험만 있다. 복원 도구는 `restore_session`을 통해서만 시작하고(검증 완료, PC), 허용 목록이 비어 있어 지금은 TSS가 전부 거부된다 (설계 의도).
3. **응답 크기 상한**이 shim에 있는지 확인하지 못했다 (`curl_mbedtls.c`에서 본문 상한 관련 코드를 찾지 못함, 미검증).
4. **단계 경계의 보고**: 어느 TSS 요청(AP / LocalPolicy / RecoveryOS)에서 실패했는지를 한 구조로 보고하는 곳이 없다.

## 4. 설계 결정

### 4.1 승인 목적지 정책 (설계 결정)

- 허용 목록의 기본값은 비어 있다. 실제 Apple 요청을 승인할 때만 `(gs.apple.com, 443)` 등 필요한 항목을 추가한다.
- 항목은 **이름과 포트** 쌍이다. 이름이 맞아도 해석된 주소가 사설·루프백·링크로컬이면 거부한다 (구현됨).
- 세 호스트 중 어떤 것을 허용할지는 승인 때 정한다. 기본 제안은 `gs.apple.com:443` 하나다. 나머지 둘은 첫 호스트가 전송 계층에서 실패했을 때만 쓰이므로, 필요성이 확인되기 전에는 넣지 않는다.
- 정책 항목은 요청 단위가 아니라 **실행 단계**에 묶는다: TSS 단계가 시작될 때 추가하고 끝나면 제거한다. 복원 모드 이후의 장치 지정 URL은 이 항목으로 허용되지 않는다 (URLAsset은 자체 목록).

### 4.2 TLS 검증 (설계 결정)

- 출하 빌드: 시스템 신뢰 저장소로 체인과 호스트 이름을 항상 검증한다. 검증 끄기 옵션은 shim이 무시한다 (검증 완료).
- 시험 빌드: 시험용 자체 서명 CA를 `HV_CA_PATH`로 지정한다. 이 스위치는 시험 빌드에서만 컴파일되고, 출하 빌드에 들어갔는지는 `check-no-test-flags.sh`가 검사한다 (검증 완료).
- 가짜 서버의 인증서는 시험 실행마다 `openssl`로 만들고(유효 2일), 저장소에 커밋하지 않는다.

### 4.3 제한 (설계 결정)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 요청 본문 | 요청 plist 크기를 기록하고 상한 1 MiB로 시험 | 요청은 수 KB 수준이어야 함 (미검증: 실제 크기 미측정) |
| 응답 본문 | 상한 **1 MiB** (shim에 없으면 추가: 호스트 파일, 승인된 범위) | 티켓은 수십 KB. 상한을 넘으면 `REPLY_TOO_LARGE` |
| 시간 | 연결 20 s, 전체 60 s, 총 150 s (기존 값) | 코드 확인 |
| 재시도 | 전송 계층 오류에 한해 최대 6회. **정책 거부와 인증서 오류는 0회** | 정책 거부는 재시도해도 같은 결과 |
| 자동 재시도 (사용자 확인 단위) | 금지. 한 번의 사용자 확인으로 TSS 3건(AP / LocalPolicy / RecoveryOS)을 각각 1회 | `restore-architecture.md` 2절 |

### 4.4 실패 분류 (설계 결정)

각 TSS 요청은 아래 코드 중 정확히 하나로 끝난다. 코드는 **누가 판단했는가**로 나눈다.

| 코드 | 판단한 층 | 관측 지점 | 재시도 | 사용자에게 보이는 뜻 |
| --- | --- | --- | --- | --- |
| `OK` | — | 응답 plist 파싱 성공, 필수 키 존재 | — | 준비 단계 성공 (복원 완료 아님) |
| `POLICY_DENIED` | 우리 정책 (`net_guard`) | 가드의 거부 카운터 증가 + 로그의 거부 사유 | 0 | 앱이 막음. 서버는 요청을 받지 않았다 |
| `NET_DNS` | 네트워크 | 진단 `TRANSPORT … DNS` | 6 | 이름을 찾지 못함 |
| `NET_CONNECT` | 네트워크 | `CONNECT`이면서 가드 거부 카운터 불변 | 6 | 서버에 닿지 못함 |
| `NET_TIMEOUT` / `NET_IO` | 네트워크 | `TIMEOUT` / `IO` | 6 | 시간 초과 / 전송 중 끊김 |
| `TLS_FAILED` | TLS | `TLS_OR_OTHER` + 인증서·호스트 이름 | 0 | 인증서 검증 실패. 보안 신호이므로 다른 호스트로 바꿔 재시도하지 않음 |
| `HTTP_ERROR` | 서버(HTTP) | 진단 `HTTP: n` (n ≠ 200) | 6 | 서버가 HTTP 오류를 돌려줌 |
| `SERVER_REFUSED` | 서버(TSS 정책) | 진단 `TSS_STATUS: n` (n ≠ 0), `MESSAGE_CLASS` | 0 | 서명 서버가 이 요청을 거절. 우리 쪽 네트워크·구현 오류가 아닐 수 있음 |
| `BAD_REPLY` | 서버/파서 | `NOT_A_TSS_REPLY` / `SUCCESS_BUT_NOT_A_PLIST` / 필수 키 없음 | 0 | 형식 불량 |
| `REPLY_TOO_LARGE` | 우리 제한 | 본문 상한 초과 | 0 | 상한 초과 |
| `CANCELLED` | 사용자/앱 | 취소 플래그 | 0 | 취소 |

원칙:
- `POLICY_DENIED`와 `NET_CONNECT`는 **가드 카운터의 증가 여부**로 가른다 (연결 코드만으로는 구별되지 않음, 3절 1항). 확정 방법은 구현 전에 정한다: (a) shim이 거부 때 별도 `CURLcode`를 돌려주게 하거나, (b) TSS 단계가 요청 전후의 가드 카운터를 비교한다. (b)는 shim 변경이 없어 우선 제안이고, (a)는 재시도까지 막으므로 장기 안이다.
- `SERVER_REFUSED`는 "서버가 요청을 읽고 거절했다"는 뜻이다. 서명 서버의 정책과 가상 장치 식별값에 영향을 받으므로, 성공해도 이후 iBSS 실행을 보장하지 않고 거부되어도 네트워크 구현 오류로 단정하지 않는다.
- 로그와 보고에는 코드·시도 수·HTTP 코드·STATUS 숫자·호스트 이름만 넣는다. ECID, nonce, 티켓, 서버 메시지 원문은 넣지 않는다.

## 5. 가짜 TSS 서버 시험 계약

### 5.1 입력

| 입력 | 값 |
| --- | --- |
| 서버 | 루프백(127.0.0.1) 위의 TLS 서버. 시험마다 새 자체 서명 CA와 인증서 |
| 허용 목록 | 시험이 `(localhost, 서버포트)`를 등록. 그 외 항목 없음 |
| 신뢰 | `HV_CA_PATH`로 시험 CA만 (시험 빌드). 출하 빌드로는 같은 시험의 "신뢰 안 됨" 쪽만 실행 |
| 요청 | 실제 요청 빌더가 만든 plist (식별값은 가짜 값 사용: 실제 ECID·nonce를 쓰지 않는다) |

### 5.2 시나리오와 기대 출력

| # | 서버 동작 | 기대 코드 | 추가 합격 조건 |
| --- | --- | --- | --- |
| 1 | 정상 응답(티켓 키 포함) | `OK` | 요청 1회, 재시도 0 |
| 2 | 청크 전송 응답 | `OK` | 재조립된 plist가 동일 |
| 3 | `STATUS=8` | `SERVER_REFUSED` (status 8) | 재시도 0, 서버 메시지 원문이 로그에 없음 |
| 4 | HTTP 500 | `HTTP_ERROR` | 6회 이하, 총 150 s 이하 |
| 5 | 본문이 plist 아님 | `BAD_REPLY` | 재시도 0 |
| 6 | 본문 1 MiB 초과 | `REPLY_TOO_LARGE` | 서버가 받은 연결 1, 메모리 상한 내 |
| 7 | 신뢰되지 않는 인증서 | `TLS_FAILED` | 재시도 0, 다른 호스트 시도 0, 서버 핸들러에 요청 도달 0 |
| 8 | 신뢰된 인증서, 다른 호스트 이름 | `TLS_FAILED` | 위와 같음 |
| 9 | 연결 거부(닫힌 포트) | `NET_CONNECT` | 6회, 가드 거부 카운터 불변 |
| 10 | 허용 목록에 없는 포트의 정상 서버 | `POLICY_DENIED` | 서버가 받은 연결 **0**, 재시도 0, 가드 거부 카운터 증가 |
| 11 | 허용 이름이 루프백 대신 사설 주소로 해석됨 (이름 해석 대체) | `POLICY_DENIED` | 서버 연결 0 |
| 12 | 응답 전 무응답 (연결 후 침묵) | `NET_TIMEOUT` | 시간 상한 내 종료 |
| 13 | 취소 플래그를 요청 중에 올림 | `CANCELLED` | 1 s 안에 반환 |
| 14 | 3건(AP / LocalPolicy / RecoveryOS) 중 두 번째만 `STATUS` 거절 | 첫째 `OK`, 둘째 `SERVER_REFUSED`, 셋째 **요청하지 않음** | 단계 보고에 어느 요청에서 멈췄는지 기록 |

### 5.3 전체 합격 기준

- 각 시나리오가 기대 코드와 추가 조건을 만족한다. 코드는 **정확히 하나**다.
- `POLICY_DENIED` 시나리오에서 가짜 서버가 받은 연결이 0이다 (카운터와 서버 쪽 관측이 일치).
- 어떤 출력(stdout, stderr, 보고 행)에도 가짜 ECID·nonce·티켓·서버 메시지 원문이 없다.
- 정상 시험이 끝난 뒤 자원 보고서(fd, 스레드, 핸들)가 시험 전과 같다 (`preflight`와 같은 기준).
- 같은 시험을 **정책 해제 대조**로 한 번 더 돌려, 대조에서는 시나리오 10·11이 서버에 닿는다 (시험이 정책을 실제로 검사한다는 증거).
- 출하 빌드에 시험 스위치가 없음을 `check-no-test-flags.sh`가 계속 확인한다.

### 5.4 실행 위치

- PC(이 개발 환경)와 GitHub Actions 모두. 새 스크립트 `tools/tss-stage-test.sh`로 두고 `android-engine.yml`의 독립 단계로 추가한다. 실패하면 CI 전체가 실패해야 하며 `continue-on-error`를 쓰지 않는다.

## 6. 구현 순서 (승인 후)

1. 확인: shim이 정책 거부 때 돌려주는 `CURLcode`, 응답 크기 상한 유무.
2. 실패 분류 함수와 단계 보고 구조 (호스트 파일).
3. 가짜 TSS 서버 시험(5.2) 구현과 합격 기준 자동 판정.
4. (필요하면) shim에 응답 상한 추가: 호스트 파일이며 별도 확인 후.
5. PC 회귀 → CI.

## 7. 별도 승인이 필요한 항목 (이 문서로 승인되지 않음)

- [ ] 실제 Apple TSS 요청 (허용 목록에 `gs.apple.com:443` 등 추가 포함)
- [ ] 개인화된 이미지의 가상 DFU 장치 전송
- [ ] RecoveryOS 진입
- [ ] 설치 디스크 생성·쓰기
- [ ] 벤더링 소스(libtatsu 등) 변경이 필요해지는 경우

## 8. 알려진 한계

- 서명 서버가 가상 장치 식별값에 어떻게 반응하는지는 실제 요청 없이는 알 수 없다 (미검증).
- 가짜 서버는 응답 형식만 흉내 낸다. 실제 서버의 지연, 오류 문구, 정책 변경은 재현하지 못한다.
- 복원 모드 이후의 펌웨어 TSS 약 10곳은 이번 단계 범위가 아니다 (`restore-architecture.md` 3절).

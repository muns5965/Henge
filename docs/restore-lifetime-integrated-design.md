## 0. 설계 완료 기준

| 번호 | 기준 |
| --- | --- |
| K1 | 정상 종료, 오류 종료, 취소 실패의 모든 경로에서 객체 해제 책임이 정의되어 있다 |
| K2 | 스레드 등록부터 완료까지 상태 전환과 동기화 조건이 모순되지 않는다 |
| K3 | 최초 오류가 보존되고 최종 성공으로 잘못 보고되지 않는다 |
| K4 | 공유 연결과 정책 훅의 수명이 활성 작업보다 짧아지지 않는다 |
| K5 | 모든 안전성 요구에 소스상 보장 방법과 검증 방법이 연결되어 있다 |
| K6 | 미확정 사항마다 검증 조건과 검증 실패 시 적용할 대안이 있다 |

"완성"은 모든 위험이 해소됐다는 뜻이 아니라 모든 위험의 처리 방식이 정의됐다는 뜻이다. 소스 구조로 보장해야 하는 사항(객체 수명, 등록 원자성, 오류 전파)은 "시험 예정"으로 남기지 않는다. 점검은 여섯 종료 경로(정상, 오류, 취소 실패, 루프 미종료, 감시 경합, `CLOSED` 이후 정리 지연)와 두 경쟁(취소 수락 vs `CLOSED`, 실패 기록 vs `CLOSED`)에 대해 한다(11절).

## 1. 범위

| 단위 | 생성 | 현재 종료 보장 | 이 설계의 처리 |
| --- | --- | --- | --- |
| 복원 엔진 스레드 | `host/install.c` → `restore_session.c` | `end()`가 등록 수만 확인 | 유지, 종료 순서·상태 규칙에 포함 |
| 비동기 데이터 요청 스레드(5종) | `restore.c` 루프, detach | **없음** | 레지스트리 카운터(D1) |
| 리버스 프록시 제어·연결 스레드 | `reverse_proxy_client_start_proxy` / 제어 스레드 | 제어·마지막 연결만 join, 무기한 | 같은 등록·완료 규칙 + 종료 요청 분리 (D8) |
| 호스트 감시 | 신규 | 없음 | 종료 트리거 뒤에만 도는 독립 스레드 (D2) |
| FDR 스레드 | `#ifndef HAVE_REVERSE_PROXY` | 빌드 설정상 컴파일되지 않음(P11) | 해당 없음(설정이 바뀌면 재평가) |
| 다운로드·TSS 스레드 | 호스트 모듈 | 별도 | 이 설계의 취소 신호만 연결 |

관리 대상 객체: `client`, `client->restore`(장치 핸들, restored 연결, `bbtss`), `build_identity`, `ipsw`, `filesystem`, 서비스·ASR 연결, 정책 훅, 세션 기록(TSS 포함), 연결 등록 항목.

## 2. 사실

### 2.1 앞 문서의 전제

P1~P11은 `async-lifetime-design.md`를 따른다(비동기 스레드 detach·카운터 부재, 훅 제거 후 허용·본문 상한 상실, `client` 참조 필드, 처리기의 `FLAG_QUIT` 미확인, `async_err`·`flags` 비동기화 접근, 수신 호출 한도와 작업 전체 한도의 차이, `close`의 한계, P10 오류 덮어쓰기, P11 빌드 설정).

### 2.2 이번 소스 확인 결과 (세 열)

| 번호 | 확인 대상 | 확인된 소스 사실 | 코드상 위험 (미관측) | 실행 검증 필요 |
| --- | --- | --- | --- | --- |
| S1 | 프록시 구조 | `start_proxy`가 제어 스레드를 만들고, 제어 스레드가 연결 요청마다 연결 스레드를 만들며 핸들을 변수 `th_conn` 하나에 대입한다. 프록시 루프는 장치 연결이 닫히거나 오류가 날 때까지 돈다. 외부 호스트 소켓은 `socket_connect`(글루 훅 적용)로 열고 루프 끝에서 `socket_close` | 연달아 오는 연결 요청에서 이전 연결 스레드의 핸들이 유실되어 join·free되지 않고, 해제된 제어 `client`를 참조(P13) | T13 |
| S2 | 프록시 정리 함수 | `reverse_proxy_client_free`: `client->parent = NULL` → 제어 스레드 join → `service_client_free(parent)`. 제어 스레드는 `parent`가 NULL이면 수신 함수가 즉시 INVALID_ARG를 돌려주어 종료 경로로 빠진다(진행 중이던 수신은 최대 1000 ms 뒤 반환). 제어 스레드는 종료 시 마지막 `th_conn`을 join한다 | `client->parent`는 비원자적 쓰기·읽기(데이터 경쟁). 마지막 연결 스레드가 끝나지 않으면 제어 스레드 join이 **무기한**(P15) | T12 |
| S3 | `service_client_free` | `idevice_disconnect`(`close(fd)`, SSL이면 SSL 해제 선행) 후 `free`. 평문 연결에서는 비차단 | SSL 연결 경로의 종료 핸드셰이크는 확인하지 않음 | 복원 경로에서 SSL 연결이 쓰이는지(V11) |
| S4 | 연결 경로의 포괄 범위 | `idevice_connect`/`idevice_disconnect`는 장치 서비스 연결(restored, ASR, PLIST 서비스, FDR, 프록시의 장치 쪽)을 모두 만든다. 프록시의 외부 호스트 소켓은 별도(`socket_connect`/`socket_close`). curl 대체 계층은 자체 200 ms 폴링 취소 | libusbmuxd↔usbmuxd 소켓, 이벤트 리스너는 이 훅이 포괄하지 않음 | 취소 대상이 되는 연결의 전수 확인 |
| S5 | `CLOSED` 이후 정리 호출 | `idevice_free`: 해제만(비차단). `restored_client_free`: `restored_goodbye`가 **Goodbye를 보내고 응답을 받는다**(수신 한도까지 블로킹). `idevicerestore_client_free`: `dfu/recovery_client_free`(USB 핸들), 이벤트 구독 해제(내부에서 listenfd `shutdown` 후 이벤트 스레드 취소·join; irecv 쪽 구독 해제의 블로킹 여부는 전부 읽지 못함) | 정리 호출은 비차단이 아니다. 종료 시간의 상한은 보장되지 않는다(12절) | 정리 시간 측정(T9) |
| S6 | 호스트 감시 | `restore_session.c`와 `install.c`에 감시·취소 경로가 **없다**. 시작 함수는 스레드를 만들고 즉시 반환한다. `restore_preflight.c`에 "제한 시간 → `global_quit_flag` 설정 → 3 s 폴링" 선례가 있다. `global_quit_flag`는 `restore.c` 루프가 읽지 않는다(루프는 `client->flags`의 `FLAG_QUIT`만 본다) | 호스트는 해제될 수 있는 `client`에 접근하지 않고는 루프를 멈출 수 없다 | T14, T17 |
| S7 | 반환 경로의 해제·`end()` 순서 | `restore_thread`: `run_client` → (엔진 등록 해제) → `idevicerestore_client_free(c)` → `end()` → `g_result` 갱신 → 진행 콜백. 정상·`run_client` 거부 경로는 이 순서 | 조기 반환 경로가 `end()`를 건너뜀: `idevicerestore_client_new` 실패(`g_result=-1`, 콜백 없음), `hv_install_start`의 `pthread_create` 실패(`begin()` 이후 `g_result=1`로 남아 이후 시작이 "이미 실행 중"으로 막힘) — 기존 결함 후보 | - |
| S8 | 엔진 등록 해제 이후 실행 코드 | `hv_restore_session_run`은 `engine_leave` 뒤 `*rc = r`만 한다. 그러나 `install.c`는 그 뒤에 `idevicerestore_client_free`, `end()`, `g_result`, 진행 콜백을 실행한다 | (1) `begin()`이 엔진 수 0만 보므로 엔진 등록 해제와 `end()` 사이에 `begin()`이 성공하면 새 세션의 훅을 이전 세션의 `end()`가 제거할 수 있다 — 지금은 `hv_install_start`의 `g_result==1` 검사로만 막혀 있다. (2) 진행 콜백이 전역 `g_progress`/`g_progress_user`를 `end()`와 `g_result` 갱신 **뒤**에 읽어, 다음 세션이 덮어쓰면 경쟁한다 | T16 |

| S9 | `idevicerestore_start()`의 `restore_device()` 이후 구간 (`idevicerestore.c` 1596~1632)과 `build_identity` 소유권 | `restore_device()`가 음수를 돌려주면 `build_identity`를 해제하지 않고 즉시 반환한다. 음수가 아니면 `build_identity_needs_free`일 때만 `plist_free`한다(1630~1631). **`needs_free`는 `FLAG_CUSTOM`일 때(`plist_new_dict`)만 1로 설정된다(897~899).** 그 외 경로의 `build_identity`는 `build_manifest_get_build_identity_for_model[_with_variant]`가 `BuildIdentities` 배열에서 `plist_array_get_item`으로 돌려주는 **하위 노드**(소유권 없음)다. 호스트 설정(`install.c`)은 `FLAG_ERASE`(+`FLAG_DEBUG`)만 쓰고 `FLAG_CUSTOM`을 쓰지 않는다. 하위 노드는 `idevicerestore_client_free`의 `plist_free(client->build_manifest)`로 해제된다. 비동기 처리기는 `client->restore->build_identity`로 같은 노드를 참조한다 | 호스트 설정에서는 `build_identity`를 `idevicerestore_start`가 해제하지 않으므로 "일반 실패 경로의 `build_identity` 누수"는 **존재하지 않는다**(v2.1 문서의 해당 가정을 철회). 보호해야 할 것은 `build_identity` 단독 해제가 아니라 그 상위 `build_manifest`를 해제하는 `idevicerestore_client_free`의 생략이다(C18). `FLAG_CUSTOM` 경로에서는 `needs_free`=1인 독립 사본이므로 7b에서 양수 반환 시 해제되는 위험이 있다 | T25, T26 |

### 2.3 이전 확인 사실 (유지)

P12(제어/연결 스레드 구조), P13(핸들 유실), P14(프록시 루프와 글루 훅), P15(`reverse_proxy_client_free`는 `restore_client_free` 앞이며 무기한 블로킹 가능), P16(프록시 스레드는 엔진 등록 수에 안 보임), P17(복원 연결 송신은 길이+본문 두 번 송신, 잠금 없음, `restored_send`가 단일 진입점), P18(`DataPort` 없는 처리기에서 `restored_send` 호출 최소 7곳), P19(`usbmuxd_disconnect`는 `close`만), P20(루프 뒤 정리 구간은 `restore.c` 5907~5924)는 v1과 같다.

## 3. 제약 [제약]

| 번호 | 제약 |
| --- | --- |
| C1 | 신규 작업의 **등록 승인과 해당 카운터 증가는 하나의 원자적 전환**(같은 레지스트리 잠금). 등록 허용 상태는 4.2의 표를 따른다 |
| C2 | 등록된 작업은 스레드 생성 지연·실패와 무관하게 카운터로 보호된다. 스레드를 만드는 작업은 `잠금 아래 예약+카운터 증가 → 잠금 해제 → 생성 → (성공: 실행 / 실패: 잠금 아래 실패 기록+예약 해제)` 순서이며 생성은 잠금 밖에서 한다. 생성 실패는 "요청 없음"으로 되돌리지 않고 실패 이력과 재시도 가능 여부를 남기며, 해당 작업을 기다리는 모든 대기자에게 종결 통지(결과 코드 포함)로 전달한다. 재시도 가능한 생성 실패와 종료 불가 실패를 구분하며, 모든 생성 실패를 즉시 `QUIESCENCE_FAILED`로 처리하지는 않으나 기록 없이 소거하지 않는다 |
| C3 | `CLOSING` 진입과 등록 검사는 같은 잠금 아래에서 한다. 이미 승인된 작업의 실행·실패 기록·완료 통지·카운터 감소는 `CLOSING`에서도 허용한다 |
| C4 | 작업의 **모든 종료 실패는 그 작업의 완료 통지 이전에 확정**한다. **실패 기록과 카운터 감소는 같은 임계구역**에서 한다. 완료 통지는 작업이 세션 객체에 접근하는 마지막 동작 뒤에 한 번 일어나며, 통지 이후 작업은 세션 객체를 건드리지 않는다. `CLOSED` 이전에 수행된 작업의 실패는 단순 진단이 아니라 종료 판정에 반영되는 기록이다. `CLOSED` 이후의 실패는 엔진의 객체 정리 실패(정리 진단, `IDLE` 전환 금지)와 뒤늦은 취소 요청(거부 사실만 기록)으로 구분한다 |
| C5 | 레지스트리는 세션 객체보다 오래 산다(프로세스 정적 저장소). 늦은 완료 통지가 해제된 메모리에 쓰지 않는다 |
| C6 | 세션 객체(`client`, `client->restore`, 장치 핸들, restored 연결, `build_identity`, `ipsw`, `filesystem`, 세션 기록)는 **`CLOSED` 상태에서 해제 권한을 가진 엔진 스레드만** 해제한다. 감시는 직접 해제하지 않는다. 한도 도달만으로 해제하지 않는다 |
| C7 | 정책 훅은 `end()`가 `CLOSED`에서만 제거한다. 훅을 쓰는 모든 실행 단위(프록시 스레드, 비동기 처리기, 취소 작업 포함)가 끝나기 전에는 제거되지 않는다 |
| C8 | 오류 보존(최초 오류의 처리기·메시지 종류·오류 코드 식별)과 실패 전파(최초 오류가 난 실행의 최종 결과는 성공이 아님)를 각각 충족한다. 두 조건은 서로 대체할 수 없다 |
| C9 | 최종 결과는 활성 카운터 0을 확인한 뒤에 확정한다. 완료 확인 전에 성공을 보고하지 않는다. `QUIESCENCE_FAILED`로 끝나는 실행의 결과는 항상 실패다. **카운터 0 조건은 `CLOSED`로 가는 정상 완료 경로에 적용하며, `QUIESCENCE_FAILED`는 카운터가 0보다 커도 실패를 확정해 보고하는 명시적 예외다**(작업 완료 판정과 실패 확정은 별개이며, 확정 뒤 카운터가 0이 되어도 상태 복귀·해제는 없다). **최종 보고는 복원 결과(성공 / 일반 실패 / 사용자 취소)와 세션 정리 결과(완료 / 진행 중 / 실패 확정)를 합성**하며(4.7 표), 세대당 **한 번만** 확정한다(잠금 아래 비교-설정). `CLEANUP_DELAYED`는 중간 보고이며 최종 결과가 아니다. 정리 실패가 최초 오류 기록과 최종 보고 종류를 지우지 않도록 둘은 별도로 보존한다 |
| C10 | 복원 연결로의 송신은 **메시지 단위로 직렬화**한다(길이+본문이 한 임계구역). 잠금 객체의 초기화는 연결 생성 시, 해제는 연결 해제(`CLOSED` 이후) 때 한다 |
| C11 | **`QUIESCENCE_FAILED`에서는 미완료 작업이 참조할 수 있는 객체와 정책 훅을 유지하고 세션 전체 정리를 금지한다.** 같은 프로세스의 신규 세션을 거부하고 자동 복귀하지 않는다. 완료된 작업의 독립 자원은 소유권과 마지막 참조가 확인된 경우 해제할 수 있다(처리기가 자기 연결을 닫는 것) |
| C12 | 레지스트리 잠금을 잡은 채 처리기·콜백·네트워크 호출(`shutdown`, `close`, 스레드 생성 포함)을 하지 않는다. 종료 대기는 비동기 처리기 스레드에서 호출하지 않는다 |
| C13 | **`CLOSED` 전환 조건**(모두 같은 잠금 아래에서 한 번에 판정): (a) 모든 작업 카운터(비동기 요청, 프록시 제어, 프록시 연결, 진행 중 취소)가 0, (b) 처리되지 않은 종료 실패 기록이 없음, (c) 이 결정과 같은 잠금 안에서 취소 작업의 신규 등록을 닫음. `CLOSED` 전환 권한은 엔진 스레드에만 있고, 감시는 `QUIESCENCE_FAILED` 확정만 한다 |
| C14 | **연결 참조 규약**: 취소 측은 잠금 아래에서 연결 항목의 참조를 확보하고 잠금을 푼 뒤 `shutdown`을 부르고 참조를 반환한다. 소유자는 닫기 전에 등록을 해제하고 참조 반환을 **한도 안에서** 기다린다. 한도를 넘으면 **fd를 닫지 않고 유지**하며 실패를 레지스트리에 기록만 한다(상태 전환은 직접 하지 않고, 엔진 또는 감시가 같은 잠금 아래에서 `QUIESCENCE_FAILED`를 확정한다). 늦게 참조가 반환돼도 `QUIESCENCE_FAILED`에서 복귀하지 않는다. 한도 초과가 기록된 뒤에는 카운터가 0이어도 `CLOSED`가 되지 않는다(C13 (b)) |
| C15 | **`IDLE` 전환 조건**(같은 잠금 아래에서 모두 확인): (a) 현재 세대 번호와 일치한다, (b) 그 세대에 정리 실패 확정 기록이 없다, (c) 모든 세션 객체와 정책 훅의 정리가 완료됐다(세션 객체·훅의 마지막 사용 종료 포함), (d) `end()`가 정상 반환했다, (e) 엔진 등록 해제 뒤 남아 실행되는 코드가 전역 레지스트리와 다음 세션의 상태(전역 콜백·결과 변수 포함)에 접근하지 않는다, (f) 이미 확정된 최종 결과는 `IDLE` 전환이 바꾸지 않는다. **복원 결과(성공 / 일반 실패 / 사용자 취소)는 `IDLE` 전환을 막지 않는다.** 막는 것은 세션 정리 결과가 "실패 확정"이거나 "미완료"인 경우뿐이다. `begin()`은 `IDLE`에서만 허용하며 호출마다 증가하는 **세대 번호**를 발급한다. 감시·취소·진행 콜백·실패 기록은 자기 세대 번호와 일치할 때만 레지스트리에 쓰고, 불일치 통지는 거부하고 진단으로만 남긴다. 세대 번호는 기록 오염을 막을 뿐 객체 수명을 보호하지 않으며 수명은 C6·C7·C11이 맡는다. 엔진 스레드의 실제 종료 대기는 요구하지 않되 (e)를 근거로 한다 |
| C16 | 감시와 호스트는 해제될 수 있는 `client`에 접근하지 않는다. 종료 요청은 레지스트리가 소유한 원자적 종료·취소 플래그로 전달하고, 복원 루프가 반복 맨 앞에서 이 플래그를 읽는다 |
| C17 | **취소 단일 개시와 결과 전달**: 취소 요청의 수락·중복 판정·진행 중 취소 카운터 증가는 같은 잠금 아래에서 한다. 이미 개시된 취소는 합쳐 한 번만 실행하며(엔진과 감시가 동시에 요청해도 하나의 종료 절차), 취소 실행 상태에 따라 처리한다: **예약 또는 실행 중** — 중복 스레드 금지, 중복 요청자는 첫 작업의 종결 통지를 기다림 / **생성 실패** — 실패 기록과 예약 해제를 한 임계구역에서 처리하고 종결 통지(생성 실패 코드)로 대기자를 깨움, 재시도는 허용 정책 안에서 잠금 아래 **한 요청자에게만** 허용하고 다른 요청자는 그 결과를 기다림 / **실행 완료** — 완료와 성공은 별개이며 연결 참조 반환과 진행 중 카운터로 성공 여부를 따로 판정. 대기자는 종결 결과를 확인한 뒤에만 재시도를 판단한다. 생성 실패를 "취소 완료"로 간주하지 않는다. 마감을 넘어 살아 있는 취소 스레드의 카운터는 강제로 0으로 만들지 않고 `QUIESCENCE_FAILED`로 수렴한다. **정상 종료의 유예 단계에서 취소 단계로 넘어가는 전환**도 단일 실행이다: 단계 전환·취소 예약·진행 중 취소 카운터 증가를 같은 잠금의 한 임계구역에서 하고, 먼저 전환한 쪽이 취소를 개시하며 나머지는 이미 전환된 것을 확인하고 기존 취소의 종결 통지를 기다린다. 잠금 안에서는 예약과 상태 변경만 하고 스레드 생성·`shutdown`은 잠금 밖에서 한다(C2, C12). 예약한 쪽의 생성 실패는 대기자 모두에게 종결 통지로 전달되며 예약 상태를 무기한 기다리지 않는다. `CLOSED` 이후 도착한 취소 요청은 "이미 종료된 세션에 대한 요청"으로 거부하고 새 취소 작업을 만들지 않으며 거부 사실만 기록한다 |
| C18 | **반환 계약과 해제 판단**: `restore_device()`는 일반 복원 실패와 `QUIESCENCE_FAILED` 모두에서 **음수**를 돌려준다(`idevicerestore_start`가 음수에서 즉시 반환하여 `FLAG_CUSTOM` 사본을 포함해 아무것도 해제하지 않기 때문 — S9). 음수 반환값만으로는 두 실패를 구분할 수 없으므로 호스트(`install.c`)는 해제 전에 **레지스트리의 세션별 해제 허용 여부**를 조회한다: `CLOSED`면 `idevicerestore_client_free`(→`build_manifest`와 그 하위 `build_identity` 해제)와 `end()`를 수행, `QUIESCENCE_FAILED`면 둘 다 생략한다. 조회 결과는 이후 뒤집히지 않는다(두 상태 모두 종단 취급, `CLOSED` 이후 수명 실패 전환 금지). 반환값이 0이어도 레지스트리가 `QUIESCENCE_FAILED`면 실패로 처리하고 해제를 생략한다. 7b에서도 `g_result` 확정과 앱 보고는 수행한다. **`build_identity` 자체의 독립 해제는 `FLAG_CUSTOM` 사본(`needs_free`=1)에만 해당하며, 필요하면 `idevicerestore_start`의 음수 반환 경로에 `hv_*` 훅(NULL이면 기존 동작)을 두어 아래 표대로만 해제한다**(호스트 설정에서는 해당 경로가 활성화되지 않으므로 방어 장치이며 필수 구현이 아니다). 해제 판단표: (1) `CLOSED` + `needs_free`=참 + 유효한 훅 응답 → 해제 허용, (2) `CLOSED` + `needs_free`=거짓 → 독립 해제 금지(`build_manifest` 하위 노드), (3) `QUIESCENCE_FAILED` → 해제 금지, (4) 훅 NULL → 음수 반환 경로의 기존 동작 유지(해제 없음), **정상 반환 경로의 `needs_free` 정리는 어떤 경우에도 바꾸지 않음**, (5) 조회 실패·세대 불일치·알 수 없는 상태 → 해제 금지, 오류 기록(세대가 유효하지 않으면 세션 오류가 아니라 **세션과 무관한 진단 기록**으로만 남김, C15) |
| C19 | **마감 시계와 정리 한도**: 모든 마감(유예, 취소, 정리)은 `CLOCK_MONOTONIC` 기준 **절대 시각**이며, 대기에 쓰는 조건변수도 `pthread_condattr_setclock(CLOCK_MONOTONIC)`로 같은 시계를 쓴다. 한도의 **값**은 T7·T9 계측 전에는 정하지 않으나 **집행 방식은 확정**한다: 독립 감시가 마감을 판정하며(엔진은 블로킹 중 스스로 판정할 수 없다), 작업 단계 마감 초과는 `QUIESCENCE_FAILED`, 정리 단계 마감 초과는 앱 보고 종류 `CLEANUP_FAILED`와 "정리 실패 확정" 기록으로 이어진다. 한도는 강제 해제 시각이 아니라 **실패 확정·보고 시각**이다: 실행 중인 정리가 있으면 객체 해제나 훅 제거를 하지 않고, 실패 확정 뒤 정리가 늦게 끝나도 `IDLE`이나 신규 세션으로 자동 전환하지 않는다 |

### 4.2 상태와 전환

```
IDLE ─begin()─▶ ACTIVE ─(종료 시작)─▶ CLOSING ─(C13 세 조건)─▶ CLOSED ─(엔진 정리+end())─▶ IDLE
                  │                      │
                  └──────────────────────┴─(한도 도달 / 엔진 미종료 확정)─▶ QUIESCENCE_FAILED (종단)
```

- **`CLOSED` = 세션 작업 정리 완료 + 객체 해제 권한 확정.** 객체 해제가 끝났다는 뜻이 아니다. 해제 완료는 엔진 정리·`end()`·`IDLE` 전환이다.
- `QUIESCENCE_FAILED`는 `ACTIVE`/`CLOSING`에서 선착순으로 확정한다. `CLOSED`가 먼저 확정되면 감시는 상태를 바꾸지 않는다.
- 사유 구분(상태 추가 없음): `tasks_not_quiescent`, `engine_not_exited`, `conn_ref_not_returned`.
- `CLEANUP_FAILED`는 새 레지스트리 상태가 아니라 **앱 보고 종류 + 해당 세대의 정리 실패 확정 기록**이다. 기록이 있으면 상태는 `CLOSED`로 남되 `IDLE` 전환과 `begin()`이 거부된다(C15). `CLOSED`가 "정리 완료"를 뜻하지 않는다.

등록·허용 규칙:

| 동작 | ACTIVE | CLOSING | CLOSED | QUIESCENCE_FAILED |
| --- | --- | --- | --- | --- |
| 비동기 데이터 요청 등록 | 허용 | 거부 | 거부 | 거부 |
| 프록시 제어·연결 등록 | 허용 | 거부 | 거부 | 거부 |
| 취소 작업 등록 | 허용 | 허용 | 거부(C17) | 거부 |
| 완료 통지·카운터 감소·실패 기록 | 허용 | 허용 | 해당 없음 | 허용(기록만, 상태 불변) |
| 객체 해제(엔진만) | 불가 | 불가 | 가능(권한 보유 시) | **세션 전체 정리 불가**(C11) |
| 훅 제거(`end()`) | 불가 | 불가 | 가능 | 불가 |
| `begin()` | 거부 | 거부 | 거부 | 거부 |

`begin()`이 허용되는 상태는 `IDLE`뿐이다.

| 5a | **프록시 신규 연결 차단** — 별도 플래그가 아니라 3의 `CLOSING` 전환 자체이며, 연결 스레드 등록(`try_register`)이 같은 잠금에서 상태를 판정한다(C1, C3). 기존 연결은 건드리지 않는다 | 허용 | 허용 |
| 5b | **기존 프록시 연결 `shutdown`** (취소 단계에서만) | **하지 않음**(유예 한도 이후에만, 자연 완료 대기) | 4와 함께 수행 |
| 6 | **한도 있는 완료 확인**(절대 `CLOCK_MONOTONIC` 마감, C19): 모든 카운터 0, 연결 참조 반환, 종료 실패 기록 없음. 정상 종료는 유예 한도 도달 시 **즉시 실패 확정하지 않고** 취소 단계로 전환(아래 단계 규칙) | 유예 마감 → 취소 단계 → 취소 마감 | 취소 마감 |
| 7a | 확인됨 → `CLOSED` 확정(엔진, C13) → 프록시 객체 해제 → `async_err`/첫 오류 합성 → `restore_client_free` | 동일 | 동일 |
| 7b 조건 | **최종 단계(취소 마감) 도달** → `QUIESCENCE_FAILED` 확정 |  |  |

**단계 규칙**: 정상 종료는 `자연 완료 유예 → (미완료 시) 취소 개시(4, 5b 수행) → 취소 한도 대기 → (미완료 시) 7b`, 오류 종료는 `즉시 취소 → 취소 한도 대기 → (미완료 시) 7b`. 유예에서 취소로의 전환은 C17에 따라 엔진과 감시 사이에서 한 번만 일어난다. 감시는 **현재 단계의 마감**만으로 판정하며, 정상 종료의 유예 마감만으로 `QUIESCENCE_FAILED`를 확정하지 않는다. `QUIESCENCE_FAILED`는 카운터가 0보다 커도 확정·보고된다(C9 예외).

프록시 정리는 7a에서만 `reverse_proxy_client_free`를 부른다. 이 시점에는 모든 프록시 스레드가 완료 확인되어 있으므로 함수 안의 join은 이미 끝난 스레드에 대한 호출이다.

### 4.4 복원 루프 자체가 종료되지 못하는 경우 (호스트 감시)

- 구조적 안전: `restore_client_free`는 `restore_device` 안에서 루프 종료 뒤에만, `idevicerestore_client_free`는 `idevicerestore_start` 반환 뒤에만 불리므로, 루프가 멈추면 어떤 객체도 해제되지 않고 엔진 등록 수가 0이 아니어서 `end()`도 훅을 제거하지 않는다(안전 측).
- 빠진 것은 통지다. 호스트 감시가 담당한다.
  1. 종료 트리거(사용자 취소 또는 오류) 때 감시 스레드를 시작한다. **종료 트리거 없이 멈춘 엔진(무진행)은 이 설계의 범위 밖**이다(V10).
  2. 감시는 레지스트리의 종료 플래그와 취소를 설정한다(C16; `client`에 접근하지 않음). 한도 안에 엔진이 `CLOSED`에 도달하는지 기다린다.
  3. 현재 단계의 마감(정상 종료 유예 / 취소 / 정리)을 넘으면 같은 잠금 아래에서 상태와 단계를 읽고, 유예 마감이면 C17의 단일 전환으로 취소 단계에 넘기며, 취소 마감이면 `CLOSED`가 아니면 `QUIESCENCE_FAILED`를 확정한다. 이미 `CLOSED`면 아무것도 바꾸지 않는다.
  4. 확정 뒤 엔진이 뒤늦게 루프를 빠져나오면 해제 결정 지점(4.3 7a/7b)에서 상태를 읽고 `QUIESCENCE_FAILED`면 7b를 따른다. 자동으로 `CLOSED`가 되지 않는다.
  5. **감시 수명은 `CLOSED`에서 끝나지 않고 `IDLE` 또는 정리 실패 확정까지 이어진다.** 정리 단계의 절대 마감(C19)도 감시가 판정한다. 마감 전: 앱에는 `CLEANUP_DELAYED`(중간 보고)를 낼 수 있다. 마감 초과: 정리 실패 확정 기록 + `CLEANUP_FAILED` 보고(강제 해제 없음). 확정 뒤 정리가 늦게 끝나도 `IDLE`로 전환하지 않는다. 엔진이 정리를 마쳐 조건을 만족하면 감시는 종료한다.
- 감시 한도 기준은 개별 curl 취소 주기가 아니라 작업 전체의 종료 가능성이다(P7).

### 4.5 레지스트리 연산

| 연산 | 설명 |
| --- | --- |
| `try_register(kind)` | 잠금 → 허용 상태이면 해당 카운터++, 아니면 거부 |
| `unregister(kind, failure)` | 생성 실패 등: 실패 기록 후 카운터-- (같은 임계구역, C4) |
| `complete(kind, failure)` | 작업의 마지막 동작: 실패 기록 후 카운터--, 모든 카운터 0이면 대기자 깨움 |
| `request_cancel()` | 잠금 → 수락·중복 판정·진행 중 취소 카운터++ (C17) → 잠금 해제 → 연결 참조 확보 후 `shutdown` → 잠금 → 참조 반환·카운터-- |
| `conn_register(fd)` / `conn_unregister_wait(fd, deadline)` | 4.6 |
| `close_begin()` | 잠금 → `CLOSING` |
| `wait_and_close(deadline)` | 엔진: 조건변수 대기 → C13 세 조건이 참이면 `CLOSED`, 한도 도달이면 `QUIESCENCE_FAILED` |
| `record_error(source, code)` | 첫 오류만 저장(`source`, `code`, 기록 순서, 스레드 종류), 총 오류 수 증가 |
| `declare_failed(reason)` | 감시 또는 엔진: 잠금 아래 `ACTIVE`/`CLOSING`에서만 `QUIESCENCE_FAILED` 확정 |

취소는 **전용 단기 스레드**에서 실행한다(v2의 호출자 스레드 동기 실행 권고는 철회: 취소 실행이 `shutdown`에서 지연되면 같은 스레드가 마감을 판정할 수 없다). 생성은 C2의 예약→생성→실패 처리 규칙을, 중복 요청과 생성 실패·재시도·결과 전달은 C17을 따른다. 마감은 레지스트리의 절대 마감 시각 하나를 엔진 대기와 감시가 공유하며 실행 주체와 판정 주체는 분리된다. 개시가 계속 실패하면 한도 안에서 재시도한 뒤 `QUIESCENCE_FAILED`로 수렴한다.

### 4.6 연결 등록과 참조 규약 (C14)

- 등록 지점: `idevice_connect` 성공 직후 `conn_register`, `idevice_disconnect`의 `close` 직전 `conn_unregister_wait`(S4). 프록시 외부 호스트 소켓은 별도 등록 지점. 다른 경로(libusbmuxd 소켓 등)는 취소 대상에서 제외하고 사유를 기록한다.
- 취소 측: 잠금 아래에서 대상 항목의 참조를 확보(목록 복사) → 잠금 해제 → 항목마다 `shutdown(SHUT_RDWR)` → 잠금 아래 참조 반환·신호.
- 소유 측: 닫기 전에 잠금 아래에서 등록 해제 → 참조 반환을 한도 안에서 대기 → 반환되면 `close`. 한도 초과면 **닫지 않고** 실패를 기록한다. 참조가 남은 fd를 강제로 닫지 않는다(fd 재사용 경쟁 방지).
- `shutdown`의 대기 해제 효과는 Linux에서도 아직 가정이다(V5). Android는 보장하지 않는다.

### 4.7 최종 결과 합성

복원 결과와 세션 정리 결과를 분리한다. 일반 복원 실패나 사용자 취소라도 정리가 안전하게 끝났으면 `IDLE`로 돌아가 재시도할 수 있다.

| 복원 결과 | 정리 결과 | 최종 보고 | 세션 상태 |
| --- | --- | --- | --- |
| 성공 | 완료 | 성공 | `IDLE` |
| 일반 실패 | 완료 | `RESTORE_FAILED` | `IDLE` |
| 사용자 취소 | 완료 | `ABORTED_BY_USER` | `IDLE` |
| 성공 또는 실패 | 진행 중 | `CLEANUP_DELAYED`(중간 보고, 최종 아님) | `CLOSED` |
| 성공 또는 실패 | 실패 확정 | `CLEANUP_FAILED`(재시도 불가) | `CLOSED`(정리 실패 기록 유지), 신규 세션 금지 |
| (작업 미종료) | 해당 없음 | `SESSION_NOT_QUIESCENT`(재시도 불가) | `QUIESCENCE_FAILED` |

`CLOSED` 유지는 정리 실패 기록이 있는 채로 남는다는 뜻이며 정리가 끝났다는 뜻이 아니다. 최종 보고는 세대당 한 번 확정되고(C9), 중간 보고 뒤 정리 완료·실패가 오면 그 결과가 최종으로 한 번 확정된다. 첫 오류 기록과 최종 보고 종류는 별도로 저장해 정리 실패가 최초 오류를 지우지 않는다.

## 5. 결정 (D1~D8)

### D1 완료 대기 방식과 종료 판정

- 제약: C1~C5, C12, C13, C17.
- 대안: (a) 작업 종류별 카운터+조건변수, (b) 작업 목록+`thread_join`.
- 비교: 비동기 스레드는 detach되어 핸들이 없고 생성 지점이 `restore.c` 한 곳이다. (b)는 한도 있는 join이 이식성 있게 제공되지 않는다. (a)는 `pthread_cond_timedwait`로 한도를 주기 쉽다.
- **권고: (a).** 종료 판정은 하나다 — C13의 세 조건.
- 검증: T1a, T3, T9, T14, T15. 실패 시 대안: 잠금 순서에 결함이 나오면 잠금 범위를 줄인다(구조는 유지).

### D2 대기 한도, 취소, 감시

- 제약: C6, C11, C14, C16, C17. 소스는 작업 단위의 종료를 보장하지 않는다(P7).
- 대안: 일괄 한도 / 작업 종류별 한도 / 단계별(자연 완료 유예 → 취소 → 재대기).
- **권고: 단계별.** 취소는 전용 스레드에서 실행하고 마감은 절대 단조 시각으로 공유한다(4.5, C17, C19). 정상 종료는 취소 없이 유예 한도까지, 오류 종료는 즉시 취소 후 취소 한도까지 대기한다. 한도 값은 T7 관측 전에는 정하지 않는다. 취소는 원자 취소 플래그와 연결 `shutdown`(4.6)이다. `close`는 취소 수단이 아니다. 호스트 감시는 4.4를 따른다. 취소 요청은 C17로 단일화한다.
- 검증: T5, T6, T7, T8, T14, T15, T17. 실패 시 대안: `shutdown`이 깨우지 않으면 취소 한도를 길게 두고 `QUIESCENCE_FAILED` 수렴에 의존한다(안전 측).

### D3 오류 보존과 실패 전파 (P10)

- 제약: C8, C9.
- 대안: A 첫 오류 보존 / B 오류 직후 탈출 / C A+B.
- **권고: A.**
  1. 루프의 `err` 대입 직후에서 `err < 0`이면 `record_error(source, code)`를 부른다(첫 오류만 저장). 비동기 처리기는 `async_err` 대입을 같은 `record_error`로 대체한다.
  2. **비동기 오류 발생 시**: 첫 오류 기록과 종료 요청(레지스트리의 원자 종료 플래그, 기존 `flags |= FLAG_QUIT` 대체)을 한 호출에서 동기화한다. 루프는 반복 맨 앞에서 종료 요청을 본다.
  3. **표현(정확):** 종료 요청 이후에도 루프 구조상 추가 메시지 수신과 처리 경로에 진입할 수 있으며, 수신 결과와 처리기 동작에 따라 실제 종료 시점이 달라진다. 종료 플래그 확인 지점(반복 맨 앞)과 실제 탈출 조건은 별개다.
  4. 종료 순서 7a에서 최종 `err`를 합성한다: 첫 오류가 있으면 그 코드(음수), 없고 `async_err`도 없으면 기존 `err`. **합성은 `CLOSED` 확정 뒤**에 한다(C9). `QUIESCENCE_FAILED`면 결과는 실패이고 첫 오류와 사유를 함께 돌려준다.
  5. 호스트 방어 확인: `idevicerestore_start`가 0을 돌려줘도 레지스트리에 첫 오류가 있으면 `HV_INSTALL_FAILED`로 보고한다(호스트만의 변경).
  6. 메시지 처리 순서는 바꾸지 않는다. **오류 이후 추가 메시지 처리의 부작용(장치로의 추가 전송 등)은 그대로 남는다 — 허용하는 한계.**
  7. 호스트는 해제될 수 있는 `client`에 접근하지 않는다(C16).
- 오류 식별 정보: `{source(처리기·메시지 종류 열거), code, 기록 순서, 스레드 종류}`. TSS 분류기 결과는 별도 TSS 기록(`tss-integration-design.md` 3.4)이며 첫 오류 기록이 그 항목을 `source`로 참조한다.
- 검증: T2-보존, T2-전파((a)~(d)와 대조군), 변경 전 기준선과 변경 후 회귀. 실패 시 대안: 추가 메시지의 부작용이 문제로 나오면 B를 추가 검토하되 먼저 장치 프로토콜 영향을 시험으로 확인한다. B는 현 단계에서 선택하지 않는다.

### D4 공유 연결 직렬화

- 제약: C10. 한 메시지가 두 번의 송신이다(P17).
- 대안: (a) `restored_send` 안의 연결별 뮤텍스(벤더링 `libimobiledevice/src/restore.c`), (b) `restore.c` 호출 지점 전부를 래퍼로 교체, (c) 호스트가 연결 계층을 가로챔.
- **권고: (a).** 단일 진입점이어서 한 곳 변경으로 모든 호출자를 덮는다. 뮤텍스는 `restored_client` 생성 시 초기화, 연결 해제 시 파기(`CLOSED` 이후라 사용 중 파기되지 않는다, C6). 수신은 확인한 범위에서 루프 스레드만 호출한다(구현 승인 전에 재확인).
- 주의: `restored_client_free`의 `restored_goodbye`는 같은 연결에 송신·수신하므로 비동기 작업이 끝난 뒤에만 호출한다(C6, S5).
- 검증: T4. 실패 시 대안: 송신 잠금으로 해결되지 않는 순서 문제가 나오면 `DataPort` 없는 비동기 요청을 루프에서 직렬 처리(D5)하는 안을 해당 종류에 한해 재평가한다. 비동기 응답 순서가 장치에 영향을 주는지는 실기 검증(V2).

### D5 비동기 종류를 동기로 전환

- **권고: 채택하지 않는다(대안으로만 유지).** 프로토콜 호환성과 루프 블로킹(장시간 `SystemImageData` 중 다른 메시지를 못 받음)이 미검증이다.

### D6 앱 보고

- 제약: C9, C11, C15.
- **권고:** `host/install.c`에 실패 종류 조회를 추가한다(`hv_install_result()`의 0/-1은 유지). 종류: `RESTORE_FAILED`(정리 완료 후 재시도 가능), `SESSION_NOT_QUIESCENT`(같은 프로세스에서 새 복원 불가; 사유 `tasks_not_quiescent`/`engine_not_exited`/`conn_ref_not_returned`), `CLEANUP_DELAYED`(**중간 보고**; 정리 진행 중, 최종 결과 아님, 성공으로 보고 금지, `IDLE` 전까지 새 세션 거부), `CLEANUP_FAILED`(정리 한도 초과 또는 정리 오류로 확정; 결과 실패, 재시도 불가, 프로세스 재시작 필요), `ABORTED_BY_USER`(정리 완료 후 재시도 가능). 합성 규칙은 4.7을 따른다. 재시도 가능 여부 표시는 세션 상태와 일치하며, 종료 실패를 성공이나 재시도 가능으로 표시하지 않는다.
- Android Activity 재생성이나 화면 재시작은 네이티브 프로세스 종료가 아니다. 프로세스가 종료되지 않으면 남은 스레드와 전역 정책 상태가 유지되므로 앱은 프로세스 종료를 요청해야 한다. 재시작이 장치 측 복원 상태를 정상화한다는 보장은 없다.
- 진행 콜백: 시작 시 `g_progress`/`g_progress_user`를 복사해 쓰고, 전역 변수를 `IDLE` 이후에 읽지 않는다(C15, S8).
- 검증: T5, T6, T11, T16, T23. 대안 없음(앱 표시 문제로 국한).

### D7 객체 소유권

| 구분 | 결정 |
| --- | --- |
| 소유권 | 서비스·ASR 연결은 처리기 소유(현행 유지). `client`, `client->restore`, 공유 restored 연결은 엔진 소유(현행). 레지스트리·세션 기록·연결 등록 항목은 레지스트리 소유 |
| 소유권(build_identity) | 호스트 설정: 독립 소유권 없음(`build_manifest` 종속). `FLAG_CUSTOM` 사본만 `idevicerestore_start` 소유(`needs_free`), 해제는 C18 판단표를 따름 |
| 사용 권한 | 처리기는 등록~`complete()`까지만 세션 객체를 참조한다. `complete()` 이후에는 세션 객체를 건드리지 않는다(C4). 취소 측은 연결 항목의 참조를 확보한 동안만 해당 fd에 접근한다(C14) |
| 종료 책임 | 취소 실패 시 엔진이 세션 객체를 모두 유지하고 호출자(`install.c`)도 레지스트리 조회(C18)로 해제를 생략한다(C11). `build_identity`는 호스트 설정에서 `build_manifest`의 하위 노드이므로 `idevicerestore_client_free` 생략으로 함께 유지된다(S9, C18). 완료된 작업의 독립 자원은 정리된다 |

- 처리기가 연결을 소유해도 세션 종료는 작업 종료를 확인한다. 세션이 연결 소유권을 넘겨받는 안은 채택하지 않는다.
- 검증: T3, T5, T9, 해제 감시(AddressSanitizer). 실패 시 대안: 처리기의 늦은 참조가 발견되면 해당 필드를 처리기 시작 시점에 지역 복사하게 바꾸되 `client` 자체는 C6으로 유지한다.

### D8 리버스 프록시 종료 보장

- 제약: C2, C3, C4, C7. S1~S3.
- 판단: 프록시는 `client` 해제 전에 join되는 순서(P15)로 부분적으로 묶여 있으나 (1) 연결 스레드 핸들 유실, (2) 무기한 join, (3) 제어·연결 스레드 등록 없음이 있다.
- **권고:**
  1. 제어 스레드와 연결 스레드 모두 같은 등록·완료 규칙을 쓴다(C1, C2, C4). 제어 스레드 생성도 `ACTIVE` 검사를 거친다(거부되면 `start_proxy` 실패).
  2. 정상 종료의 유예 단계에서는 신규 연결 차단(`CLOSING` 전환, 등록 시 거부)만 하고 기존 연결 `shutdown`은 취소 단계에서만 한다(4.3의 5a/5b). `CLOSING` 이후 연결 요청은 거부하고, 제어 스레드는 `running = 0`으로 빠져나온다. 이것이 장치 측 연결 요청을 적절히 종료시키는지는 별도 검증 대상이다(V9).
  3. 연결 스레드의 완료 통지는 자신의 연결 클라이언트 해제 뒤에, 제어 스레드의 완료 통지는 자신의 마지막 객체 접근 뒤에 한다. 연결 스레드 수를 세어 핸들 유실을 제거한다.
  4. 종료를 **요청 / 한도 있는 완료 확인 / 해제**로 분리한다. 종료 요청은 플래그 설정과 연결 `shutdown`만 하며 join하지 않는다. 해제는 완료 확인 뒤에만 호출한다. 프록시 루프는 종료 플래그를 확인한다.
  5. 완료 확인 한도 도달 시 프록시 객체를 유지하고 `QUIESCENCE_FAILED`로 수렴한다.
  6. `client->parent` 비원자 접근은 종료 플래그로 대체하거나 원자 접근으로 바꾼다.
- 범위 판단: 리버스 프록시는 공통 수명 관리 대상에 포함한다.
- 검증: T12, T13. 실패 시 대안: `reverse_proxy.c` 수정이 승인되지 않으면 프록시 정리를 별도 감시 스레드에서 한도 있게 수행해 실패 시 `QUIESCENCE_FAILED`로 처리한다.

## 11. 교차 검증 (K1~K6 × 일곱 종료 경로 + 두 경쟁)

(v2의 여섯 경로 중 "`CLOSED` 이후 정리 지연"을 지연 / 실패 확정으로 나누어 일곱 경로로 점검한다.)

### 11.1 종료 경로 점검표

| 경로 | 상태 처리 | 해제 주체·시점 | 훅 | 새 세션 허용 | 결과 보고 |
| --- | --- | --- | --- | --- | --- |
| 정상 종료 | `ACTIVE→CLOSING→CLOSED→IDLE` | 엔진: `CLOSED` 확정 뒤 프록시→`restore_client_free`, 호출자: `idevicerestore_client_free`→`end()` | `end()`에서 제거 | `IDLE`부터 | 첫 오류 없음 → 성공 |
| 오류 종료 | 첫 오류 기록→취소→`CLOSING→CLOSED→IDLE` | 동일 | 동일 | `IDLE`부터 | 첫 오류가 있으면 실패(C8, C9) |
| 취소 실패 | `QUIESCENCE_FAILED`(`tasks_not_quiescent`/`conn_ref_not_returned`) | **세션 전체 정리 없음**; 완료된 작업의 독립 자원만 처리기가 해제 | 유지 | 거부(종단) | `SESSION_NOT_QUIESCENT`(실패) |
| 루프 미종료 | 감시가 `QUIESCENCE_FAILED`(`engine_not_exited`) 확정 | 해제 없음. 엔진이 뒤늦게 탈출하면 7b | 유지(엔진 등록 수>0, 상태≠`CLOSED`) | 거부 | `SESSION_NOT_QUIESCENT` |
| 감시 경합 | 같은 잠금에서 선착순: 감시의 `declare_failed`와 엔진의 `CLOSED` 중 먼저 확정된 쪽 | 해제 권한은 `CLOSED` 보유 엔진만 | `CLOSED`면 `end()`가 제거, 아니면 유지 | 결과에 따름 | `CLOSED`가 먼저면 감시는 상태 불변·보고만 |
| `CLOSED` 이후 정리 지연 | `CLOSED` 유지, 감시가 정리 마감까지 관찰(C19) | 엔진이 계속 해제 | 정리 후 `end()` | `IDLE` 전 거부 | `CLEANUP_DELAYED`(중간), 최종은 정리 완료 후 한 번 확정 |
| 정리 마감 초과·정리 오류 | `CLOSED` + 정리 실패 확정 기록 | **강제 해제 없음**, 늦게 끝나도 `IDLE` 불가 | 유지 | 거부 | `CLEANUP_FAILED`(재시도 불가) |

### 11.2 두 경쟁

| 경쟁 | 처리 | 근거 |
| --- | --- | --- |
| 취소 요청 수락 vs `CLOSED` 전환 | 수락·카운터 증가와 `CLOSED` 판정(취소 등록 차단 포함)이 같은 잠금. 먼저 수락되면 카운터>0이라 `CLOSED` 불가, 먼저 `CLOSED`면 "종료된 세션에 대한 요청" 거부 기록 | C13(c), C17 |
| 참조 반환 실패 기록 vs 정상 종료 판정 | 한도 초과 기록은 C13 (b)를 거짓으로 만들어 카운터 0이어도 `CLOSED` 불가. 기록이 `CLOSED` 이후에 도착하면 (완료 통지 전 기록 원칙 C4 때문에) 소유자 쪽 규약상 발생하지 않음 — 발생한다면 규약 위반이므로 정리 진단과 `IDLE` 금지로 처리 | C4, C14 |

### 11.4 v1 → v2 교차 점검에서 찾은 모순과 처리

1. 프록시 정리가 한도 있는 대기보다 앞이라 무기한 join이 한도를 무력화 → "요청/한도 있는 확인/해제"로 분리, 7a에서만 해제(D8).
2. 활성 수 범위가 비동기 요청뿐이라 종료 판정이 둘이 될 수 있음 → 종류별 카운터 4종과 단일 판정 C13.
3. C11 "아무것도 해제하지 않는다"와 D7 "처리기가 자기 연결을 닫는다" 충돌 → 세션 전체 정리 금지, 완료된 작업의 독립 자원은 해제 가능.
4. 비동기 첫 오류 뒤 종료 요청 경로 없음 → D3 2항.
5. `CLOSED`와 감시 결과의 의미 충돌 → `CLOSED`는 작업 정리 완료+해제 권한, 감시는 `CLOSED` 뒤 상태 불변(4.4).
6. 연결 `shutdown`을 잠금 중에 호출 → C12와 충돌 → 참조 규약(C14).
7. 취소 수락과 `CLOSED` 경쟁 → C13(c), C17.
8. 새 발견(S8): `begin()`이 엔진 수만 보고 `IDLE`을 모르며, 진행 콜백이 `end()` 뒤 전역을 읽음 → C15, D6, I2, I7.
9. 새 발견(S7): 조기 반환 경로가 `end()`·`g_result`를 건너뜀 → I7 정리 항목(기존 결함 후보).
10. 새 발견(S6): 호스트는 `global_quit_flag`로 루프를 멈출 수 없고 `client`는 해제될 수 있음 → C16.
11. 취소 작업 예약·생성·실패 처리(C2, C17, 4.5)와 실패 기록·완료 통지 순서(C4)를 명시.

### 11.5 v2 → v2.1 변경

1. 반환 계약(C18): 일반 실패와 수명 실패를 반환값이 아니라 레지스트리 조회로 구분. `restore_device`는 항상 음수(S9 근거).
2. 취소: 호출자 동기 실행 철회 → 전용 스레드, 절대 마감 공유(4.5), 예약·생성 실패·실행 완료 세 상태와 결과 전달(C17).
3. 정상 종료의 프록시 처리: 신규 연결 차단(`CLOSING` 전환, 등록 시 판정)과 기존 연결 `shutdown`(취소 단계)을 분리(4.3 5a/5b, D8).
4. 정리 실패: `CLEANUP_DELAYED`(중간)와 `CLEANUP_FAILED`(확정) 구분, 감시 수명을 `IDLE`/정리 실패 확정까지 연장(4.4, C19).
5. `IDLE` 조건에서 복원 결과와 정리 결과 분리(C15, 4.7). 일반 복원 실패 후 정리가 끝났으면 재시도 허용.
6. 세대 번호와 불일치 통지 거부(C15), 최종 결과 단일 확정(C9), 단조 시계(C19, V12).
7. I8의 시험 범위를 `T1~T24`로 정정(T18 누락 포함), 시험 T19~T24 추가.

### 11.6 v2.1 → v2.2 변경

1. C9: 카운터 0 조건은 `CLOSED` 정상 완료 경로 한정, `QUIESCENCE_FAILED`는 카운터>0에서도 실패 확정·보고하는 예외로 명시.
2. 4.3·4.4·C17: 정상 종료는 유예 마감에서 곧바로 실패 확정하지 않고 취소 단계를 거친 뒤 취소 마감에서 7b. 감시는 현재 단계 마감만 판정, 유예→취소 전환은 단계 전환·취소 예약·카운터 증가를 한 임계구역에서 단일 실행.
3. S9·C18: 소스 확인 결과 호스트 설정(`FLAG_ERASE`)에서 `build_identity`는 `build_manifest`의 하위 노드이고 `needs_free`는 `FLAG_CUSTOM`일 때만 1이다. v2.1의 "일반 실패 경로의 `build_identity` 누수" 가정은 **철회**. 해제 판단표(훅 NULL·조회 실패·세대 불일치 포함)는 `FLAG_CUSTOM` 사본용 방어 장치(I10, 선택)로 정리. 호스트 반환 계약(레지스트리 조회로 `idevicerestore_client_free`·`end()` 생략)은 유지.
4. 세대 불일치 조회 실패는 세션 오류가 아니라 세션과 무관한 진단 기록으로 귀속(C15와 일치).
5. 시험 T25~T28 추가, I8을 `T1~T28`로 정정, I10 추가(구현 항목은 I1~I10).

## 12. 한계와 남은 위험

- **종료 시간 상한**: `CLOSED` 이후 정리는 상태를 `QUIESCENCE_FAILED`로 되돌리지 않으므로 안전은 유지되나 시간 상한은 보장되지 않는다. `restored_client_free`의 Goodbye 응답 대기와 이벤트 구독 해제가 호출당 한도 안에서 블로킹할 수 있다(S5). irecv 구독 해제의 블로킹은 전부 읽지 못했다.
- **루프 정지**: 종료 트리거 없이 멈춘 엔진은 감지하지 않는다(V10).
- **관측**: P10 성공 오보고, 비동기 수명 결함, 공유 연결 프레이밍 손상, 프록시 스레드 유실, `begin()`/콜백 경합은 모두 코드상 위험이며 실행 관측은 없다. 변경 전 기준선 시험(I8)으로 먼저 관측한다.
- **플랫폼**: `shutdown` 효과, 새니타이저, 링크 가로채기, `CLOCK_MONOTONIC` 조건변수(V12)는 Android 검증 전까지 보장하지 않는다.
- **정리 한도 값**: 값은 미정(V13)이며 집행 방식만 확정이다. 정리 호출 자체는 중단하지 않으므로 마감 초과 뒤에도 정리 스레드는 남을 수 있다(`CLEANUP_FAILED` 보고, 객체·훅 유지).
- **판정의 층**: 이 문서의 충족 판정은 설계 문장 사이의 정합성이다. CI 성공은 실제로 실행된 검사에 한정한다.

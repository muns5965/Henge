# 안드로이드 포팅 — 부팅 및 장치 호환성 검증 기록

이 문서는 Henge 안드로이드 포팅에서 VMApple 게스트가 정상 부팅을 마치지 못하고 리셋되는 현상을 조사하면서 확보한 사실, 미확인 가설, 철회한 주장을 기록한다. 새로운 근거가 나오면 기존 항목의 판정을 갱신하고, 철회 사유는 남긴다.

**공개 범위:** Henge 자체의 소스코드, 장치 에뮬레이션, 호스트 측 ROM 적재 경로 및 VM 실행 로그. Apple의 독점 부트 ROM(AVPBooter.vmapple2.bin)에 대한 명령어 단위 디스어셈블리, 내부 검증·리셋 분기 주소 목록은 포함하지 않는다.

## 판정 기준

- **확인됨:** 실제 소스코드나 식별 가능한 실행 로그로 확인된 사실.
- **구현 확인됨:** Henge 코드의 동작은 확인됐으나 실제 Apple Virtualization.framework와의 일치 여부는 검증하지 못한 사항.
- **미확인:** 확보한 근거와 모순되지는 않지만 아직 입증되지 않은 가설.
- **철회됨:** 앞서 주장했지만 근거가 없거나 틀린 것으로 밝혀져 더 이상 결론으로 사용하지 않는 설명.

## 1. ROM 적재와 CPU 초기화 — 확인됨

- 안드로이드 앱의 MainActivity.java에 있는 findLocalRom()/isGenuineRom()은 앱 외부 전용 폴더의 vm/rom.bin을 우선 찾고, 없거나 검증에 실패하면 내부 저장소의 vm/AVPBooter.vmapple2.bin을 확인한다. 파일 크기와 SHA-256이 앱의 기대값과 일치하는 경우에 사용한다. 이 검증은 기대한 파일과의 일치 확인이지 Apple 원본 여부에 관한 독립적인 증명은 아니다.
- host/vmrun.c는 --rom, --disk, --aux를 파일 경로로 받아 설정에 저장한다. 이 인자 파싱 단계에서는 ROM 내용을 읽지 않는다.
- host/vm.c의 hv_vm_create()는 ROOT/AUX 저장장치를 열고 가상 하드웨어를 구성하는 hv_vmapple_create()를 실행한 뒤 ROM 파일을 적재한다.
- devices/vmapple.c는 펌웨어용 1MiB 영역을 VMAPPLE_FIRMWARE=0x00100000에 배치한다. 메인 RAM은 0x70000000부터 시작하므로 별도 영역이다.
- hv_vmapple_load_rom()은 파일에서 최대 1MiB를 fread()로 해당 영역에 복사한다. 이 함수에서 별도 압축 해제, 구조 파싱, SHA-256 검사는 하지 않는다. 새로 할당한 익명 메모리 영역의 미사용 부분은 0으로 초기화된다. 펌웨어 영역은 현재 Henge에서 쓰기 가능한 RAM으로 등록된다.
- hv_vmapple_reset_cpu()는 CPU0의 시작 PC를 0x100000으로 설정한다. 초기 상태는 EL1, MMU 비활성화, 인터럽트 마스킹 상태이며 보조 CPU는 PSCI CPU_ON을 기다린다.

**판정:** ROM 로더가 파일 내용을 재배치하거나 변형한다는 근거는 발견되지 않았다. 다만 ROM 실행 이후에도 Henge가 제공하는 장치 응답과 예외 처리가 실행 결과에 영향을 미치므로, 부팅 실패의 원인을 ROM 자체로 한정할 수 없다.

## 2. CFG 설정 장치 — 확인됨

devices/cfg.c는 VMAppleCfg 구조체를 MMIO 장치로 노출한다. CPU 수, ECID, RAM 크기, 설치기 모드 설정값(run_installer1/run_installer2), MAC 주소, 시리얼·모델·SoC 이름 및 난수 관련 레지스터 등이 포함된다.

- 일반 부팅에서 run_installer1=0, run_installer2=0이다.
- 설치기 부팅에서 host/vm.c는 두 값을 모두 1로 설정한다.
- HV_RUN_INSTALLER 환경변수를 설정한 실험에서는 두 값을 개별적으로 지정할 수 있다.
- Android의 기존 순수 일반 부팅 시험에서는 ECID=0, seed=0이었다. iOS의 신규 가상머신 설치 준비에서는 별도의 ECID를 생성하므로 두 경로의 모든 조건이 동일하지는 않다.

**판정:** Henge가 게스트에 전달하는 CFG의 구현과 시험 설정은 확인됐다. 개별 값이 일반 부팅 리셋을 유발하는지는 아직 확인되지 않았다.

## 3. BDIF 장치 — 확인됨 / 구현 확인됨

### 3.1 장치 선택과 저장장치 처리

devices/bdif.c는 접근 오프셋에 DEVID_MASK를 적용하여 다음 장치를 구분한다.

| 장치 | 식별값 |
|---|---|
| ROOT | 0x00000000 |
| AUX | 0x00010000 |
| USB | 0x00100000 |

ROOT/AUX의 REG_NEXT_DEVICE(+0x420)는 게스트가 볼 수 있는 저장장치 크기를 512바이트 섹터 수(disk->size / 512)로 반환한다. 기존 상세 로그에서 AUX 용량 0x10000(65,536섹터)이 확인됐으며 §4의 파일 크기와 일치한다.

저장장치의 읽기·쓰기 요청은 command()에서 각각 hv_disk_read()/hv_disk_write()로 처리한다. 로그 수준 2 이상 또는 오류 상황에서는 장치 이름, 섹터, 길이, 플래그, 성공 여부를 기록한다. 성공 기록은 호스트 입출력이 완료됐다는 뜻이지, 게스트의 데이터 내용 검증에 성공했다는 뜻은 아니다.

### 3.2 USB 미노출 슬롯의 공통 폴백 — 구현 확인됨, 호환성 검증 후보

현재 bdif_read()에서 USB 장치가 존재하는 경우에만 전용 usb_read()가 호출된다. b->usb가 NULL이면 DEVID_USB 접근도 ROOT/AUX에 사용되는 공통 switch로 내려간다. USB 미노출 시 반환값은 소스코드로 확인되었으며, 2026-11-17 상세 MMIO 로그(§7-1·§7-2)에서 ROM이 실제로 해당 값을 읽은 사실도 확인되었다. 아래 표는 그 소스 정의 값이다.

| 레지스터 | USB 미노출 시 Henge 반환값 | USB 노출 시 Henge 반환값 |
|---|---|---|
| REG_STATUS(+0x0) | 1 | 1 |
| REG_CFG(+0x4) | 2 | 0x1A01 |
| REG_NEXT_DEVICE(+0x420) | ~0ull | ~0ull |

USB 포트가 없어도 상태 레지스터는 1, 유형 레지스터는 2를 반환한다. USB 미노출 상태에서 ROM이 실제로 이 슬롯에 접근하고 REG_CFG=2를 읽는다는 사실은 2026-11-17 상세 MMIO 로그로 확인됐다(§7-1). 그 직후 진단성 CFG 기록과 PSCI SYSTEM_RESET이 이어지는 것도 확인됐지만(§7-2), 해당 반환값이 리셋의 직접적인 원인인지는 아직 입증되지 않았다. 실제 Apple Virtualization.framework의 비어 있는 슬롯 동작과 다른지도 확인되지 않았다. **확정된 결함이 아니라 소스 및 실행 로그로 확인한 구현 특성 및 검증 후보**로 기록한다.

## 4. AUX 파일 구조 — 확인됨

- host/vm.c는 AUX 파일을 열 때 기본 오프셋 16,384바이트를 지정한다. host/disk.c의 hv_disk_read()는 실제 파일 접근 위치에 이 오프셋을 더한다. 따라서 게스트 AUX 섹터 0은 파일 오프셋 16,384에서 시작한다.
- host/disk.h는 파일 앞 16KiB를 게스트에 보이지 않는 메타데이터 영역으로 설명하며 QEMU vmapple의 관례를 언급한다.
- host/vmrun.c의 make_aux()는 처음 24바이트에 고정 헤더를 기록한 다음 ftruncate()로 파일 전체 크기를 33,570,816바이트로 확장한다.
- 신규 파일의 24바이트 이후 영역은 0으로 초기화되므로 최초 생성 직후 게스트 가시 영역도 모두 0이다. 실제 VM 실행 이후에도 값이 계속 0이라는 일반적 보장은 아니다.
- 게스트 용량은 33,570,816 - 16,384 = 33,554,432바이트, 즉 32MiB = 65,536섹터(0x10000)이다.

### iOS와 Android의 신규 AUX 생성 결과 비교 — 확인됨

ios/Henge/Native/henge-vm.c의 henge_make_aux()와 host/vmrun.c의 make_aux()는 동일한 24바이트 헤더를 기록하고 동일한 크기로 확장한다. **새로 생성되는 파일의 바이트 내용과 크기는 동일하다.** iOS의 Installer.swift에서도 신규 가상머신을 준비할 때 henge_make_aux()를 호출한다.

주석은 완전히 같지 않다. iOS 쪽은 ‘64바이트 헤더’라고 표현하지만 실제 고정 헤더 쓰기는 24바이트이며, Android 쪽 주석은 24바이트라고 설명한다. 이 차이는 파일 생성 결과를 바꾸지 않는다.

**판정:** 빈 AUX 생성은 Android 포팅에서 새로 도입한 방식이 아니라 기존 Henge iOS 구현과 동일한 초기화 방식이다. 하지만 이 사실만으로 빈 AUX가 설치 완료 후 일반 부팅에도 충분하다는 점이 증명되는 것은 아니다.

## 5. 철회된 인과 가설 — 철회됨

### ‘빈 AUX → 개인화 검증 실패 → 리셋’ 주장

이전 분석에서는 AUX 가시 영역이 0이라는 사실과 게스트의 SVC 호출을 연결해, 개인화 검증에 실패하고 특정 상태값이 설정돼 리셋된다고 결론지었다. **이 인과관계는 입증되지 않았으므로 철회한다.**

- AUX 읽기 성공은 데이터의 의미 또는 유효성에 관한 판정이 아니다.
- core/exception.c에서 SVC #0은 Henge가 서비스 의미를 직접 판정하는 경로가 아니라 게스트 EL1 예외 핸들러로 전달된다.
- SVC 호출 관측만으로 개인화 검증의 존재, 성공·실패 또는 리셋 원인을 확인할 수 없다.
- 신규 빈 AUX는 iOS 구현에서도 사용된다. 이는 ‘빈 AUX는 항상 즉시 거부된다’는 단정을 약화하지만, 설치 후 일반 부팅에 필요한 AUX 상태를 입증하지는 않는다.

향후 직접적인 비교 자료가 나오기 전까지 이 인과관계를 다시 확정 사실로 사용하지 않는다.

## 6. 부팅 모드별 실험 — 실행 사실 확인됨 / 원인 미확인

### 6.1 USB 장치 포트 노출 조건

devices/vmapple.c는 run_installer1, run_installer2 중 하나가 참이거나 HV_USB_ON_NORMAL 환경변수가 있을 때 가상 USB 장치 포트를 생성한다. Henge 소스 주석은 설치기 부팅에서 이 포트를 제공하는 구성을 Apple Virtualization.framework와 일치하는 것으로 설명한다.

HV_USB_ON_NORMAL은 일반 부팅 값(run_installer1/2=0)을 유지하면서 USB 포트만 추가하는 **기본 비활성화 실험 옵션**이다. 이 구성은 Henge의 표준 일반 부팅 구성이 아니다. 주석만으로 실제 Apple VZ의 모든 버전·조건에서 USB 장치가 반드시 동일하게 노출된다고 독립 확인한 것은 아니다.

### 6.2 일반 부팅 + USB 추가 실험

2026-11-14 빌드 144의 ‘일반 부팅 + USB 프로브’ 시험은 installer=0을 유지하면서 HV_USB_ON_NORMAL을 활성화한 비교 조건이다. 이 조건에서 USB 장치 접근과 별도 실행 경로가 관측됐다. 비표준 비교 조건에서 얻은 모든 결과를 순수 일반 부팅의 실행 경로로 일반화해서는 안 된다.

### 6.3 USB 미노출 순수 일반 부팅

2026-11-14와 2026-11-16의 두 순수 일반 부팅 시험은 USB 포트 없음, installer=0, ECID/seed=0, 신규 빈 AUX를 사용했다. **두 실행 모두 PSCI SYSTEM_RESET이 발생했다.**

- 11월 14일 로그와 11월 16일 로그는 PSCI 호출 지점의 게스트 내부 주소가 서로 달랐다(게스트 ROM 내부 명령어 주소는 위 "공개 범위"에 따라 기록하지 않는다).
- 두 실행 모두 종료 시 CPU0 PC는 서로 일치했다(구체적 주소는 게스트 ROM 내부 값이므로 비공개 기록).

**판정:** 인위적으로 USB를 추가한 것만으로 일반 부팅 리셋을 설명할 수는 없다. 단, PSCI 호출 주소에 차이가 있으므로 두 실행이 동일한 내부 분기에서 리셋됐는지는 미확인이다. USB 미존재 슬롯 폴백이 리셋의 직접 원인인지도 확인되지 않았다.

### 6.4 설치기(DFU) 모드 순수 부팅 — 리셋 없음, 로그 확인됨

2026-11-19, build 145, `vmrun --installer --ecid ... --log 3 --usb-probe --psci-log`(미설치 빈 ROOT/AUX, 매 실행 `--recreate-blank`). 30초 전체 실행 동안 **PSCI SYSTEM_RESET이 한 번도 발생하지 않았다.** 대신 CPU0이 타이머 레지스터 읽기(`mrs S3_3_C14_C0_2`)와 BDIF USB 영역 접근(`REG_QSEL(+0x410)` 쓰기, `REG_UNK1(+0x10)` 읽기)을 반복하는 루프에 머물렀고, `vmrun`이 "usb port: guest on the bus=1 session=1 ... DRIVER_OK=0"을 계속 보고했다. 30초 시간제한으로 `exit reason 7 (halt)`로 정상 종료됐으며, DFU 문자열의 ECID가 설정값과 일치했다. 화면 출력은 없음("boot display none").

**판정:** 설치기 모드는 ROM이 기대하는 대로 USB가 노출되므로(§6.1), §7 item 2에서 확인된 일반 부팅의 유형 불일치가 이 조건에서는 나타나지 않았고 리셋도 없었다. 관측된 루프는 실제 DFU 대기 상태(호스트의 USB 명령을 기다림)와 패턴이 일치하지만, 이것이 "정상적으로 진행 중"이라는 확정적 증거는 아니며 — 다른 이유로 같은 루프에 머물러 있을 가능성도 배제되지 않는다. §7 item 2의 "USB 불일치가 일반 부팅 리셋에 관여한다"는 가설과 모순되지 않는 방향의 관찰이다.

같은 ROM/AUX로 곧바로 실행한 `ui_runner_vm`(안전 실행기, 일반 모드 고정)에서는 리셋 대신 자체 내장 진단(`PANIC_DIAG`, 게스트 내부 주소이므로 비공개, `hits=1`, `x0=0xfffffffd`)이 한 번 걸린 채 30초 타임아웃까지 멈췄다. 화면에는 아무것도 그려지지 않았다(`frames 0`). 이 지점이 §7 item 2의 USB 비교 지점과 같은지 다른지는 확인하지 않았다 — 별도 계측이므로 섣불리 동일시하지 않는다.

### 6.5 설치기(DFU) 모드 + irecv 프로브 — 가상 DFU 장치 열기/조회/닫기 전부 성공, 로그 확인됨

2026-11-19, build 145, `vmrun --irecv-probe --installer --ecid ... --psci-log`(미설치 빈 ROOT/AUX, `--log 3` 없이 일반 상태 스냅샷만). 실제 `libirecovery` 라이브러리(복원 도구가 쓰는 것과 같은 라이브러리이며, 이 시험에서는 `vmrun` 자신에 함께 링크되어 "외부 호스트" 역할로 동작)가 Henge의 가상 DFU 장치를 PCI virtio-usb 경로(`05ac:1227`, PCI 슬롯 8)로 다음 단계까지 모두 성공적으로 수행했다:

- 장치 발견(`irecv_open_with_ecid` 성공), `GET_CONFIGURATION`/`SET_CONFIGURATION(1)` 수락, 인터페이스 클레임.
- 일련번호 문자열 읽기·해석: `CPID 0xfe00 CPRV 0x00 CPFM 0x03 SCEP 0x01 BDID 0x20 ECID 0x2d2a8d94f32ba4d2 IBFL 0x3c SRTG iBoot-10151.140.19` — ECID가 지정값과 일치.
- 장치표 조회 성공: `VirtualMac2,1` / `vma2macosap` / "Apple Virtual Machine 1", AP/SEP nonce 존재.
- 정상 종료(`irecv_close` → 0).

Henge 자신의 시험 도구가 보고한 결과: **"irecv probe: done, 0 stage(s) failed"** — 점검한 7개 항목(events/discover/open/info-serial/info-table/close/boundary) 전부 `ok`. 도구 자체가 다음을 명시적으로 단서로 남긴다: "opened and closed only; no firmware was sent, no TSS request made, nothing downloaded. A pass says libirecovery can open this virtual device, not that a restore will work." — 즉 이 결과는 가상 장치를 **열 수 있다**는 것만 증명하며, 복원 자체가 동작한다는 증거는 아니다.

프로브 종료 이후 30초 동안의 상태 스냅샷(세밀 트레이스 없이 몇 초 간격)에서는: CPU0의 `pc`가 두 값(비공개, 게스트 내부 주소) 사이를 오갔고 `esr_el1=0x56000000`(SVC64 예외 클래스)은 전 구간 동일했다 — 이 값이 스냅샷마다 새로 갱신된 것인지는 §3 분석의 단서대로 확정할 수 없다. CPU1은 시작부터 끝까지 `pc=0x100000, el=1`에 정지해 있었다. USB 상태는 "guest on the bus=1 session=1 (rom front-end owns port=1, PCI front-end DRIVER_OK=0)"로 전 구간 유지됐고, PSCI 리셋은 한 번도 없었으며 화면 출력도 없었다(`boot display none`). 30초 시간제한으로 `exit reason 7 (halt)`, 양쪽 CPU `halted=3`으로 정상 종료.

**판정:** ROM 측 BDIF 프런트엔드(게스트가 자신의 "연결" 상태를 올리는 쪽)와 PCI virtio-usb 프런트엔드(외부 호스트가 실제로 보고 통신하는 쪽)가 같은 가상 포트의 양 끝으로서 실제 USB/DFU 프로토콜 수준에서 끝까지 맞물려 동작한다는 것을 보여준다. §3.2/`devices/virtio_usb.h`에서 이미 구분한 `rom_on`/`pci_on`(PCI `DRIVER_OK`) 두 플래그 중, 이번 결과는 ROM 쪽이 아닌 PCI virtio-usb 경로로 실제 제어 전송이 왕복했다는 최초의 직접 확인이다. 다만 `DRIVER_OK=0`이 계속 유지된 것은 이 irecv 프로브가 PCI "드라이버"로서의 영구 연결을 맺는 것이 아니라 열기·조회·닫기만 수행했기 때문일 수 있으며, 이 프로브만으로 실제 복원(펌웨어 전송, TSS 요청)이 성공한다는 결론은 나오지 않는다. 또한 이 결과가 §6.4의 USB 폴링 루프가 "정상 DFU 대기"라는 가설을 강화하는 정황은 되지만, 그 루프 자체의 정체를 확정하는 것은 아니다.

**상세 로그로 재확인 (2026-11-19, build 146, 동일 시험을 `--log 3` 추가로 재실행).** 요약 결과는 동일하게 재현됐다("irecv probe: done, 0 stage(s) failed", 7개 항목 전부 `ok`). 프로브 종료 후 화면에 표시된 로그 꼬리(전체 20,752,572줄 중 마지막 200줄) 구간에서는, §6.4가 서술한 것과 같은 패턴 — 타이머 레지스터 읽기(`mrs S3_3_C14_C0_2`) → BDIF `REG_QSEL(+0x410)` 쓰기(값 0) → `REG_UNK1(+0x10)` 읽기(값 0) — 가 이 구간 전체에서 끊김 없이 반복되는 것이 MMIO 단위로 직접 확인됐으며, 이 구간에 PSCI 호출은 전혀 없었다. 종료 시 CPU0 레지스터는 `esr_el1=0x56000000`(SVC64 예외 클래스, §6.5 상단과 동일), `far_el1=0`, `sctlr_el1=0x448d520d` — `pc`·`elr_el1`·`vbar_el1`은 게스트 ROM 내부 코드 주소이므로 이 문서에는 값을 적지 않으며, 다만 이전 관측값들과 일치한다는 사실만 기록한다. 이것이 같은 예외 상태가 반복 관측되는 것인지, 우연의 일치인지는 확정하지 않는다. CPU1은 이번에도 끝까지 별도 동작 없이 멈춰 있었다(세부 레지스터는 §6.5 상단과 동일 패턴). **이 재실행은 §6.5의 기존 결론을 바꾸지 않으며, 거친 간격 스냅샷으로 추정했던 폴링 루프의 정체를 MMIO 수준에서 그대로 확인해준다.**

### 6.6 설치기(DFU) 모드 + DNLOAD A0~A3 더미 전송 — 실제 데이터 블록 전송·상태 전이·상태 조회까지 성공, 로그 확인됨

2026-11-19, build 146, `vmrun --dnload-probe --installer --ecid ... --psci-log`(미설치 빈 ROOT/AUX). §6.5의 irecv 프로브(열기·조회·닫기만)보다 한 단계 더 나간 시험으로, 표준/클래스 USB 제어 전송을 실제로 왕복시켜 DFU 상태 머신의 반응을 그대로 관측했다. 순서(모두 "다음 요청 전까지 응답 수신 확인됨"):

1. 버스 리셋.
2. `GET_CONFIGURATION`(표준) → `0`(미설정) → `SET_CONFIGURATION(1)`(표준) → 수락(0바이트 응답) → `GET_CONFIGURATION` 재확인 → `1`(설정됨).
3. **[A0]** `DFU_GETSTATE`(클래스) → 상태값 `2`(`dfuIDLE`).
4. **[A1]** `DFU_DNLOAD`(클래스, `wLength=16`, 더미 데이터 16바이트 전부 `0x00`) → 장치가 요청을 수락(0바이트 응답, 거부 없음).
5. **[A2]** `DFU_GETSTATE`(클래스) → 상태값 `5`(`dfuDNLOAD-IDLE`).

Henge 시험 도구의 판정: "control requests sent: 6 (limit 8); stopped at: no stop, A0-A2 all answered" — 중단 없이 세 단계 모두 응답을 받았다. 상태값 `2`→(DNLOAD 수락)→`5`는 USB DFU 표준이 정의하는 상태 전이(유휴 상태에서 데이터 블록을 받으면 `dfuDNLOAD-IDLE`로 전이, 다음 블록이나 종료 신호를 대기)와 일치한다. 도구 자신의 캡션: "reading: dfuDNLOAD-IDLE. The device is waiting for the next block or the end of the download. nothing further is sent." — 이 시험은 여기서 멈추며, 실제 펌웨어나 서명된 데이터를 전송하지 않는다(16바이트는 전부 `0x00`인 더미 값).

**A3까지 추가 확인 (같은 build 146, `--dnload-probe-a3`).** A0~A2까지는 위와 동일하게 재현됐고, 이어서 **[A3]** `DFU_GETSTATUS`(클래스, `bRequest=3`)를 한 번 더 보내 `bStatus=0`(OK, 오류 없음), `bwPollTimeout=50ms`, `bState=5`(`dfuDNLOAD-IDLE`), `iString=0`을 받았다 — A2에서 `DFU_GETSTATE`로 읽은 상태(`5`)와 A3의 `DFU_GETSTATUS`가 보고하는 상태가 서로 일치한다. Henge 도구 자신의 캡션이 이 결과의 한계를 명시한다: "Whether state 5 is normal for this ROM, or the ROM accepted the 16 bytes, is not answered by this." 판정: "control requests sent: 7 (limit 8); stopped at: no stop, A0-A3 all answered" — 역시 중단 없음. 두 번째 `GET_STATUS`나 `ABORT`/`CLR_STATUS`/0바이트 `DNLOAD`(다운로드 종료 신호)/추가 데이터 블록은 이 시험에서 전혀 보내지 않았다. 이후 30초 동안의 상태 스냅샷도 PSCI 리셋 없이, §6.5/§6.6과 같은 USB 연결 상태를 유지한 채 정상 종료했다.

프로브 종료 이후 30초 동안의 상태 스냅샷에서는 PSCI 호출이 전혀 없었고, USB 상태는 "guest on the bus=1 session=1 (rom front-end owns port=1, PCI front-end DRIVER_OK=0)"로 유지됐으며, CPU0은 §6.5에서 이미 관측된 것과 같은 두 지점 사이를 오가는 패턴을 반복했다(구체적 주소는 게스트 ROM 내부 값이므로 비공개). CPU1은 시작부터 끝까지 정지 상태였다. 30초 시간제한으로 `exit reason 7 (halt)`, 양쪽 CPU `halted=3`으로 정상 종료, 화면 출력 없음.

**판정:** Henge의 가상 DFU 장치는 단순히 열기·조회·닫기(§6.5)에 응답하는 것을 넘어, 실제 `DFU_DNLOAD` 데이터 블록을 받아들이고 USB DFU 표준이 정의하는 상태 전이(유휴→다운로드 대기)까지 올바르게 보고하며, `DFU_GETSTATE`와 `DFU_GETSTATUS` 두 조회 경로가 서로 일치하는 상태를 보고한다. 이는 지금까지의 시험 중 가장 깊이 들어간 프로토콜 수준 확인이지만, 받은 것은 여전히 더미(전부 0) 데이터 한 블록뿐이며 서명 검증·실제 펌웨어 블록 처리·다운로드 종료(매니페스트) 단계는 아직 시도되지 않았다. 이 결과만으로 실제 복원이 끝까지 진행된다는 결론은 나오지 않는다.

### 6.7 설치기(DFU) 모드 + DNLOAD A4(ABORT)~A5(GETSTATE) — ABORT는 수락됐으나 그 직후 USB 세션이 바뀜, 로그 확인됨 / 원인 미확인

2026-11-20, build 146, `vmrun --dnload-probe-a4 --installer --ecid ... --psci-log`. §6.6의 A0~A3(설정→`DFU_GETSTATE`→`DFU_DNLOAD`→`DFU_GETSTATE`→`DFU_GETSTATUS`)까지는 동일하게 재현됐고, 이어서:

- **[A4]** `DFU_ABORT`(클래스, `bRequest=6`) → 장치가 요청을 수락(0바이트 응답, 거부 없음).
- **[A5]** `DFU_GETSTATE`(클래스) 요청 전송 → **응답을 받지 못함**. 요청이 오가는 도중 "guest went on the bus"(세션 변경)가 관측됐고, 호스트 쪽 USB 세션 번호가 `1`→`2`로 바뀌었다. 시험 도구는 이를 `-3`("guest left the bus", 해당 요청 자체가 사라짐)으로 기록했다.

Henge 시험 도구가 남긴 설명을 그대로 유지한다: "the host cannot tell when between those two points the guest left or which request, if any, caused it; the new session is not queried." 즉 **A4(ABORT)가 세션 변경의 원인인지, 게스트 ROM 자신의 다른 동작이 원인인지, 또는 단순히 시점이 겹친 것인지 이 로그만으로는 알 수 없다.** A5 실패의 직접 원인은 요청 한도가 아니라 USB 세션 변경이다 — `host/dnload_probe.c`의 한도 검사(`if (c->sent >= c->limit ...) return -100;`)는 전송 전·카운터 증가 전에 이뤄지고, A5(아홉 번째 요청) 시점의 `c->sent`는 8이므로 `8 >= 9`는 거짓이라 검사를 통과해 실제로 전송됐다(로그에도 "request #9" 전송 기록이 있다). 요청 한도 9(`HV_DNLOAD_MAX_REQUESTS_A4`)는 애초에 "A0~A5 전체 시퀀스를 끝까지 보낼 수 있게" 맞춰 놓은 값으로, A5 이후 추가 전송을 막는 별개의 제한이며 이번 A5 실패와는 무관하다. ABORT가 장치를 `dfuIDLE`로 되돌렸는지도 이 시험에서는 확인되지 않았다(세션이 먼저 바뀌어 상태 조회 자체가 무산됨).

세션 변경 이후 새 세션(`2`)으로는 아무것도 전송하지 않았고(시험 도구 자신이 명시), 30초 동안의 상태 스냅샷에서는 USB 상태가 "guest on the bus=1 **session=2**"로 안정적으로 유지됐다(세션 번호만 바뀌고 다시 끊기지는 않음). 이 구간에도 PSCI 리셋은 없었고, 화면 출력도 없었다. **30초 실행 제한에 도달하여 `vmrun`이 종료됐으며**(`exit reason 7 (halt)`, 양쪽 CPU `halted=3`), 이는 시험 도구 자신의 시간제한 처리일 뿐 게스트의 자발적 종료나 정상 부팅을 뜻하지 않는다.

**판정:** `DFU_ABORT` 요청 자체는 수락됐다(응답 코드상 거부 없음). 그 직후 USB 세션이 교체된 것이 ABORT에 대한 ROM의 반응(예: 일부 DFU 구현은 ABORT 후 재열거를 수행함)인지, 우연히 겹친 별도의 ROM 동작인지, 혹은 Henge의 가상 장치 쪽 사정인지는 **미확인**이다. 이는 §6.6까지의 "중단 없이 전부 응답됨" 패턴과 다른, 지금까지 DNLOAD 계열 시험에서 처음 나온 "예상대로 진행되지 않은" 결과이므로 다음 시험에서 재현되는지, 그리고 세션 `2`에 대한 재조회(새로 `GET_CONFIGURATION`/`DFU_GETSTATE`부터 다시 시작)로 ABORT 이후 상태를 확인할 수 있는지가 남은 과제다.

### 6.8 설치기(DFU) 모드 + DNLOAD A6(세션 변경 후 재탐색) — 새 세션에서 장치가 정상 재발견됨, 로그 확인됨 / §6.7의 원인은 여전히 미확인

2026-11-20, build 148, `vmrun --dnload-probe-a6 --installer --ecid ... --make-blank --recreate-blank --psci-log`. §6.7과 동일하게 A0~A3(설정→상태→DNLOAD→상태→GETSTATUS)과 **[A4]** `DFU_ABORT`(수락, 0바이트 응답)까지 재현됐고, **[A5]** `DFU_GETSTATE` 요청 역시 §6.7과 동일하게 전송 중 세션이 바뀌어(`1`→`2`) 응답을 받지 못했다("guest left the bus"로 기록, 마지막으로 응답받은 요청은 #8 ABORT). 이 부분은 §6.7과 수치까지 일치하는 재현이다.

여기서 새로 추가된 부분:

- **[A6]** 세션이 바뀌었고 게스트가 버스에 돌아와 있으므로(위 조건을 만족), 새 세션(`2`)에 대해 읽기 전용 재탐색을 1회 수행 — `GET_CONFIGURATION` → 응답 `1`(이미 설정됨, `SET_CONFIGURATION` 재전송 없음) → `DFU_GETSTATE` → 응답 `2`(`dfuIDLE`).

즉 **새 세션에서 장치는 정상적으로 다시 발견됐고, DFU 상태는 `dfuIDLE`(2)로 응답했다.** ABORT가 수락된 뒤 세션이 바뀌었지만, 그 뒤에도 장치 자체는 (적어도 USB/DFU 계층에서는) 살아서 정상 응답하고 있다는 뜻이다. A6 이후로는 시험 도구가 명시한 대로 아무것도 더 보내지 않았고(재시도·ABORT·DNLOAD·두 번째 GETSTATE 없음), 이어지는 30초 동안의 상태 스냅샷에서도 "guest on the bus=1 session=2"가 안정적으로 유지됐으며 PSCI 리셋은 없었다. 30초 실행 제한으로 `vmrun`이 종료됐다(`exit reason 7 (halt)`, 양쪽 CPU `halted=3`) — 이 역시 시험 도구의 시간제한 처리일 뿐 게스트의 자발적 종료나 정상 부팅을 뜻하지 않는다.

**판정:** 세션 변경 자체의 원인(§6.7에서 미확인 상태로 남긴 것)은 이번 시험으로도 밝혀지지 않았다 — A6은 "원인"이 아니라 "결과"만을 확인하는 읽기 전용 재탐색이기 때문이다. 다만 이번 결과는 §6.7이 남긴 "장치가 응답 불가 상태(멈춤·고장)로 간 것은 아닌지"에 대해서는 답을 준다: **새 세션에서 장치는 정상적으로 열거되고 정상적인 DFU 상태로 응답했으며, ABORT 이후 상태가 비정상(예: 오류 상태, 응답 없음)으로 보이지는 않는다.** 이는 세션 변경이 장치 쪽의 치명적 문제라기보다 (ABORT에 대한 ROM의 재열거 반응이든, 다른 ROM 동작이든) 정상적인 USB 재연결에 가까운 모습이라는 쪽에 무게를 더하지만, 어느 쪽이 실제 원인인지는 여전히 **미확인**이다.

**재현 확인 (build 149):** 로그 문구 수정(커밋 `df297ef`) 이후 같은 시험을 다시 실행한 결과, A0~A6의 모든 수치(요청 번호, 세션 `1`→`2`, `dfuIDLE`/`dfuDNLOAD-IDLE` 상태값, A6의 `GET_CONFIGURATION`→`1`·`DFU_GETSTATE`→`2`)가 build 148과 정확히 일치하게 재현됐다 — 즉 이 거동은 일회성이 아니라 최소 2회 동일 조건에서 안정적으로 재현된다. 수정된 로그 문구("one read-only re-discovery (A6) is attempted next on the new session")도 실제 기기에서 의도대로 출력되는 것을 확인했다(수정 전 build 148의 모순된 문구와 대조). CPU 레지스터 추적값(`pc`/`elr_el1`/`vbar_el1`, 게스트 ROM 내부 주소라 값은 기록하지 않음)도 이전 관측값들과 일치한다.

   ```
   지점 A (호출): x4(기대 유형)=0x1A01, x5=2
   지점 B (비교 직전): actual(w0)=2, expected(w24)=0x1A01, mismatch=1
   ```
   그 직후, 같은 로그에서 곧바로 다음이 이어진다 (장치 레지스터 오프셋만 기록; 게스트 ROM 내부 명령어 주소는 포함하지 않음):
   ```
   이후 CFG 기록
     cfg+0x64 = 0x40200003

   추가 CFG 기록
     cfg+0x64 = 0x80010001
     cfg+0x68 = [게스트 내부 주소값, 비공개 기록]
     cfg+0x6c = 0x40200003
     cfg+0x70 = 0

   이후 PSCI SYSTEM_RESET (fn=0x84000009)
   ```
   엔진 자신이 남긴 진단 메시지도 이를 뒷받침한다: `hengevm: SYSTEM_RESET requested by cpu0, whose last diag-probe hit (of 6) was <지점 B, 게스트 내부 주소 비공개> ... x0=2` — 리셋 직전 마지막으로 찍힌 계측 지점이 바로 이 USB 유형 불일치 비교(지점 B)였다는 것을 엔진이 직접 기록했다. 시간순 인접성에 더해, 계측된 두 지점(A·B) 사이에 다른 BDIF/CFG 접근이 없다는 것도 상세 로그로 확인된다. 다만 이것이 계측되지 않은 ROM 내부 분기까지 전부 배제한 **완전한 인과 증명**은 아니며, `cfg+0x64`/`cfg+0x68` 쓰기가 일반적인 결과·오류 보고 레지스터라는 추정도 여전히 로그 관찰에 근거한 가설이다. '패닉 코드'·'상위 오류 코드'·'이전 오류 체인'처럼 의미를 확정하는 명칭은 쓰지 않는다. `0x40200003`과 `0x80010001`은 관측된 16진수 값으로만 기록한다.
3. **기준 환경의 비어 있는 슬롯 응답.** Apple Virtualization.framework의 실제 동작 또는 검증 가능한 자료와 비교한다. 증거 없이 REG_STATUS/REG_CFG를 0으로 바꾸지 않는다.
4. **두 순수 일반 부팅의 리셋 경로 비교.** 11월 14일과 16일의 PSCI 호출 주소 차이가 생긴 원인을 비교한다. 종료 PC가 같다는 사실만으로 원인이 같다고 판단하지 않는다.
5. **`cfg+0x64`/`cfg+0x68`/`cfg+0x6c`/`cfg+0x70` 쓰기 패턴의 의미.** 로그 전체에서 반복적으로 나타나는 이 4워드 쓰기가 범용 결과/오류 보고 레지스터인지, 그렇다면 어떤 코드 체계를 쓰는지 아직 확인되지 않았다. `0x80010001`이 USB 슬롯 조회 실패를 나타내는 코드인지도 미확인이며, 의미를 확정하는 명칭(패닉 코드 등)은 쓰지 않는다.

## 8. 분석과 변경 관리 원칙

- 소스로 확인한 반환값과 실행 중 실제 관측한 값을 구별한다.

### 현재 종합 판정

**확인됨:** ROM 로딩 경로와 CPU 초기화, CFG 구성, BDIF ROOT/AUX 저장장치 처리, 16KiB AUX 오프셋과 65,536섹터 용량, iOS·Android 신규 AUX 생성 결과의 동일성, USB 미노출 일반 부팅의 PSCI SYSTEM_RESET, USB 미노출 일반 부팅(미설치 빈 ROOT/AUX 조건)에서 ROM이 실제로 `DEVID_USB` 레지스터(`REG_STATUS`/`REG_UNK2`/`REG_CFG`)에 접근함, **그리고 그 접근에서 ROM이 기대하는 USB 유형(`0x1A01`)과 Henge의 폴백 반환값(`2`) 사이에 실제 불일치(`mismatch=1`)가 발생하며 그 직후 진단성 CFG 기록과 PSCI SYSTEM_RESET이 이어짐(2026-11-17, `HV_DIAG_PROBE_CALLER` 계측 로그, 엔진 자체의 "마지막 계측 지점이 이 비교였다"는 기록 포함)**.

**구현 확인됨:** USB 포트가 없는 경우 DEVID_USB 접근이 공통 BDIF 레지스터 처리 구문으로 내려가는 동작.

**미확인:** USB 미존재 슬롯 응답과 Apple VZ 동작의 차이(즉 이 불일치가 "올바른" 동작인지), 유형 불일치가 리셋의 **유일한** 원인인지(계측되지 않은 다른 분기 가능성은 배제되지 않음), `cfg+0x64`류 쓰기의 의미, AUX 내용과 리셋의 인과관계, 두 순수 일반 부팅의 내부 리셋 경로 동일성, 설치기 모드의 USB 폴링 루프가 정상적인 DFU 대기인지 다른 원인의 정체 상태인지(§6.4), irecv 프로브가 PCI virtio-usb 장치 열기/조회/닫기에 전부 성공한 것이 실제 복원(펌웨어 전송·TSS 교환)의 성공 가능성에 대해 무엇을 뜻하는지(§6.5, 도구 자신도 단서로 남김), `DFU_ABORT`(A4) 직후 관측된 USB 세션 변경의 원인 — ABORT에 대한 ROM의 반응인지, 별도로 겹친 ROM 동작인지, Henge 가상 장치 쪽 사정인지(§6.7·§6.8, 시험 도구 자신도 "알 수 없다"고 명시; §6.8은 세션 변경 이후 장치가 정상 응답한다는 점만 추가로 확인했을 뿐 원인 자체는 그대로 미확인으로 남김).

**구현 확인됨(추가):** ROM 측 BDIF 프런트엔드와 PCI virtio-usb 프런트엔드가 실제 USB 제어 전송 수준에서 끝까지 맞물려 동작함 — 실제 `libirecovery`가 Henge의 가상 DFU 장치를 열기·일련번호 조회·닫기까지 0건 실패로 수행(§6.5). 가상 DFU 장치가 실제 `DFU_DNLOAD` 데이터 블록(더미 16바이트)을 받아들이고 USB DFU 표준이 정의하는 상태 전이(`dfuIDLE`→`dfuDNLOAD-IDLE`)까지 올바르게 보고하며, `DFU_GETSTATUS`로도 같은 상태를 일관되게 보고함(§6.6, 서명·실제 펌웨어·매니페스트 단계는 미시도). `DFU_ABORT` 직후 세션이 바뀐 뒤에도 새 세션에서 장치가 정상적으로 재발견되고(`GET_CONFIGURATION`→1) `dfuIDLE` 상태로 정상 응답함(§6.8) — 세션 변경이 장치 쪽의 응답 불가·고장 상태로 이어진 것은 아님을 확인.

**철회됨:** ‘신규 AUX가 비어 있으므로 개인화 검증에 실패하고 리셋된다’는 확정적 주장.

## 9. 추가 검증: 빈 ROOT 디스크와 실제 설치 후 일반 부팅의 구분 — 확인됨 / 원인 미확인

### 9.1 iOS의 신규 가상머신 설치 순서 — 소스 확인됨

ios/Henge/Installer.swift의 신규 설치 경로는 다음 순서다.

1. prepare()에서 별도의 ECID를 발급하고, ROM을 복사하며, 신규 ROOT 디스크와 AUX 파일을 생성한다.
2. install()에서 henge_vm_install()을 호출한다. ios/Henge/Native/henge-vm.c는 이때 installer=1을 전달하여 설치기 모드와 가상 USB 포트를 활성화한다.
3. IPSW 복원 과정이 정상 완료되면 installed 표시 파일을 기록하고 가상머신을 목록에 등록한다.
4. 이후 일반 부팅은 henge_vm_boot()의 installer=0 경로에서 이루어진다.

따라서 **새로 생성한 빈 디스크를 즉시 일반 부팅하는 것**과 **IPSW 복원을 끝낸 디스크를 일반 부팅하는 것**은 서로 다른 시험 조건이다. 이 차이로 인해 리셋이 발생했을 가능성은 있지만, 인과관계는 아직 입증되지 않았다.

### 9.2 Android의 기존 순수 일반 부팅 시험 — 로그 확인됨

2026-11-14와 2026-11-16의 순수 일반 부팅 로그에는 다음 인자가 포함된다.

- --make-blank --recreate-blank
- ROOT: blank_disk.img, 초기 생성 크기 8GiB
- AUX: blank_aux.img, 신규 생성
- --installer 미사용(설정값 0), ECID 0, seed 0, USB 미노출

host/vmrun.c는 --make-blank와 --recreate-blank를 함께 사용하면 파일명이 blank_로 시작하는 기존 파일을 삭제한 후 빈 저장장치를 새로 생성한다. 실제 로그에서도 두 파일의 삭제 및 신규 생성 성공이 기록됐다. 따라서 두 시험의 ROOT에는 IPSW로 복원된 macOS가 들어 있지 않았다.

**추가 판정:** 이 시험에서 SYSTEM_RESET이 확인됐다는 사실은 유지한다. 그러나 그 리셋을 ‘이미 설치된 정상 macOS 가상머신의 일반 부팅 실패’로 분류하는 것은 부정확하다. 현재 검증한 것은 **미설치 신규 ROOT/AUX로 일반 부팅을 시도한 결과**다.

### 9.3 USB 미노출 BDIF 응답과의 관계 — 미설치 조건에서 접근 확인됨 / 인과관계 미확인

devices/bdif.c의 USB 미노출 슬롯 공통 폴백 응답은 소스로 확인된 구현 특성이다. 2026-11-17 상세 MMIO 로그(§7-1)로, 역시 미설치 빈 ROOT/AUX 조건에서 ROM이 실제로 이 USB 슬롯을 읽는다는 사실이 확인됐다. 다만 이 로그도 §9.2와 같은 미설치 빈 저장장치 조건이고, ROOT가 비어 있다는 독립적인 차이가 여전히 남아 있으므로, 현 단계에서 USB 폴백을 리셋의 유일한 원인으로 지목해서는 안 된다.

### 9.4 검증 우선순위 갱신

1. 기존 순수 일반 부팅의 대상이 빈 ROOT/AUX였다는 조건을 모든 분석·비교에 명시한다.
2. 먼저 소스·기존 로그 범위에서 미설치 저장장치라는 조건과 USB 폴백 가설을 구분한다.
3. ~~순수 일반 부팅에서 실제 DEVID_USB MMIO 접근 여부.~~ — **완료 (2026-11-17, §7-1).** 다만 이 확인도 미설치 빈 ROOT/AUX 조건으로 범위가 한정된다.
4. 정상 설치 완료 후 일반 부팅과의 호환성 비교는 설치 완료된 저장장치와 해당 가상머신의 설정값을 사용하는 별도 시험으로 취급한다. 기존 빈 파일을 그대로 교체하거나 새로운 설치를 실행했다는 의미는 아니다.

**현재 결론:** 호스트의 ROM·AUX·BDIF 구현 일부는 검증됐지만, 기존 신규 빈 디스크 일반 부팅 리셋만으로 정상 설치된 macOS 가상머신의 Android 부팅 호환성까지 판정할 수 없다. 실기기 재실행, 설치·복원, 디스크 교체 및 장치 반환값 변경은 이 추가 검증에서 수행하지 않았다.

### 9.5 Android 설치 실행기 통합 시 선결 과제 — 소스 확인됨

실제 설치·복원 실행을 승인하기 전에, 기존 복원 엔진(host/install.c, host/restore_session.c)을 Android 앱(ProcessBuilder 기반 별도 네이티브 실행기 구조)에 통합하려면 아래 항목이 아직 해결되지 않은 상태임을 소스로 확인했다. 이 항목들은 설계 결정이 필요한 공백이며, 어떤 코드도 변경하지 않았다.

- **네트워크 허용 목록의 한계:** host/net_guard.c의 `hv_net_guard_allow_host()`는 `void` 함수이고 등록 목록은 `MAXL=8`로 고정돼 있다. 목록이 가득 차면 추가 등록은 아무 통지 없이 무시된다. 복원 과정에서 필요한 접속 대상을 먼저 조사하고, 등록 실패를 호출자가 알 수 있는 구조로 보완해야 한다.
- **신규 설치 디스크 크기 정책 불일치:** iOS(`ios/Henge/Installer.swift`)는 신규 설치 시 64GiB(`64 << 30`) 디스크를 만들지만, Android의 `host/disk_policy.h`는 `HV_INSTALL_DISK_BYTES`를 128GiB(`128ULL << 30`)로 정의한다. 두 플랫폼이 서로 다른 정책을 쓰고 있어, 어느 쪽을 기준으로 할지 별도 결정이 필요하다.
- **프로세스 경계를 넘는 생명주기 동기화:** host/restore_session.c의 소유권·정리 관리는 복원을 실행하는 그 네이티브 프로세스 내부에 한정된다. Android 앱은 별도 프로세스에서 이를 구동하므로(ProcessBuilder), 앱 종료·백그라운드 전환·강제 종료·사용자 취소를 네이티브 프로세스에 전달하고 그 결과를 다시 앱에 돌려주는 규약이 앱-프로세스 경계에 별도로 필요하다. 이 규약은 현재 코드 어디에도 존재하지 않는다.
- **설치 완료 판정 체계 부재:** iOS의 "installed 표시 파일" 방식과 동등한 장치가 Android/공유 호스트 코드 어디에도 없다(§9.1 참조). 복원 도중 프로세스 종료, 저장장치 기록 실패, 복원 완료 직후 앱 종료 등을 구분하려면 최소한 `미설치 → 설치 준비 → 설치 진행 → 설치 완료/실패`의 상태 구분이 필요하다.

이 네 가지 선결 과제에 대한 구체적 설계 초안(앱–네이티브 실행기 계약, 네트워크 승인·격리 계약, 저장장치·설치 상태 계약)은 별도 문서 `docs/android-install-integration-design.md`에 정리했다. 해당 문서 §5에는 앱과 엔진의 상태 구분, 상태 파일 원자적 기록·재시작 복구, 취소/성공 경합, 네트워크 등록 실패, VM별 디스크 식별정보와 단계별 오프라인 검증 관문도 추가했다. 모두 설계 제안이며, 실제 코드 변경·네트워크 접근·저장장치 생성/초기화·VM 실행은 수행하지 않았다.

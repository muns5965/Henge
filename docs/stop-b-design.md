# 정지점 B 설계: TSS 준비·개인화 검증, 실패 분류, 가짜 TSS 서버 시험 계약

상태 표기는 `docs/restore-architecture.md` 0절과 같다: 검증 완료 / 코드 확인 / 설계 결정 / 미검증 / 별도 승인 필요.

## 1. 목적과 범위

**목적**: 복원 엔진이 "TSS를 준비하고 개인화 요청을 만들고 응답을 처리하는" 단계를 PC에서 끝까지 시험할 수 있게 하고, 실패가 어느 층에서 났는지 구별할 수 있게 한다.

| 구분 | 이번 문서의 범위 |
| --- | --- |
| 포함 | 요청 목적지 정책, TLS 검증 범위, 요청·응답 계약, 크기·시간·재시도 제한, 실패 분류 코드, 가짜 TSS 서버 시험의 입력·출력·합격 기준 |
| 제외 (구현도 하지 않음) | 실제 Apple TSS 요청, 개인화된 이미지의 장치 전송, RecoveryOS 진입, 설치 디스크 생성·쓰기 |
| 별도 승인 필요 | 위 제외 항목 전부. 문서가 승인되어도 이 항목들의 승인이 되지는 않는다 |

## 2. 이미 있는 것 (코드 확인)

| 항목 | 위치 | 내용 |
| --- | --- | --- |
| https 전용 TSS (Android 빌드) | `third_party/libtatsu/src/tss.c`, `HV_TSS_HTTPS_ONLY` | 목록의 https 3개 호스트만 사용: `gs.apple.com`, `gs.apple.com.akadns.net`, `gs.apple.com.v.aaplimg.com` (포트 443). http 항목은 목록에 없다 |
| 재시도 제한 | 같은 파일 | 최대 6회, 총 150 s, 연결 20 s / 전체 60 s. 인증서·정책 거부는 재시도하지 않는다 (`tss_curl_error_retryable`) |
| 진단 문자열 | `tss_last_diag()` | 서버가 보낸 텍스트를 복사하지 않는 고정 어휘: 시도 수, 전송 계층 분류(`DNS`/`CONNECT`/`TIMEOUT`/`IO`/`POLICY_REFUSED`/`TLS_OR_OTHER`), HTTP 코드, `TSS_STATUS`, `MESSAGE_CLASS`, `NOT_A_TSS_REPLY`, `SUCCESS_BUT_NOT_A_PLIST` |

| 시험 전용 신뢰 저장소 | `curl_mbedtls.c`의 `HV_ALLOW_CA_ENV` | 시험 빌드에서만 `HV_CA_PATH`/`HV_EXTRA_ANCHOR` 사용. `tools/check-no-test-flags.sh`가 출하 빌드에 없음을 검사 |

## 3. 비어 있던 것과 이번 구현 (코드 확인 → 구현·PC 시험)

1. **정책 층과 서버 층의 구별** — 구현됨 (PC 시험, CI 확인 대기)
   - 이전: 훅이 거부한 주소를 shim이 건너뛰었고, 모든 주소가 거부되면 `CURLE_COULDNT_CONNECT`로 끝나 libtatsu가 재시도했다. 진단에도 `CONNECT`로 찍혔다.
   - 지금: 한 홉의 **모든** 주소가 훅에 거부되면 shim이 `CURLE_UNSUPPORTED_PROTOCOL`을 돌려준다. libtatsu는 이 코드를 재시도하지 않는다 (`tss_curl_error_retryable`, 코드 확인). libtatsu 수정은 없다.
   - 반환 코드만으로는 실제 미지원 프로토콜(예: `ftp://`)과 구별되지 않으므로, **요청별 기록**(`host/curl_last.h`, 스레드별)을 함께 둔다: `policy_denied`(최종 결과가 전부 거부였음), `addrs_denied`, `addrs_tried`(훅이 허용해 `connect()`를 호출한 수), `connected`, `tls_done`, `request_sent`, `http_status`, `too_large`, `body_to_cb`, `max_buf`.
   - 기록은 매 `curl_easy_perform` 시작에 지워지고 그 요청(리다이렉트 홉 포함)만 설명한다. 읽는 쪽은 같은 스레드에서 반환 직후에 읽는다. 스레드를 넘기는 비동기 호출에는 이 기록을 쓰지 않는다 (현재 호출 경로에는 없음).
   - 최종 반환 코드가 `UNSUPPORTED_PROTOCOL`이 아니면 `policy_denied`는 0으로 되돌린다. 일부 주소가 거부되어도 다른 주소에서 응답을 받으면 정책 거부가 결과를 덮어쓰지 않는다. 일부 거부 + 허용된 주소의 연결 실패는 `COULDNT_CONNECT`이며 `POLICY_DENIED`가 아니다.
2. **복원 도구를 통한 TSS 경로**는 여전히 정책 아래서 시험되지 않았다 (libtatsu 단독 + 분류기 시험만; 복원 도구 전체 경로는 미검증). 허용 목록이 비어 있어 지금 TSS는 전부 거부된다 (설계 의도).
3. **응답 크기 상한** — 구현됨. 1 MiB는 **디코딩된 본문**(청크 프레임 제거 후; 이 클라이언트는 내용 압축 해제를 하지 않는다) 기준이고, 헤더는 별도 상한을 가진다 (4.3절).
4. **요청별 분류와 단계 보고** — `host/tss_stage.{h,c}`로 구현. 아직 앱·복원 흐름에 연결하지 않았다 (연결은 별도 작업).

## 4. 설계 결정

### 4.1 승인 목적지 정책 (설계 결정)

- 허용 목록의 기본값은 비어 있다. 실제 Apple 요청을 승인할 때만 `(gs.apple.com, 443)` 등 필요한 항목을 추가한다.
- 항목은 **이름과 포트** 쌍이다. 이름이 맞아도 해석된 주소가 사설·루프백·링크로컬이면 거부한다 (구현됨).
- 세 호스트 중 어떤 것을 허용할지는 승인 때 정한다. 기본 제안은 `gs.apple.com:443` 하나다. 나머지 둘은 첫 호스트가 전송 계층에서 실패했을 때만 쓰이므로, 필요성이 확인되기 전에는 넣지 않는다.
- 정책 항목은 요청 단위가 아니라 **실행 단계**에 묶는다: TSS 단계가 시작될 때 추가하고 끝나면 제거한다. 복원 모드 이후의 장치 지정 URL은 이 항목으로 허용되지 않는다 (URLAsset은 자체 목록).

### 4.1a 시험 전용 루프백 예외 (구현됨, 시험 빌드에만)

- `HV_NET_TEST_LOOPBACK`로 컴파일한 `net_guard.c`만 `hv_net_guard_test_allow_loopback(port)`를 가진다. 허용 대상은 **정확히 `127.0.0.1:port`, HTTP 목적**뿐이다. 다른 루프백 포트, `127.0.0.2`, 사설 주소, `::1`, FDR·DEFAULT 목적은 계속 거부된다 (시험 7·8·9번에서 확인).
- 출하 객체에는 심볼도 문자열도 없고, 시험 객체에는 있음을 `tools/check-no-test-flags.sh`가 대조(통제)와 함께 검사한다. 앱 코드가 이 함수를 부르거나 출하 빌드 파일이 스위치를 정의하면 그 검사가 실패한다.

### 4.2 TLS 검증 (설계 결정)

- 출하 빌드: 시스템 신뢰 저장소로 체인과 호스트 이름을 항상 검증한다. 검증 끄기 옵션은 shim이 무시한다 (검증 완료).
- 시험 빌드: 시험용 자체 서명 CA를 `HV_CA_PATH`로 지정한다. 이 스위치는 시험 빌드에서만 컴파일되고, 출하 빌드에 들어갔는지는 `check-no-test-flags.sh`가 검사한다 (검증 완료).
- 가짜 서버의 인증서는 시험 실행마다 `openssl`로 만들고(유효 2일), 저장소에 커밋하지 않는다.

### 4.3 제한 (설계 결정)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 요청 본문 | 요청 plist 크기를 기록하고 상한 1 MiB로 시험 | 요청은 수 KB 수준이어야 함 (미검증: 실제 크기 미측정) |
| 응답 본문 | 상한 **1 MiB, 디코딩된 본문 기준**. 정확히 1 MiB는 허용, 1 바이트 초과는 `REPLY_TOO_LARGE` | 티켓은 수십 KB |
| 응답 헤더 | 줄당 64 KiB(기존), 상태줄+헤더+트레일러 합계 256 KiB | 합계 초과도 `REPLY_TOO_LARGE`로 분류 |
| 시간 | 연결 20 s, 전체 60 s, 총 150 s (기존 값) | 코드 확인 |
| 재시도 | 전송 계층 오류에 한해 최대 6회. **정책 거부와 인증서 오류는 0회** | 정책 거부는 재시도해도 같은 결과 |
| 자동 재시도 (사용자 확인 단위) | 금지. 한 번의 사용자 확인으로 TSS 3건(AP / LocalPolicy / RecoveryOS)을 각각 1회 | `restore-architecture.md` 2절 |

### 4.4 실패 분류 (설계 결정)

각 TSS 요청은 아래 코드 중 정확히 하나로 끝난다. 코드는 **누가 판단했는가**로 나눈다.

| 코드 | 판단한 층 | 관측 지점 | 재시도 | 사용자에게 보이는 뜻 |
| --- | --- | --- | --- | --- |
| `OK` | — | 응답 plist 파싱 성공, 필수 키 존재 | — | 준비 단계 성공 (복원 완료 아님) |
| `POLICY_DENIED` | 우리 정책 (`net_guard`) | curl 1 + 요청별 `policy_denied` (한 홉의 모든 주소가 거부됨) | 0 | 앱이 막음. 서버는 요청을 받지 않았다 |
| `NET_DNS` | 네트워크 | 진단 `TRANSPORT … DNS` | 6 | 이름을 찾지 못함 |
| `NET_CONNECT` | 네트워크 | curl 7. 일부 주소가 거부되고 허용된 주소의 연결이 실패한 경우도 여기 | 6 | 서버에 닿지 못함 |
| `NET_TIMEOUT` / `NET_IO` | 네트워크 | `TIMEOUT` / `IO` | 6 | 시간 초과 / 전송 중 끊김 |
| `TLS_FAILED` | TLS | `TLS_OR_OTHER` + 인증서·호스트 이름 | 0 | 인증서 검증 실패. 보안 신호이므로 다른 호스트로 바꿔 재시도하지 않음 |
| `HTTP_ERROR` | 서버(HTTP) | 완전한 응답, 진단 `HTTP: n` (n ≥ 300) | libtatsu 현행 (STATUS 없으면 최대 6) | 서버가 HTTP 오류를 돌려줌 |
| `SERVER_REFUSED` | 서버(TSS 정책) | 진단 `TSS_STATUS: n` (n ≠ 0), `MESSAGE_CLASS` | 0 | 서명 서버가 이 요청을 거절. 우리 쪽 네트워크·구현 오류가 아닐 수 있음 |
| `BAD_REPLY` | 서버/파서 | `NOT_A_TSS_REPLY` / `SUCCESS_BUT_NOT_A_PLIST` / 필수 키 없음 | 0 | 형식 불량 |
| `REPLY_TOO_LARGE` | 우리 제한 | curl 63 (본문 또는 헤더 상한) | 0 | 상한 초과 |
| `CANCELLED` | 사용자/앱 | curl 42 | 0 | 취소 |
| `NOT_SENT` | libtatsu | 진단 없음 (https 아닌 URL 등) | 0 | 요청 전에 거부 |
| `TRANSPORT_OTHER` | 전송 | 그 밖의 curl 코드, 실제 미지원 프로토콜 포함 | 0 | 분류 밖의 전송 실패 |

원칙:
- **분류는 요청이 도달한 단계로 한다.** 고정 우선순위(전송 → HTTP → TSS)가 아니다. 전송 코드가 있으면 완전한 응답이 오지 않은 것이므로 상태줄이 보였더라도 전송 실패다 (응답 중 끊김 → `NET_IO`). 완전한 HTTP 응답이 있고 상태가 300 이상이면 `HTTP_ERROR`(본문의 `STATUS`와 무관). 그 외에 `STATUS`가 0이 아니면 `SERVER_REFUSED`.
- `POLICY_DENIED`는 curl 코드 1 **그리고** 요청별 기록의 `policy_denied`일 때만이다. 코드 1만 있으면 `TRANSPORT_OTHER`(실제 미지원 프로토콜). curl 63은 `REPLY_TOO_LARGE`, 42는 `CANCELLED`, 28은 `NET_TIMEOUT`, 6은 `NET_DNS`, 7은 `NET_CONNECT`, 인증서·TLS 코드는 `TLS_FAILED`, 52·55·56은 `NET_IO`. libtatsu가 요청 전에 거부한 URL(https 아님)은 진단이 비어 `NOT_SENT`.
- **재시도 열은 libtatsu의 현재 동작이며 이번에 바꾸지 않는다.** 분류는 사후 보고일 뿐 재시도 횟수를 정하지 못한다. HTTP 상태별 재시도 정책(4xx 즉시 중단 등)은 libtatsu 수정이 필요하므로 별도 승인 작업이다. 시험은 실제 관측된 시도 수(서버가 받은 요청 수와 일치)를 기록한다.
- `SERVER_REFUSED`는 "서버가 요청을 읽고 거절했다"는 뜻이다. 서명 서버의 정책과 가상 장치 식별값에 영향을 받으므로, 성공해도 이후 iBSS 실행을 보장하지 않고 거부되어도 네트워크 구현 오류로 단정하지 않는다.
- 로그와 보고에는 코드·시도 수·HTTP 코드·STATUS 숫자·호스트 이름만 넣는다. ECID, nonce, 티켓, 서버 메시지 원문은 넣지 않는다.

## 5. 가짜 TSS 서버 시험 계약

### 5.1 입력

| 입력 | 값 |
| --- | --- |
| 서버 | 루프백(127.0.0.1) 위의 원시 소켓 HTTP/1.1 서버(`tests/test_tss_stage.py`). 대부분 http(libtatsu 시험 변형이 `127.0.0.1`/`localhost`의 http만 허용), TLS 시나리오는 시험마다 `openssl`로 만든 자체 서명 인증서(유효 2일, 커밋하지 않음) |
| 정책 | 시험 도구가 `hv_net_guard_test_allow_loopback(서버포트)`만 호출. 호출하지 않으면 모든 연결이 거부된다 |
| 신뢰 | `HV_CA_PATH`로 시험 CA만 (시험 빌드). 출하 빌드에는 이 스위치가 없다 |
| 요청 | 식별값이 가짜인 plist. 가짜 ECID가 출력에 나오는지 검사한다 |
| 관측 | (1) `connect()` 실제 호출 수: 링커 `--wrap=connect`로 세어, 정책 훅이 거부했으면 호출되지 않았음을 확인한다 (2) 서버가 받은 연결·요청 수 (3) 이름 해석은 `--wrap=getaddrinfo`로 `localhost`만 대체 |

### 5.2 시나리오와 합격 조건 (구현·PC 통과)

| # | 서버 동작 | 기대 코드 | 추가 합격 조건 |
| --- | --- | --- | --- |
| 1 | 정상 응답 / 청크 응답 | `OK` | 시도 1, `connect()` 1, 서버 요청 1 |
| 2 | 허용 포트 없음 | `POLICY_DENIED` | `connect()` 0, 시도 1(재시도 없음), 서버 연결 0 |
| 3 | 시험 허용 포트와 다른 루프백 포트 | `POLICY_DENIED` | `connect()` 0, 서버 연결 0 |
| 4 | 허용 포트라도 사설(10.x)·127.0.0.2로 해석 | `POLICY_DENIED` | `connect()` 0, 거부 2 |
| 5 | 실제 미지원 프로토콜(`ftp://`) | curl 1, `policy_denied` 0 | 정책 거부와 구별 |
| 6 | 한 주소 거부 + 허용 주소 연결 실패 | `NET_CONNECT` | 시도마다 거부 1·시도 1, 재시도 유지 |
| 7 | 한 주소 거부 + 다른 주소가 응답 | `OK` | 거부 1·시도 1·`connect()` 1 |
| 8 | HTTP 404 / 500+STATUS | `HTTP_ERROR` | 보고된 시도 수 = 서버가 본 요청 수 |
| 9 | HTTP 500(STATUS 없음) | `HTTP_ERROR` | libtatsu 현행 재시도(최대 6)를 그대로 두고 관측 시도 수 보고 |
| 10 | 200 + 쓰레기 / 성공 문구+깨진 plist | `BAD_REPLY` | 관측 시도 수 = 서버 요청 수 |
| 11 | 200 + `STATUS=8` | `SERVER_REFUSED` (8) | 서버 메시지 원문이 출력에 없음 |
| 12 | 응답 중간에 연결 끊김 | `NET_IO` (curl 56) | 상태줄이 보였어도 HTTP 오류가 아님 |
| 13 | 본문 정확히 1 MiB | `OK` | 경계 허용 |
| 14 | 1 MiB+1 / Content-Length 4 MiB / 길이 없이 12 MiB / 청크 12 MiB / 청크 하나가 2 MiB 선언 / 헤더 800 KB | `REPLY_TOO_LARGE` | 시도 1, libtatsu로 간 본문 ≤ 1 MiB(선언 초과 3종은 0), shim 내부 버퍼 최대 ≤ 256 KiB |
| 15 | 5건 순차 중 3번째가 `STATUS` 거절 | `OK, OK, SERVER_REFUSED` | 네 번째·다섯 번째는 요청하지 않음 (서버 3건), 멈춘 위치 보고 |
| 16 | 응답 전 침묵 중 취소 | `CANCELLED` | 12 s 침묵 중 3 s 안에 반환 (읽기 대기는 200 ms 단위로 취소 확인) |
| 17 | libtatsu 재시도 대기 중 취소 | `CANCELLED` | 5 s 안 (아래 취소 한계 참조) |
| 18 | 신뢰된 인증서 / 신뢰되지 않는 인증서 / 다른 호스트 이름 | `OK` / `TLS_FAILED` ×2 | 실패 쪽은 시도 1, 서버에 요청 0 |
| 19 | https 아닌 URL | `NOT_SENT` | `connect()` 0 |

연결 단계(블랙홀 주소로의 `connect`) 취소는 루프백만으로 재현할 수 없어 이번 시험에 없다 (미검증; shim의 `wait_fd`는 200 ms 단위로 취소를 확인한다는 코드 확인만 있음).

### 5.3 취소 기준 (현재 코드가 지원하는 대기 단계별)

| 대기 단계 | 취소 반응 | 근거 |
| --- | --- | --- |
| 연결 완료 대기, TLS·읽기·쓰기 대기 | 약 200 ms 이내 (`wait_fd` 슬라이스) | 코드 확인; 읽기 대기는 시험(16번) |
| 본문 수신 중 (데이터가 계속 도착) | 청크마다 확인 | 코드 확인 |
| `getaddrinfo` | **취소 불가**. 반환 후에야 확인 | 한계. 별도 DNS 스레드는 이번 단계에 도입하지 않는다 |
| libtatsu 재시도 사이 `sleep(2)` | **취소 불가**, 최대 약 2 s 지연 후 다음 시도 시작에서 확인 | 한계. 벤더링 소스 수정이 필요하므로 별도 승인 항목 |

"어디서나 1 s 안 반환"은 보장하지 않는다.

### 5.4 전체 합격 기준

- 각 시나리오가 기대 코드와 추가 조건을 만족한다. 코드는 정확히 하나다.
- 정책 거부 시나리오에서 `connect()` 호출이 0이고 서버가 받은 연결이 0이다.
- 어떤 출력에도 가짜 ECID·티켓·서버 메시지 원문이 없다.
- 출하 빌드에 시험용 루프백·CA 설정이 없음을 `check-no-test-flags.sh`가 대조와 함께 확인한다.
- 대조: 허용 포트를 주면 같은 요청이 서버에 닿는다(시나리오 1), 주지 않으면 닿지 않는다(시나리오 2). 시험이 정책을 실제로 검사한다는 증거다.

### 5.5 실행 위치

PC와 GitHub Actions. `tools/tss-stage-test.sh`, `android-engine.yml`의 독립 단계, `continue-on-error` 없음.

### 5.6 결과 필드의 관측 범위

| 필드 | 관측 범위 |
| --- | --- |
| `attempts` | libtatsu가 보고한 전체 시도 횟수 |
| `tss_status` | libtatsu 최종 진단에서 확인한 TSS 상태값 (시도 누적 통계가 아님) |
| `http`, `curl_code` | 마지막 시도 또는 최종 실패의 상태 |
| `addrs_denied`, `addrs_tried` | 마지막 curl 실행의 연결 통계 |
| `body_to_lib`, `max_buf` | 마지막 curl 실행의 본문·버퍼 통계 |

### 5.7 본문 상한의 복원

`hv_curl_set_body_cap`은 이전 값을 돌려주고, `hv_tss_send`는 어떤 경로로 끝나든 이전 값을 되돌린다. 시험은 상한 12345를 걸어 둔 채 정상·정책 거부·응답 초과·서버 거절·취소·인증서 실패로 끝나는 요청을 보낸 뒤, 같은 스레드의 20 KB 응답 요청이 실제로 12345 상한에 막히는지(저장된 값이 아니라 동작)를 확인한다. 대조: 상한 없이는 같은 요청이 통과한다. 복원을 빼면 6건 모두 실패함을 확인했다.

## 8. 알려진 한계

- 서명 서버가 가상 장치 식별값에 어떻게 반응하는지는 실제 요청 없이는 알 수 없다 (미검증).
- 가짜 서버는 응답 형식만 흉내 낸다. 실제 서버의 지연, 오류 문구, 정책 변경은 재현하지 못한다.
- 시험용 키·인증서는 시험 실행마다 `openssl`로 새로 만든다(유효 2일). 과거 커밋에 추적되던 `build-curltest/`의 키는 실서비스에 쓰인 적이 없으며 재사용하지 않는다.
- 요청별 기록은 스레드별이다. 요청이 다른 스레드로 넘어가는 호출 경로에는 쓸 수 없다.
- 내용 압축(gzip)은 지원하지 않으므로 압축 해제 후 크기 검사는 해당 없다. 지원을 추가하면 별도 상한이 필요하다.
- 복원 모드 이후의 펌웨어 TSS 약 10곳은 이번 단계 범위가 아니다 (`restore-architecture.md` 3절).

# 가짜 장치 시험 명세 (비동기 작업 수명)

상태: 명세 초안. 시험 구현은 별도 승인 대상이다.
관련: `docs/async-lifetime-design.md`(요구 R1~R9), `docs/tss-integration-design.md` 2.6~2.8절.

이 명세는 구현 구조를 선결정하지 않는다. 정의하는 것은 세 가지뿐이다: **어떤 실행 순서를 재현할 것인가 / 어떤 상태와 자원을 관측할 것인가 / 어떤 결과를 실패로 판정할 것인가.** 등록·완료 통지·취소·종료 대기의 인터페이스는 수명 관리 상세 설계에서 정한다.

## 1. 한계 (결론 해석 규칙)

- 가짜 장치는 제어 가능한 연결이다. 실제 Apple 장치의 메시지 순서와 프로토콜 동작은 검증하지 못한다.
- 통과는 "시험한 실행 순서에서 위반이 없었다"는 뜻이다. 모든 스레드 실행 순서에서 안전하다는 결론을 내리지 않는다.
- 시험으로 입증할 수 없는 것: 등록 차단의 원자성, 객체 해제 순서의 일반 보장, 정책 훅 수명의 일반 보장. 이는 소스의 동기화 구조와 함께 검증한다.
- 실제 Apple 서버·실제 장치·RecoveryOS·루트 파일시스템 전송은 사용하지 않는다. 연결은 루프백 또는 소켓쌍이며 시험 전용 빌드에서만 켠다(`check-no-test-flags.sh` 대상에 포함).

## 2. 시험 환경 개요

- 가짜 restored: 시험이 지정한 순서로 plist 메시지(`AsyncDataRequestMsg`, `DataRequestMsg`, `ProgressMsg` 등)를 보내고, 수신한 응답을 기록한다.
- 가짜 `DataPort` 서비스: 지정한 지연·정지·끊김을 낸다.
- 제어점: 응답 지연, 응답 정지(무한 대기), 연결 끊김, 메시지 사이 간격, 처리기 진입 시점 통지.
- 관측점: 활성 작업 수, 세션 상태, 정책 훅 설치 여부, 객체 해제 여부(해제 감시용 표식 또는 소멸 알림), 가짜 장치가 받은 메시지 목록, 반환 오류값, 스레드 생존 여부.
- 동기화 취약 지점 탐지는 스레드 새니타이저(ThreadSanitizer)와 주소 새니타이저(AddressSanitizer) 빌드를 병행한다(PC에서만; Android 네이티브는 미검증).

## 3. 시험 항목

각 항목: **재현 순서 / 관측 / 실패 판정 / 확인 대상 요구**.

### T1 종료 중 신규 요청 거부
- 재현: 비동기 작업 하나가 진행 중인 상태에서 종료를 시작하고, CLOSING 중에 새 `AsyncDataRequestMsg`를 보낸다.
- 관측: 스레드 생성 여부, 활성 작업 수, 엔진이 받은 오류값, 가짜 장치가 받은 응답.
- 실패: 거부된 요청에 대해 스레드가 만들어지거나, 오류가 엔진에 전달되지 않거나, 활성 수가 어긋남.
- 대상: R1, R2, R3. 부분 확인(원자성은 입증 불가).

### T2 거부 오류의 보존 (P10)
- 재현: 오류를 일으킨 직후 가짜 장치가 (a) 아무 메시지도 보내지 않음, (b) 오류를 0으로 돌려주는 메시지(`ProgressMsg`)를 보냄, (c) 알 수 없는 `MsgType`을 보냄.
- 관측: 복원 함수의 최종 반환값.
- 실패: 오류 후 어떤 경우라도 최종 반환값이 0(성공)으로 바뀜. (b)에서 바뀌면 P10 확정.
- 대상: R9. 현재 코드의 동작 관측용(기준선)이며, 설계 변경 후에는 회귀 항목이 된다.

### T3 생성 실패 시 등록 취소
- 재현: 스레드 생성 실패를 주입(시험 전용 후크)한다.
- 관측: 활성 작업 수, 오류값, 작업 객체의 해제 여부(`args->message` 포함).
- 실패: 활성 수가 0으로 돌아오지 않음, 객체 누수.
- 대상: R1.

### T4 공유 연결 동시 송신
- 재현: `DataPort` 없는 비동기 요청 처리 중 루프도 같은 연결로 송신하도록 가짜 장치가 두 종류 메시지를 겹쳐 보낸다. 송신 크기를 크게(소켓 버퍼를 넘는 크기) 해서 부분 쓰기를 유도한다.
- 관측: 가짜 장치가 받은 바이트열이 plist 단위로 온전한지, 메시지 순서.
- 실패: plist 파싱 실패, 메시지 중간에 다른 메시지가 끼어듦.
- 대상: R7. 통과해도 일반 안전성은 주장하지 않는다.

### T5 장치 응답 정지와 대기 한도
- 재현: 비동기 작업이 가짜 서비스의 응답을 기다리는 중 서비스가 응답을 멈춘다. 종료를 시작하고 대기 한도까지 둔다.
- 관측: 한도 도달 시 상태, 훅 설치 여부, 객체 해제 여부, 스레드 생존, 신규 세션 시작 결과.
- 실패: 한도 도달 후 `client` 등 참조 객체가 해제됨 / 훅이 제거됨 / 신규 세션이 시작됨.
- 대상: R5, R6.

### T6 지연 완료 후 상태 변화
- 재현: T5 이후 정지했던 서비스가 응답하고 작업이 뒤늦게 끝난다.
- 관측: 상태 전이, 활성 수, 신규 세션 시작 가능 여부.
- 실패: 일관성 확인 없이 자동으로 정상 상태 복귀하고 신규 세션이 시작됨(기본안은 자동 복귀 없음).
- 대상: R5.

### T7 취소 신호 전달 범위
- 재현: 작업 종류별(ASR 연결 대기, URLAsset 다운로드, BasebandData 요청)로 블로킹 상태를 만들고 취소 신호를 보낸다.
- 관측: 종료까지 걸린 시간, 종료 여부.
- 기록(판정 아님): 취소에 반응하는 종류와 반응하지 않는 종류의 구분. 실패 기준이 아니라 대기 한도 설계의 입력이다.
- 대상: R4, R5, D2.

### T8 연결 닫기와 대기 해제 (P8)
- 재현: 다른 스레드가 수신 대기 중인 연결을 `close`(shutdown 없음)로 닫는다. 비교군으로 `shutdown` 후 `close`.
- 관측: 대기 스레드의 반환 시점과 오류값, 닫힌 fd 번호 재사용 시 오사용 여부.
- 기록: 플랫폼별 결과(PC Linux에서의 결과가 Android와 같다고 가정하지 않음).
- 대상: 미확정 해소(P8).

### T9 정상 종료 순서
- 재현: 비동기 작업이 자연 완료되는 정상 종료.
- 관측: 객체 해제와 훅 제거가 작업 완료 뒤에 일어나는지(순서 기록).
- 실패: 작업 완료 전 해제/제거.
- 대상: R4, R6.

### T10 오류·종료 상태 동기화 (P6)
- 재현: 비동기 작업의 오류 기록과 루프의 종료 판정이 겹치도록 타이밍을 조정하고 반복 실행한다. ThreadSanitizer 병행.
- 관측: 데이터 경쟁 보고, 최종 오류값.
- 실패: 경쟁 보고 또는 오류 유실.
- 대상: R9. 반복 실행에서 미검출이어도 경쟁이 없다는 결론은 내리지 않는다.

### T11 세션 간 경계
- 재현: QUIESCENCE_FAILED 이후 `begin()`을 호출한다.
- 관측: 거부 여부, 정책 목록·훅 상태 불변 여부.
- 실패: `begin()`이 성공해 목록이 비워지거나 훅이 재설치됨.
- 대상: R5, 정책 보호.

## 4. 판정 구분

| 구분 | 의미 |
| --- | --- |
| 통과 | 시험한 순서에서 위반 관측 없음 (일반 안전성 아님) |
| 실패 | 실패 판정 조건 관측 |
| 기록 | 판정 없이 값을 수집 (T7, T8) |
| 시험 불가 | 시험으로 입증할 수 없고 소스 구조로 보장해야 함 |

## 5. 현재 코드에 대한 기대 (관측 전 가설, 결과로 쓰지 않음)

- T2(b), T5, T3, T11은 현재 코드에서 실패할 수 있는 항목이다. 결과를 보기 전에는 결함 확정으로 쓰지 않는다.
- 시험은 설계 변경 전 기준선을 먼저 기록한 뒤 변경 후 회귀로 쓴다.

## 6. 별도 승인 필요

시험 구현(가짜 장치, 시험 전용 후크), 벤더링 소스에 시험 후크를 넣는 변경, 새 의존성(새니타이저는 컴파일러 기능이므로 의존성 추가 없음, 단 CI 환경 확인 필요).

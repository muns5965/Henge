# G7 analysis notes (2026-11-24) — code reading and public sources only; nothing here was measured on a device

## 1. AOSP phantom-process path (read from android.googlesource.com, main branch; the device's Android 17 build may differ)
- Kill chain for the CPU case: `MainHandler` message `CHECK_EXCESSIVE_POWER_USE_MSG` → `ActivityManagerService.checkExcessivePowerUsage()` → `updatePhantomProcessCpuTimeLPr(...)` → `PhantomProcessList.killPhantomProcessGroupLocked(app, proc, reason, subReason, msg)` with the reason `ApplicationExitInfo.REASON_EXCESSIVE_RESOURCE_USAGE` and a message of the form "excessive cpu ... during ... dur=...".
- Condition on the parent app seen in the same code: the app's set process state is `>= PROCESS_STATE_HOME` (not top / foreground-visible). A CPU percentage limit tier (`POWER_CHECK_MAX_CPU_1..4`) is compared with CPU time used over the check interval.
- `killPhantomProcessGroupLocked` kills the triggering phantom, then its siblings ("Caused by siling process"), then the PARENT APP ("Caused by child process"), unconditionally.
- A separate path, `trimPhantomProcessesIfNecessary`, kills only surplus phantoms above `MAX_PHANTOM_PROCESSES`; it does not kill the parent.
- The runner is started with `ProcessBuilder` from the app, so it is a child of the app process and a candidate for this tracking. WHETHER this killed the app in the observed run is NOT established: a kill by this path would normally show `REASON_EXCESSIVE_RESOURCE_USAGE` and the "Caused by child process" text in the exit record (`dumpsys activity exit-info`, logcat -b events/system). Without that record it stays one hypothesis next to memory pressure, a native crash and vendor policy.

## 2. USB / libusb shim / network buffers (host/libusb_shim.c, host/usb_host.c, devices/virtio_usb.c, host/dns_proxy.c)
- Per-transfer allocations in the shim are small: `XferBox` (transfer struct), control-transfer buffers of 8 + wLength (wLength ≤ 65535), descriptor copies; each has a matching free on the normal path (`libusb_free_transfer`, `free(buf)` in `ctrl_transfer`). Counted by grep: libusb_shim.c 12 allocation sites / 18 frees, usb_host.c 2 / 6, virtio_usb.c 4 / 8, dns_proxy.c 2 / 7. Counts are not a leak proof (error paths not traced one by one).
- Bulk data buffers are supplied by the CALLER (the restore stack / libirecovery code under third_party), not allocated by the shim. So whether firmware / IMG4 / IPSW members are held whole in memory is decided in that stack; this was not traced here and no peak is claimed.
- IPSW SHA-256 check (host/g7_ipsw_check.c) allocates nothing itself.
- Still open: trace the restore stack's buffers for the largest members (RootFS is streamed or not), Reverse Proxy session buffers, net_slirp queues. Needed before saying anything about USB/network memory.

## 2026-11-25 — why iBootStage1 stops in recovery mode (reviewer 6; source reading only, nothing on the device changed)

Restore-end handling (third_party/idevicerestore, libirecovery, host):
- dfu.c sends `setenv auto-boot false` + `saveenv` to iBootStage1 after the stage-1 components, then `setenvnp boot-args rd=md0 nand-enable-reformat=1 -progress ...`.
- recovery.c `recovery_set_autoboot` is called with 0 in `recovery_enter_restore`. idevicerestore.c sets auto-boot true + reset only for the old AppleTV path.
- No host code in this repo restores `auto-boot=true` / `boot-command` for a vmapple restore. That normalisation is expected from the restored ramdisk steps (set_one_time_boot_command, set_nvram_variables, persistent_boot_args, generate_boot_policies, bless_system_volume, set_boot_command, set_bootable all succeeded in the log) — whether they persisted into macos_aux.img is UNVERIFIED.
- The install pair was left `in_progress` with seal_system_volume not confirmed, so a skipped final switch to normal boot is possible but UNVERIFIED.

Read-only tools added for the next phone run (APK, mode D / AUX button):
- "AUX 비교 실행": macos_aux.initial vs macos_aux.img (size, hash, changed ranges, header, NVRAM-like regions, string hits flagged as a string search only), and each clone vs the original image.
- `--usb-mode 3` (D): mode C plus `getenv` of auto-boot, boot-command, boot-args, bootdelay, build-version using the same wire requests as irecv_getenv (vendor OUT 0x40/req 0 "getenv X", IN 0xC0/req 0). Only when the PID is 0x1280-0x1283; no setenv/saveenv/reboot/DFU/bulk. An empty reply means "unset or no answer" (not distinguishable); a failed transfer is logged as QUERY FAILED.

## 2026-11-27 — NVRAM in this host, S0 log and S1 pre-seed (research/g7-nvram1)

- [V code] There is no NVRAM device. The guest's NVRAM lives inside the aux image (macos_aux.img, first 16 KiB hidden). iBoot reaches it through bdif (devices/bdif.c aux channel) and the kernel through the aux virtio-blk; both end in hv_disk_read/write/flush on the same HvDisk (host/disk.c). A guest NVRAM write is an ordinary aux write: the host accepts it with pwrite on the clone's writable aux file (readonly_storage=0 in ui_runner_vm_clone), a sync is hv_disk_flush. The host parses, filters and keeps nothing; persistence is the file itself (the clone's macos_aux.img, folder vm/clones/clone-NNN).
- S0 (default ON): host/g7_nvram.h observes the aux disk (hv_disk_set_trace, read-only) and prints at most 200 `g7-nvram:` lines plus one `g7-nvram: summary` at stop into the runner's stdout (so into g7_cboot_*.txt). Recognition of variable entries uses the public v3 layout ("3VVN" store, 0x55AA entries, CRC-32 of the value) [I: that this guest uses it is unverified]. G7_NVRAM_LOG=0 turns it off.
- S1 (default OFF): marker file `nvram_preseed` (boot-dialog checkbox, writes `auto-boot=true`) or env G7_NVRAM_PRESEED / HENGE_NVRAM_PRESEED (`auto-boot=true;boot-volume=<explicit string>`). Writes only into a valid "3VVN" store found in the aux image (newest generation, appended entry, older copy marked 0x7c); no store, no room or a non-erased tail = nothing written, and the line says so. boot-volume has no default: its format is [N].
- [N] where the store sits in aux, whether the guest uses v3 at all, the value encoding of auto-boot (with/without NUL), the boot-volume format.
- Test: tools/g7-nvram-test.sh <build dir> (Linux). Source rules: tools/check-g7exec-launcher-source.sh.

## 2026-11-27 — JIT size selection (H1) and early framebuffer observation (F1) (research/g7-hjit2)

JIT size. The clone-boot dialog has a "JIT 크기" spinner {64, 128, 256, 384, 512, 768} MiB, default 64 (index 0; every earlier build passed 64). It is not remembered. G7CloneBoot validates the value against exactly that set and refuses the start otherwise, so no other value reaches `--jit-mb` (the runner itself would accept 16..768). Test hook (the activity takes no Intent input): marker file `jit_mb` containing one of the six numbers in the app's vm folder next to `vm_ecid.txt` (`adb shell run-as <pkg> sh -c 'echo 256 > files/vm/jit_mb'`); it only preselects the spinner, a person still starts the run. Anything else = 64.
Recorded in: the run log header (`g7-jit-config: jit_mb=<n> (default|chosen ...)` and `jit_mb=<n>;` inside `g7-gpu-options:`), `run-info.txt` (`jit_mb=`), and the export manifest (`run_jit_mb=`).
Per-window line (runner stdout, every 10 s, next to `g7-mem:`/`g7-diag:`; only values the loop already has + one getrusage):
`g7-jit: t=<s>s jit_mb=<n> used_mb=<x> flushes=<total>(+<window>) full=<total>(+<window>) dropped_blocks=<total>(+<window>) emit_fail=<n> table_full=<n> rss=<MiB> swap=<MiB> majflt=<total>(+<window>)`
flushes = whole-JIT flushes (block_flushes); full = flushes because the code region was full; dropped_blocks = translations thrown away by flushes; swap = the process's VmSwap; majflt = process major faults. The engine's own `stats` line (stderr, every 10 s) now says `blocks held <n> (<used> of <capacity> MB jit, <n> full flushes)`.
A/B reading: 64 vs 256, same clone, same run time, nothing else changed: compare `full=` and `dropped_blocks=` growth per window, `majflt`/`swap` growth, and the time the guest reaches the same stage.

F1 early framebuffer observation (host/g7_fb0.h, sampler in host/vm.c, only when env G7_FB0=1; the dialog checkbox "초기 프레임버퍼 관찰" is default ON). From the VM start every 250 ms for 60 s it counts the drawn words (any of bytes 0..2 != 0) and a 4-lane hash of the boot framebuffer window: boot_args Video words once a boot_args page exists, else the fixed carveout 0xef540000 (+9 MiB, clipped to RAM). A line is written only when the hash changed; at most 200 lines; at most 3 dumps (first nz>0, then nz changed by a factor >= 4) into LAGFX_ARM64_DUMP_DIR (needs the shader/pipeline dump checkbox, else the log says "NOT saved (no dump folder)").
`g7-fb0: start ...` / `g7-fb0: t=<s>s nz=<n> of=<words> hash=<hex> src=<raw|boot_args> base=<hex> win=<WxH|bytes> change=<first|nz_up|nz_down|same_nz> dump=<none|first_nz|big_change> (n=<scan>)` / `g7-fb0: boot_args t=...` / `g7-fb0: dump ...` / `g7-fb0: end t=<s>s scans=<n> total_ms=<x> max_ms=<x> lines=<n> suppressed=<n> dumps=<n> nz_first_t=<s|none>`. Cost: 0.96 ms per 9 MiB scan on a PC (x86); the end line reports the real cost on the phone. nz is comparable only inside one `src`. If boot_args never appear and the carveout is not at the default address, the raw window shows nothing useful ([I]).
Test: tools/g7-fb0-test.sh <build dir>. Source rules: tools/check-g7exec-launcher-source.sh.

## 1. Coherent vs non-coherent fetch selection
- vk_renderer.cpp, Renderer::initFeatures (~6430-6530). READ.
  - supportsRasterizationOrderAttachmentAccess = feature bit rasterizationOrderColorAttachmentAccess (EXT or ARM ext). Comment states: when colour fetch is used ANGLE sets the colour-blend-state flag (RASTERIZATION_ORDER_ATTACHMENT_ACCESS_BIT_EXT) AND the subpass flag (RASTERIZATION_ORDER_ATTACHMENT_COLOR_ACCESS_BIT_EXT); depth/stencil fetch uses the two depth-stencil-state flag bits.
  - Both supportsShaderFramebufferFetch and ...NonCoherent are enabled together (disabled only on Samsung for perf, Intel-desktop exceptions). So non-coherent fetch needs no extension: it is a plain input attachment + barrier.
  - mIsColorFramebufferFetchCoherent = ARM || PowerVR || rasterOrder extension enabled. READ.
- Differs from ours? We always use the coherent path (flag set). ANGLE's coherent path is identical in intent; but ANGLE has a complete NON-coherent fallback and Qualcomm gets the coherent path only if the extension is exposed. INFER: a "no rast-order flag + explicit barrier" experiment (already in your matrix c4) is exactly ANGLE's non-coherent mode, so it is a legitimate production-proven configuration; make it a priority variant.

## 2. Qualcomm / Adreno specific workarounds (grep isQualcomm, Adreno, qcom)
- vk_renderer.cpp ~6451, feature addFramebufferFetchBarrierOnUseMidRenderPass = rasterOrder supported AND vendor is Qualcomm (any driver, incl. open source). READ. Introduced by upstream commit a0e6aa12b8a9 "Vulkan: Enable raster order att access on QCOM" (title only, INFER date 2026-05). ContextVk::onFramebufferFetchUse (~9600-9645) READ: if a render pass already had draws WITHOUT fetch and then a fetch draw arrives, ANGLE inserts a memory barrier (src colour-attachment write -> dst input-attachment read, stage COLOR_ATTACHMENT_OUTPUT -> FRAGMENT_SHADER, by-region) because the driver does not synchronise automatically between non-rast-order draws and later rast-order draws; comment says "likely a driver bug". Differs: we have no such barrier (INFER: only matters at runtime, not at pipeline creation).
- vk_renderer.cpp ~7295-7312, preferDynamicRendering requires dynamicRendering + dynamicRenderingLocalRead and is FORCED OFF for Qualcomm proprietary driver < 512.801 (crbug 415738891 "driver bugs"); also off for ARM < 52 and PowerVR. READ. Comment: dynamic rendering + local read is needed for fb fetch, MSRTT and advanced blend emulation. Differs/INFER: shows Qualcomm's dynamic-rendering path has had real bugs; our Adreno 840 build (089d643e2a, driver 512.x?) is far newer than 801 so ANGLE would use dynamic rendering there. Check our driverVersion decoded with ANGLE's rule (major 512 minor N) to compare with the 512.8xx thresholds below.
- Other Qualcomm proprietary version gates (all READ, vk_renderer.cpp): SPIR-V 1.4 disabled below 512.829 (pipeline CREATE crash with OpCopyLogical, anglebug 343218484, ~6589); MSRTSS disabled below 512.822 (~6143); imageless framebuffer bug below 512.806 (~6904); vkCmdClearAttachments race below 512.762.12 (~6380); library blobs not reused by monolithic pipelines on Qualcomm (~7005); no explicit per-sample shading on Qualcomm (~7148); roundOutputAfterDithering on Qualcomm (~6540). INFER: the OpCopyLogical pipeline-create crash is the closest public precedent for "valid SPIR-V makes Adreno pipeline creation fail"; check whether our fs SPIR-V contains OpCopyLogical or SPIR-V >= 1.4 (pipe13 says SPIR-V 1.4+ features not present; OpCopyLogical not checked: grep the spirv-dis). Also check our module's declared version vs the device (1.3 target would avoid it).
- No Adreno-model-specific rule touches framebuffer fetch (only Adreno 540/622/702 rules on unrelated features). READ via grep.
- No kQualcomm/qcom string related to fetch; QCOM hits are VK_QCOM_tile_memory_heap / render_pass_store_ops only. READ.

## 3. Pipeline state/flags for fetch
- vk_cache_utils.cpp GraphicsPipelineDesc::initializePipelineFragmentOutputState (~4040-4075). READ. Colour blend state flags get the rast-order bit only if feature supported AND the render pass desc carries colour fetch mode; no other pipeline create flags are set for fetch. Depth/stencil flag bits only for depth/stencil fetch (~3880). Same as ours on the colour blend bit. Differs: ANGLE derives the flag from the render-pass desc, so it is set only on pipelines actually used with fetch; ours presumably identical (flag only when raster_order_access=1).
- Pipeline create flags in ANGLE: nothing fetch-related (flags 0, library/protected/fragment-shading-rate/legacy-dithering only; vk_cache_utils.cpp 3332-3450, 521-560). READ. Differs: none.
- Blend attachment count = renderPass colorAttachmentRange (highest used index + 1) (~4050). INFER: ANGLE uses contiguous range; our 2-attachment state matches if both used.
- Pipeline rendering info (dynamic rendering): AttachPipelineRenderingInfo (~521-560) READ chains VkPipelineRenderingCreateInfo (formats for all colour attachments) and NOTHING else for local read. 

## 4. Dynamic rendering local read: mapping structs (KEY finding)
- grep over the whole vulkan backend for VkRenderingInputAttachmentIndexInfo, VkRenderingAttachmentLocationInfo, vkCmdSetRenderingInputAttachmentIndices, vkCmdSetRenderingAttachmentLocations: ZERO hits. READ (negative grep). ANGLE relies on the spec's default identity mapping (colour i <-> InputAttachmentIndex i <-> Location i) and never chains or sets the mapping structs; MSRTT/ blend emulation likewise.
- Differs? NO, same as ours (we also do not chain them). So the missing mapping structs are NOT a likely cause of -13 (INFER): a shipping Adreno path works without them (though INFER whether it has been exercised on A8xx: unknown).
- Image layout: input-attachment colour images use VK_IMAGE_LAYOUT_RENDERING_LOCAL_READ both as the colour-attachment layout in rendering info and in descriptor writes (vk_barrier_data.cpp 55-125 ColorWriteAndInput; vk_cache_utils.cpp 6859 updateInputAttachment layout; 7646 legacy render pass colorRef uses it too). READ. Barrier data for it: stages COLOR_ATTACHMENT_OUTPUT, access colour read|write. Not relevant to pipeline creation (INFER) but relevant to runtime correctness: ours should use LOCAL_READ layout for both.
- Explicit barrier for glFramebufferFetchBarrier: ContextVk::handleDirtyGraphicsFramebufferFetchBarrier (~3108): memory barrier colour-write -> input-attachment-read, stage colour-output -> fragment shader, by-region flags (GetLocalDependencyFlags). Blend barrier (handleDirtyGraphicsBlendBarrier ~3126): colour write -> COLOR_ATTACHMENT_READ_NONCOHERENT_EXT, skipped if blend-op-advanced-coherent supported. READ. Legacy render-pass equivalent: subpass self-dependency built in vk_cache_utils.cpp ~1040-1120 (fb-fetch: src colour output/colour write, dst fragment shader/input read, by-region). READ. For us: no blend barrier relevant (blend_enable 0).

## 5. Input attachment declaration in SPIR-V / descriptors (KEY finding)
- src/compiler/translator/tree_ops/spirv/EmulateFramebufferFetch.cpp (~244): the translator gives each subpassInput layout inputAttachmentIndex = the colour index of the inout/gl_LastFragData slot (= the output location). src/compiler/translator/spirv/BuildSPIRV.cpp (~2197-2230): input-attachment variables get DescriptorSet 0 + a Binding, plus the InputAttachmentIndex decoration (depth/stencil inputs omitted: no index = depth/stencil). Locations are not used for input attachments. READ. Differs: no (ours uses InputAttachmentIndex 0/1).
- Binding layout (spv_utils.cpp AssignInputAttachmentBindings ~706-765; ProgramExecutableVk.cpp ~1365-1385; vk_cache_utils.cpp ~5985-6010): the input attachments occupy a CONTIGUOUS block of bindings starting at base, binding = base + colour index; ANGLE then reserves maxColorInputAttachmentCount (= min(maxColorAttachments, 8) with MRT fetch, 1 for advanced-blend emulation; vk_caps_utils.cpp 1440-1460) bindings, and declares EVERY one of them in the descriptor set layout as INPUT_ATTACHMENT, fragment stage only, count 1, even when the shader uses only some; unused ones are filled with dummy descriptors (descriptorCount toggles to 0 in the write descs). READ. When depth/stencil fetch is on, two extra bindings precede the colour block. Differs: ours has bindings 40,41 only (INFER from pipe13: layout lists 40 and 41 as input attachment). Not decisive: both layouts are legal. Experiment idea (INFER, cheap): present a contiguous N-binding input-attachment block with index == binding-base, and/or declare extra unused INPUT_ATTACHMENT bindings.
- Multisample fetch transformer (spv_utils.cpp ~3005-3040): adds SampleRateShading capability before InputAttachment capability only for multisampled fetch. N/A for us (single-sample, INFER).

## 6. Legacy render pass path (for contrast; our dynamic path is the relevant one)
- vk_cache_utils.cpp ~7870-7900 READ: subpass input attachments = the colour attachment refs (all colour attachments) with layout ColorWriteAndInput; subpass flag RASTERIZATION_ORDER_ATTACHMENT_COLOR_ACCESS_BIT set when colour fetch is in the desc; pipelines flag matches (VUID requires). ANGLE keeps the legacy path for old Qualcomm drivers. Experiment F in /tmp/oss-adreno13.md (legacy render pass + self-dependency) is ANGLE's fallback; INFER high value as a control.
- permanentlySwitchToFramebufferFetchMode (vk_renderer.cpp 7319): tile-based legacy passes stay in fetch mode to avoid render-pass breaks; with dynamic rendering switching is free. N/A.

## Five most relevant findings
1. ANGLE never chains VkRenderingInputAttachmentIndexInfo / VkRenderingAttachmentLocationInfo and never calls the set-mapping commands (READ, whole-backend grep negative): same as us, so absence of mapping structs is an unlikely -13 trigger.
2. ANGLE keeps a complete non-coherent fetch path (input attachment + by-region colour->input barrier, no rast-order flag) and only uses the rast-order flag when the extension is exposed; test that mode on Adreno 840 (READ for ANGLE; INFER for value to us).
3. Qualcomm-specific: addFramebufferFetchBarrierOnUseMidRenderPass (commit a0e6aa12b8a9, 2026-05 per search title) and dynamic rendering disabled on Qualcomm drivers < 512.801; these are runtime/driver-age issues, not pipeline-creation fixes (READ gates, INFER relevance).
4. Closest Qualcomm pipeline-creation precedent: SPIR-V 1.4 disabled below driver 512.829 because pipeline creation crashed with OpCopyLogical (anglebug 343218484); check whether our fs uses OpCopyLogical or a SPIR-V version above 1.3 (INFER; not yet checked, pipe13 notes no 1.4+ features).
5. ANGLE's input-attachment descriptor layout is a contiguous block, binding = base + index, all up-to-8 declared INPUT_ATTACHMENT / fragment-only; InputAttachmentIndex equals colour index equals Location; ours uses sparse bindings 40/41 in a 30-binding layout (INFER differences; low-cost variants to try).
